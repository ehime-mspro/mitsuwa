## 0. この文書について

- **目的**: 紙の「決裁申請書」（Excel を印刷し、押印して回覧）をやめ、申請から社長決裁までをシステム上で完結させるための要件を確定する。
- **読み方**: 1〜13 章は業務の決まりごと（誰が・何を・どうする）。14 章以降は安全対策と技術の仕組み（主に開発者向け）。
- **決定の出どころ**: 本書の内容は 2026/09/11 のヒアリングで決定したもの。v1.1 では、これに加えて段階 0 を本番で動かして分かった事実と、2026/09/15〜16 の対話で決まった段階 1 の変更を反映した（詳しい経緯は `docs/superpowers/specs/2026-09-16-approval-phase1-design.md`）。v1.2 では、受け取った過去の決裁台帳を実物で調べて 11 章を書き直した（調査の記録は `docs/決裁申請_過去台帳の調査.md`）。v1.3 では、住宅の契約用の申請画面の見本をご覧いただき、確かめたい 7 点にいただいた判断（2026/09/17）を 5.5 に反映した。v1.4 では、v1.3 で開発側の判断として決めた 3 点を読み直し、ご判断（2026/09/17）を受けて 2 点を直した。v1.5 では、同じ読み直しを文書全体に広げ、確認を取らずに開発側で決めていた 13 か所を洗い出して 6 か所を直した（点検の記録は `docs/決裁申請_要件定義書の点検.md`）。v1.6 では、そのうち会社の実情を伺う必要があった 4 件にご判断（2026/09/17）をいただいて確定した。v1.7 では、様式が届いたときの判定の手順を用意した。v1.8 では、部門専用の様式が住宅・不動産の契約用だけであるとご確認いただき（2026/09/24）、様式の受領待ちを解消した。v1.9 では、段階 2（決裁の本体）の設計の対話（2026/09/25〜26）で決まった変更を反映した（詳しい経緯は `docs/superpowers/specs/2026-09-25-approval-phase2-design.md`）。まだ決まっていない事項は 17 章「未確定事項」にまとめ、本文には書かない。

## 1. 概要

### 1.1 目的

紙の押印回覧をやめ、申請 → 部門長 → 審査部門 → 社長の決裁を、パソコンとスマホから行えるようにする。あわせて、決裁の記録（誰がいつ何を判断したか）を改ざんできない形で残し、決裁台帳として検索・Excel 出力できるようにする。

### 1.2 利用者と規模

| 項目 | 内容 |
|------|------|
| 対象 | グループ全体（ミツワ都市開発・DAD・ZEAL） |
| 利用者数 | 100 人以上 |
| 最終決裁者 | 社長（グループ全体の全件を同じ社長が決裁） |
| 利用端末 | パソコン・スマホ（ブラウザで利用。専用アプリなし） |

### 1.3 今回作るもの（開発スコープ）

| # | 機能 | 内容 |
|---|------|------|
| 1 | 申請 | 申請書の作成・下書き・提出・取り下げ・コピーして作成 |
| 2 | 回覧と決裁 | 部門長の承認/差戻し、審査部門の意見、社長の決裁、条件確認、差戻し後の再申請（変更点の表示） |
| 3 | 申請の種類 | 種類ごとの見出しと審査部門の設定（種類ごとの作り込みは 5.5） |
| 4 | 決裁No | 「R8-J-001」形式の自動採番（会社ごとの期） |
| 5 | 閲覧権限 | 関わった人・部門長・全件閲覧者・管理者だけが見られる制御 |
| 6 | 通知と催促 | システム内のお知らせ、メール通知、平日朝のまとめ催促 |
| 7 | 電子印と PDF | 日付入りデータ印、現行様式に近い PDF |
| 8 | 決裁台帳 | 検索・絞り込み・Excel 出力（紙の決裁を含む） |
| 9 | 過去の紙の決裁の取り込み | Excel 台帳の一括取り込み（スキャン PDF の一括紐づけは、今はスキャンが無いため仕組みだけ用意。11.5） |
| 10 | 管理機能 | 利用者・部門・種類の管理、進行中の申請の管理（付け替え・押し間違いの取り消し） |
| 11 | 基幹システムの改修 | 社員番号ログイン、「決裁のみ」利用者、社員の CSV 一括登録、ログイン案内の印刷 |
| 12 | バックアップ | データベース全体と添付ファイルを毎日暗号化し、外部（さくらのオブジェクトストレージ）へ保管 |

### 1.4 今回作らないもの

| 項目 | 理由・代わりの扱い |
|------|------|
| 会長決裁・報告案件・決裁区分 | 全件を社長決裁とするため不要 |
| 関連部門の審査・項目番号 | 使っていないため不要 |
| 代理決裁 | 不要（スマホで決裁できるため） |
| 金額による決裁ルートの分岐 | 全件を社長決裁とするため不要 |
| 決裁希望日 | 不要と決定 |
| スマホ専用アプリ | ブラウザで対応 |
| 会計・支払との連携 | 今回は対象外 |
| 電子署名・タイムスタンプ等の法的な電子契約機能 | 社内の決裁記録として、操作の記録（14.2）で担保する |

### 1.5 前提・制約

| 項目 | 内容 |
|------|------|
| 言語・仕組み | PHP（Laravel 12）。既存の基幹システム（経営管理システム `manage`）の中に「決裁」機能として作る |
| サーバー | さくらのレンタルサーバ ビジネスプロ（基幹システムと同じサーバー） |
| データベース | MySQL 8（基幹システムと同じデータベース） |
| ログイン | 基幹システムと共通（同じログイン画面・同じ利用者） |
| 稼働 | 決裁は全機能がそろってから一括で開始する（バックアップだけは先に動かす。16.1） |

## 2. 用語

| 用語 | 意味 |
|------|------|
| 申請者 | 申請書を作って提出する社員 |
| 部門 | 申請を出す単位（事業部）。部門ごとにアルファベット（住宅 = J など）を持つ |
| 部門長 | 部門の事業責任者。申請を最初に承認する |
| 審査部門 / 審査担当者 | 申請の種類ごとに決まる審査役の部門と、そこで意見を入れる担当者（複数可） |
| 社長 | 最終決裁者。基幹の管理者が 1 人を指定する |
| 全件閲覧者 | すべての申請を見られる人（経営層＝役員）。決裁用に一人ずつ指定する |
| 決裁の管理者 | 決裁機能の設定と運用（利用者・部門・種類・進行中の申請）を担当する人 |
| 基幹の管理者 | 基幹システムの経営層（既存の管理画面を使える人） |
| 決裁のみ利用者 | 基幹システムの他の機能は使わず、決裁だけを使う社員 |
| 回覧 | 申請が部門長 → 審査部門 → 社長と順に回ること |
| 差戻し | 部門長または社長が、申請者に申請を戻すこと |
| 取り下げ | 申請者が、社長の判断の前に申請をやめること |
| 条可 | 条件付き可。社長が条件を付けて可とすること |
| 決裁No | 社長の判断時に付く番号（例: R8-J-001） |
| データ印 | 部署・日付・苗字の 3 段の丸い電子印 |

## 3. 登場人物と役割

### 3.1 役割一覧

| 役割 | 誰 | できること |
|------|----|-----------|
| 申請者 | 全利用者（社長に指定されている人を除く。4.3 のケース 9） | 申請の作成・提出・取り下げ・再申請・条件確認、自分の申請の閲覧 |
| 部門長 | 部門ごとに 1 人 | 自部門の申請の承認・差戻し、自部門の申請（過去分を含む）の閲覧 |
| 審査担当者 | 審査部門ごとに 1 人以上 | 回ってきた申請への意見（可・保留・否＋コメント） |
| 社長 | 1 人 | 決裁（可・条可・差戻し・否） |
| 全件閲覧者 | 指定した人（役員） | すべての申請の閲覧（操作はできない） |
| 決裁の管理者 | 指定した人（少人数） | 管理画面（13 章の⑦〜⑫）の操作、すべての申請の閲覧 |
| 基幹の管理者 | 基幹の経営層 | 権限に関わる設定（3.2） |

- 1 人が複数の役割を持ってよい（例: 部門長で、かつ審査担当者）。
- 部門長・審査担当者・社長にはメールアドレスが必須（メールの無い社員は申請者としてのみ使える）。
- 部門長・審査担当者は、その部門に所属していなくてもよい（例: 住宅（少額・追加工事）の部門長を住宅事業部と同じ人にする）。選べるのは有効でメールアドレスのある人で、許可していないドメインの人には「通知メールが届きません」と注意を出す。

### 3.2 権限設定の線引き

なりすましや権限の乗っ取りを防ぐため、設定できる人を分ける。

| 設定 | 設定できる人 |
|------|------------|
| 社長の指定 | 基幹の管理者のみ |
| 全件閲覧者の指定 | 基幹の管理者のみ |
| 決裁の管理者の指定 | 基幹の管理者のみ |
| 部門長・審査担当者・所属部門・申請の種類 | 決裁の管理者 |
| 決裁のみ利用者の登録（CSV）・パスワード再発行・氏名と社員番号の修正・無効化と有効化 | 決裁の管理者（決裁のみ利用者に限る。ただし下の行の人は除く） |
| 社長・全件閲覧者・決裁の管理者に**指定されている人**への、パスワード再発行・無効化と有効化・氏名と社員番号の修正 | 基幹の管理者のみ |
| 決裁のみ利用者のメールアドレスの変更・利用者の削除 | 基幹の管理者のみ |
| 基幹を使う利用者のパスワード再発行・権限変更 | 基幹の管理者のみ（今までどおり） |

- 決裁の所属部門の編集だけは、上の指定の有無にかかわらず、決裁の管理者が全員について行える。
- 決裁の管理者を上の指定から外している理由: 決裁の管理者は再発行で新しいパスワードを見られるため、社長や全件閲覧者に指定された人のパスワードを再発行できると、その人になりすまして決裁できてしまう。メールアドレスの変更を外している理由も同じで、変更できると再発行の通知（12.5）を本人に届かないようにしてから再発行できてしまう。
- これらの設定の変更は、すべて「誰が・いつ・何を・どう変えたか」を記録する。

## 4. 決裁の流れ

### 4.1 基本の流れ

```
申請者 ──提出──▶ 部門長 ──承認──▶ 審査部門 ──意見──▶ 社長 ──可・条可・否──▶ 決裁確定（決裁No）
                  │                （意見のみ。            │
                  │                  否でも社長へ）          │
                  └──差戻し──▶ 申請者 ◀──────差戻し──────┘
                                  （直して最初から出し直し）
```

- 審査部門は申請の種類ごとに決まる（5.5）。
- 全件が社長まで回る（途中で却下して終わることはない。止めたいときは差戻し）。

### 4.2 各段階でできる操作

| 段階 | 操作する人 | 操作 | コメント |
|------|-----------|------|---------|
| 部門長確認 | その部門の部門長 | 承認 / 差戻し | 差戻しは必須 |
| 審査 | 審査部門の審査担当者のうち誰か 1 人 | 意見: 可 / 保留 / 否 | 保留・否は必須 |
| 社長決裁 | 社長 | 可 / 条可 / 差戻し / 否 | 条可（＝条件）・差戻し・否は必須 |
| 条件確認 | 申請者 | 条件を確認しました | 任意 |

- 判断を確定する前に、必ず確認画面（「〇〇で確定しますか？」）を出す（スマホの押し間違い防止）。
- 審査の意見は、誰か 1 人が入れた時点で社長へ進む。「保留」「否」でも止めずに社長へ回す。
- 同じ段階で 2 人が同時に操作した場合は、先に確定した操作だけを有効にする（後の人には「すでに処理されています」と表示）。
- コメントは 2,000 文字まで（技術上の上限。4.5・4.7 の理由も同じ）。

### 4.3 自動で飛ばすルールと例外ケース

| # | ケース | 扱い |
|---|--------|------|
| 1 | 申請者がその部門の部門長 | 部門長確認を自動で飛ばし、審査から始める（記録に「申請者が部門長のため省略」と残す） |
| 2 | 部門長が社長を兼ねている | 飛ばさない（部門長確認と社長決裁の両方を行う） |
| 3 | 申請者が審査担当者 | 自分の申請には意見を入れられない（他の審査担当者が入れる。回覧の途中で他の担当者がいなくなった場合は、管理者が審査担当者を追加する） |
| 4 | 部門長・社長が未設定、または申請者本人以外の審査担当者がいない | 提出できない（「〇〇が未設定です。管理者に連絡してください」と表示） |
| 5 | 回覧中に部門長が交代 | 部門の設定で部門長を変えると、その部門で部門長確認中の申請は新しい部門長に自動で移る（担当を付け替えた申請も移る。4.7） |
| 6 | 回覧中に社長の指定が変わる | 社長決裁待ちの申請は新しい社長に自動で移る |
| 7 | 回覧中に審査担当者が増減 | 審査の段階は「審査部門」に届くので、その時点の審査担当者が操作できる |
| 8 | 申請者が退職 | 管理者が申請者に代わって取り下げできる（理由必須） |
| 9 | 申請者が社長に指定されている | 申請できない（自分の申請を自分で決裁する形をなくすため。申請の画面に理由を出す） |
| 10 | 判断する番の人が申請者本人（申請のあとで部門長になった場合など） | 自分の申請には、部門長・審査・社長のどの立場でも判断できない。管理者の付け替え（4.7）か、取り下げて出し直す |

### 4.4 差戻しと再申請

- 差戻しを受けた申請者は、申請を直して再提出するか、取り下げる。
- 再提出すると、最初（部門長確認）から回り直す（ケース 1 に当たる場合は審査から）。再提出した時点の設定（部門長・審査部門・審査担当者）で回る。
- 再提出された申請では、前回からの**変更点を色付きで表示**する（件名・金額・実施時期・関連する決裁No・本文・添付の追加と削除）。本文は行ごとに、増えた行と消えた行が分かるようにする。
- 金額の明細表を使う種類（5.5.2）では、**明細表の各行（項目・販売金額・工事原価）と、坪数・坪単価・担当者・契約予定日も変更点の対象**にする。これらの種類では明細表が本文にあたるため、ここを色付きにしないと差戻しの直しどころが分からない。
- 前回までの申請内容と各人の判断は、履歴としていつでも見られる。

### 4.5 取り下げ

- 申請者は、社長の判断が出る前（部門長確認中・審査中・社長決裁待ち・差戻し中）なら、いつでも取り下げできる。コメントは任意。
- 取り下げた申請は削除せず、「取り下げ」として記録に残る。決裁No は付かない。
- 取り下げた申請も「コピーして作成」で新しい申請の元にできる。
- 一度も提出していない下書きは、申請者が削除できる。

### 4.6 条件付き可（条可）と条件確認

- 社長が「条可」を選ぶときは、条件をコメントに書く（必須）。
- 条可の時点で決裁No が付き、申請者に「条件確認のお願い」が届く。
- 申請者が「条件を確認しました」を押すと、決裁が完了する。押すまでは「条件確認待ち」のままで、催促（8.3）の対象になる。
- 条件確認は「確認しました」のみ。条件に異議がある場合はシステムの外で相談する。

### 4.7 押し間違いの取り消し・担当の付け替え（決裁の管理者）

| 操作 | 内容 |
|------|------|
| 押し間違いの取り消し | 申請の**直前の 1 操作**（承認・差戻し・意見・決裁・条件確認）を取り消し、その操作の前の状態に戻す。提出と取り下げは対象外。理由は必須。取り消された操作をした人と申請者に通知する。取り消しの記録は履歴に残る。続けて行えば 1 つずつさかのぼれる（提出の手前まで）。**差戻しの取り消しは、申請者が差戻しのあと中身か添付を直し始めていたらできない**（申請者の直しを守るため。その場合は申請者が再提出する） |
| 担当の付け替え | **部門長確認**の担当者を別の人に変える（休職などの例外時）。付け替え先は有効でメールアドレスのある人（申請者本人は不可）。理由は必須。新しい担当者に通知する。**社長決裁の付け替えは作らない**（下記） |
| 代理の取り下げ | 申請者の退職時などに、管理者が代わりに取り下げる。理由は必須 |

- 社長決裁の付け替えを作らない理由: 決裁の管理者が申請 1 件ごとに「最後に決裁する人」を選べると、社長の指定を基幹の管理者だけに限った 3.2 の意味（なりすまし防止）が崩れるため。社長が長く不在のときは、基幹の管理者が社長の指定を変える（社長決裁待ちの申請はすべて新しい社長に移る。4.3 のケース 6）。
- 決裁の管理者でも、自分が申請者の申請には、付け替え・取り消し・代理の取り下げを行えない（自分の申請の回り方を自分で変えられないようにするため）。

### 4.8 状態の一覧と移り変わり

| 状態 | 意味 | 次に進む状態 |
|------|------|-------------|
| 下書き | 作成中（申請者だけが見える） | 部門長確認中 / 審査中（ケース 1）/ 削除 |
| 部門長確認中 | 部門長の番 | 審査中（承認）/ 差戻し中 / 取り下げ |
| 審査中 | 審査担当者の番 | 社長決裁待ち（意見）/ 取り下げ |
| 社長決裁待ち | 社長の番 | 決裁済み（可）/ 条件確認待ち（条可）/ 否決（否）/ 差戻し中 / 取り下げ |
| 差戻し中 | 申請者の番（直して再提出） | 部門長確認中・審査中（再提出）/ 取り下げ |
| 条件確認待ち | 申請者の番（条件の確認） | 決裁済み（条可） |
| 決裁済み（可・条可） | 完了 | なし（押し間違いの取り消しを除く） |
| 否決 | 完了 | なし（押し間違いの取り消しを除く） |
| 取り下げ | 終了 | なし |

- 押し間違いの取り消し（4.7）では、取り消した操作の直前の状態に戻る（例: 社長の「否」を取り消すと社長決裁待ちに戻る）。

## 5. 申請書

### 5.1 入力項目

| 項目 | 必須 | 形式 | 備考 |
|------|------|------|------|
| 申請の種類 | 必須 | 選択 | 選ぶと本文に見出しが入る。審査部門が決まる |
| 申請部門 | 必須 | 選択 | 自分の所属部門から選ぶ（所属が 1 つなら自動） |
| 件名 | 必須 | 文字（100 文字まで） | 種類に決まり文句が設定されていれば、前半だけ入れると自動で組み立てる（5.5.3） |
| 金額 | 任意 | 数字（円・税抜・12 桁まで） | 表示は「28,500,000円」形式。人事・規程など金額の無い件は空欄。**金額の明細表を使う種類では入力せず、明細表の「合計金額」行の販売金額を自動で使う**（5.5.4） |
| 実施時期 | 任意 | 文字（50 文字まで） | 自由記入（例:「2026年10月〜12月」「決裁後すみやかに」） |
| 重点ポイント（5W2H） | 必須 | 文章（20,000 文字まで） | 見出し入りの箇条書き（5.2）。**見出しのまま（何も書き足していない）では提出できない**。**「5W2H の見出し」を使う種類だけ**。金額の明細表を使う種類では出さない（5.5.2） |
| 関連する決裁No | 任意 | 選択または手入力（10 個まで） | 自分が見られる決裁の番号と件名を候補に出して選ぶ。紙の時代の番号は手入力も可（形だけ確かめる。例: R7-J-015） |
| 添付ファイル | 任意 | ファイル | 5.3 |

- 申請者名・申請部門・提出日時・各段階の日時・添付の件数は、システムが自動で記録する。
- 所属部門が設定されていない人は申請できない（「所属部門が未設定です。管理者に連絡してください」と表示）。
- 社長に指定されている人は申請できない（4.3 のケース 9）。
- 金額の 12 桁・本文の 20,000 文字は技術上の上限（業務で困らない大きさ）。

### 5.2 5W2H の見出し（標準）

「5W2H の見出し」を使う種類（5.5.2）では、申請の種類を選ぶと、本文の欄に次の見出しが入った状態で始まる（種類ごとに変更可能。5.5）。「いつ」「いくら」は実施時期・金額の欄で書くため、見出しには入れない。

```
■ なぜ（目的・理由）
・
■ 何を（内容）
・
■ 誰が（担当・実施者）
・
■ どこで（場所・対象）
・
■ どのように（方法・手順）
・
■ 補足（費用の内訳・その他）
・
```

### 5.3 添付ファイル

- 1 ファイル 10MB まで。種類は基幹システムと同じ（PDF・Word・Excel・CSV・テキスト・画像〈jpg/png/gif/webp/heic〉）。1 件の申請に 20 ファイルまで。ファイル名は 255 文字まで（技術上の上限）。
- 下書き中と差戻し中は、追加・削除できる。提出後は変更できない。添付は、下書きを 1 回保存したあとに追加する（何枚かまとめて選べ、1 つずつ順に送る）。
- 画像と PDF はブラウザ上で表示できる（iPhone の写真の形式 HEIC はダウンロードにする。Safari 以外のブラウザでは表示できないため）。それ以外はダウンロードして開く。

### 5.4 下書きとコピーして作成

- 作成途中で「下書き保存」できる（必須の項目がそろっていなくてよい）。下書きは申請者本人だけが見られる。
- 過去の自分の申請（取り下げ・否決を含む）をコピーして、新しい申請を作れる（添付はコピーしない）。

### 5.5 申請の種類ごとの作り込み

- 種類（例: 購入・発注 / 契約 / 人事 / その他 / 住宅の契約用）は、決裁の管理者が管理画面で追加・変更・並べ替え・停止できる。
- 紙の様式を並べたところ、**枠組み（決裁No・件名・審査部門の欄など）はどの部門でも同じ**で、変わるのは真ん中の本文（「記」）の欄と、そこに付く数項目だけだった。そのため種類ごとに専用画面を作り込むのではなく、**部品を用意して種類ごとに「使うかどうか」と「中身」を設定する**（調査の記録は `docs/決裁申請_様式の調査.md`）。
- 新しい様式が来ても、同じ骨格であれば**開発せずに管理画面の設定だけで足せる**。

#### 5.5.1 種類ごとの設定

| 設定 | 内容 |
|------|------|
| 種類名 | 画面・台帳・PDF に表示する名前 |
| 本文の形 | 「5W2H の見出し」か「金額の明細表」かを選ぶ（5.5.2） |
| 見出し | 「5W2H の見出し」のときに、本文の欄へ最初から入れておく見出し（5.2 が標準） |
| 件名の決まり文句 | 件名の後ろに自動で付ける文字列（5.5.3）。空なら件名は今までどおり手入力 |
| 明細表の行 | 「金額の明細表」のときの行の名前と並び（5.5.4） |
| 追加の入力欄 | 坪数・坪単価・担当者・契約予定日を使うかどうか（5.5.5） |
| 定型文 | 本文の下に固定で表示する文（申請者は編集しない）。空なら表示しない |
| 審査部門 | この種類の申請が回る審査部門（1 つ）。変えても、回覧中の申請は提出したときの審査部門のまま（再提出すると新しい設定で回る） |
| 使える部門 | この種類を選べる部門（複数可）。空なら全部門で選べる |
| 表示順・利用中/停止 | 申請画面での並び順。停止した種類は新しい申請で選べない（過去の申請はそのまま）。停止した種類の下書きは、提出の前に種類を選び直す。差戻し中の申請はそのまま再提出できる |

- 申請部門は 5.1 のとおり申請者の所属部門から入る（種類では固定しない）。
- **「使える部門」を設定した種類は、その部門に所属する人の申請画面にだけ出る**。契約用に「住宅事業部」と「ミツワ不動産」を設定すれば、ほかの部門の方の選択肢には出ない。空にすれば全部門で選べる（購入・発注／人事／その他など、汎用の様式にあたる種類はこちら）。契約用を契約の種類ごとに分けても（5.5.7）、ほかの部門の方の一覧がふくらまないようにするため。

#### 5.5.2 本文の形

| 本文の形 | 本文の欄に出るもの | 5W2H |
|---------|-----------------|------|
| 5W2H の見出し | 5.2 の見出し入りの文章（必須） | 使う |
| 金額の明細表 | 金額の明細表（5.5.4）＋定型文＋補足（自由記入） | **使わない** |

- 住宅の紙の様式には 5W2H が無いため、「金額の明細表」の種類では 5W2H の欄を出さない。5.1 の「重点ポイント（5W2H）必須」は「5W2H の見出し」の種類にかかる。
- 補足（自由記入）は、紙では 2 行だが、画面では行数を制限しない。

#### 5.5.3 件名の組み立て

- 種類に「決まり文句」を設定すると、申請画面の件名欄が〔手で入れる前半〕＋〔決まり文句の表示〕に分かれる。例: 「山田」と入れると件名は「山田様請負新築工事契約の件」になる。組み立てた結果は入力中の画面に出す。
- 決まり文句どおりにできない案件のために、**「件名を直接書く」に切り替えられる**。切り替えると今までどおり 1 行の自由入力になる。
- 決まり文句を設定しない種類は、今までどおり件名を 1 行そのまま書く。
- 件名は**組み立てた結果の文字列として保存する**。あとから種類の決まり文句を変えても、過去の申請の件名は変わらない。

#### 5.5.4 金額の明細表

「金額の明細表」の種類では、本文の欄が次の 5 列の表になる。

| 列 | 入力 / 自動 | 計算 |
|----|-----------|------|
| 項目 | 設定済みの名前、または申請者が入力（自由行） | |
| 販売金額 | 入力 | |
| 工事原価 | 入力 | |
| 粗利益金額 | 自動 | 販売金額 − 工事原価 |
| 粗利率 | 自動 | 粗利益金額 ÷ 販売金額 × 100（小数第 1 位まで） |

- 合計の行は 2 つ。**「計」＝前半の行の合計**、**「合計金額」＝「計」＋後半の行の合計**。合計の行でも粗利益金額・粗利率は同じ式で出す。
- **販売金額が 0 の行の粗利率は「—」と表示する**。紙の Excel に出る `#DIV/0!` は画面にも PDF にも出さない。
- 「計」の行を出すかどうかは種類ごとに設定する（前半だけで完結する様式があるため）。

行の設定（種類ごと）。

- 前半の行・後半の行それぞれについて、**行の名前と並び**を設定する。名前を空にした行は**自由行**（申請者が名前を入れる行）。
- 紙の様式にある自由行は、**最初から空欄で出しておく**。申請者は名前と金額を入れるだけでよく、紙から移った方が行数に迷わない。
- 足りないときは「行を足す」で前半・後半それぞれに増やせる。自由行は消せる。名前を設定した行は消せない。
- 名前も金額も入れないまま残った自由行は、**申請書の作成・編集画面（13 章の②）には出すが、申請の詳細画面（同③）と PDF には出さない**。入力中は行が見えていないと書き足せず、読むときは空の行があっても意味が無いため。名前か金額のどちらかが入っている行は、どちらにも出す。

決裁台帳と PDF に載せる「金額」。

- 「金額の明細表」の種類では、5.1 の金額欄は入力せず、**「合計金額」行の販売金額を自動で金額とする**（建物側と土地側を合わせた総額）。二重入力と食い違いを防ぐため、別に手で入れる欄は出さない。
- 決裁台帳（10 章）・Excel 出力・PDF に載る金額はこの数字。
- 「5W2H の見出し」の種類は、今までどおり 5.1 の金額欄に手で入れる。

#### 5.5.5 追加の入力欄

種類ごとに「使う / 使わない」を設定する。

| 欄 | 形式 | 扱い |
|----|------|------|
| 坪数 | 数字（小数可） | 手入力 |
| 坪単価 | 数字（円） | **手入力**。紙の Excel に計算式が無く、「販売金額 ÷ 坪数」でもないため、自動計算はしない |
| 担当者 | 文字（50 文字まで） | 手入力（利用者とは結び付けず、文字のまま持つ） |
| 契約予定日 | 日付 | **実施時期（5.1）とは別の欄**。下記のとおり意味が違う |

- **実施時期と契約予定日は別のもの**として、両方を持つ。
  - 実施時期 = 工事や実施の期間（例:「2026年11月〜2027年6月」。自由記入・任意）
  - 契約予定日 = 契約を結ぶ予定の日（例: 2026/10/20。日付）
- どちらも申請書の画面と PDF に載せる。決裁台帳（10 章）と Excel 出力には、**「実施時期」と「契約予定日」の両方を列として出す**。金額の明細表を使う種類は紙に実施時期の欄が無く、実施時期の列がほぼ空になるため、契約予定日を出さないと台帳から日付が読み取れなくなる。契約予定日を使わない種類の行は空欄になる。

#### 5.5.6 スマホでの表示

- 幅の狭い画面（およそ 720px 未満）では、明細表は **1 行 = 1 枚のカード**に変わり、縦に並ぶ。項目名がカードの見出しになり、販売金額・工事原価・粗利益金額・粗利率がその下に「名前: 値」の形で並ぶ。
- 横スクロールは使わない。スマホでも明細表の入力と決裁ができる（14.4）。

#### 5.5.7 住宅事業部・ミツワ不動産の設定例

紙の `住宅・不動産決裁申請書.xls` は、住宅事業部とミツワ不動産が**契約のときに使う様式**で、部門専用の様式はこれだけ（ほかの申請は、どの部門も汎用の `決裁申請書.xls`。2026/09/24 確認）。「請負新築工事契約用」を 5.5.1 の設定に置き換えると、次のようになる。

| 設定 | 値 |
|------|----|
| 種類名 | 住宅の契約用（請負新築工事契約） |
| 本文の形 | 金額の明細表 |
| 件名の決まり文句 | 様請負新築工事契約の件 |
| 明細表・前半の行 | 工事請負金額 ／〔自由行 1 行〕／ 紹介料 |
| 「計」の行 | 使う |
| 明細表・後半の行 | 土地契約金額 ／〔自由行 1 行〕 |
| 追加の入力欄 | 坪数・坪単価・担当者・契約予定日（すべて使う） |
| 定型文 | 上記の内容に基づき、販売をおこないます。 |
| 審査部門 | 16.3 でご指定いただく |
| 使える部門 | 住宅事業部・ミツワ不動産 |

- 同じ `.xls` の「追加・少額工事契約用」は、**行の構成だけが違う**（工事請負金額と合計金額にだけ名前があり、間の 5 行は自由行。「計」の行は無い）。様式を読み取って判定したところ（2026/09/17・記録は `docs/決裁申請_様式の調査.md`）、**同じ部品で賄えることを確かめた**。設定は次のとおり。

| 設定 | 値 |
|------|----|
| 種類名 | 住宅の契約用（追加・少額工事契約） |
| 本文の形 | 金額の明細表 |
| 件名の決まり文句 | 様追加・少額工事契約の件 |
| 明細表・前半の行 | 工事請負金額 ／〔自由行 5 行〕 |
| 「計」の行 | 使わない |
| 明細表・後半の行 | 無し |
| 追加の入力欄 | 坪数・坪単価・担当者・契約予定日（すべて使う） |
| 定型文 | 上記の内容に基づき、販売をおこないます。（請負新築工事契約用と同じ文） |
| 審査部門 | 16.3 でご指定いただく |
| 使える部門 | 住宅（少額・追加工事）※ 紙の受付簿が `Ｊ` と `ＪＢ` に分かれているため。6.1 |

- **契約の種類は、請負新築工事契約だけではない**。08 年度の台帳で売買・請負の契約を数えると、住宅は建売売買契約 4 件・分譲地や住宅地の売買契約 2 件、ミツワ不動産は土地売買契約 3 件・建物請負契約 1 件・土地建物契約 1 件だった（台帳の件名は受付簿の書き方なので、契約の種類で数えた。記録は `docs/決裁申請_様式の調査.md`）。どれも明細表の建物側・土地側にそのまま入る（土地だけの契約なら建物側の行は空のまま）が、件名の決まり文句「様請負新築工事契約の件」が合うのは**請負の契約だけ**になる。
- そのため契約用の種類は、(a) 決まり文句を設定せず件名を毎回書く種類を 1 つにする、(b) 契約の種類ごとに種類を分け、それぞれに決まり文句を設定する、のどちらかにする。どちらも管理画面の設定だけで済み、開発には影響しない。**どちらにするかは 16.3 の 2（申請の種類の一覧）で決める**。

### 5.6 紙の様式との対応

| 紙の欄 | システムでの扱い |
|--------|----------------|
| 決裁NO | 決裁No（社長の判断時に自動採番） |

| 件名 | 件名 |

## 6. 決裁No

### 6.1 形式

`R8-J-001` ＝ **和暦の年度** - **部門のアルファベット** - **3 桁の連番**

| 部分 | 内容 |
|------|------|
| R8 | 令和 8 年度。年度の始まりの日が属する元号・年で決める |
| J | 部門のアルファベット（住宅 = J など。部門ごとに異なり、グループ内で重複しない。英大文字 1〜3 文字） |
| 001 | 部門ごと・年度ごとの連番。999 を超えた場合は 1000 以降をそのまま使う |

- 紙の受付簿は、**同じ事業部の中でさらに系統が分かれていることがある**。08 年度の台帳では、住宅事業部が `Ｊ・住宅`（売買契約・用地購入・工事発注などの通常の決裁 34 件）と `ＪＢ・住宅`（少額工事・追加工事 12 件）の 2 冊に分かれ、連番も別々だった（実物で確認。`docs/決裁申請_過去台帳の調査.md`）。住宅の様式が「請負新築工事契約用」と「追加・少額工事契約用」の 2 枚組であることと一致する。
- この場合は、**その系統を独立した部門として登録する**（例: 部門名「住宅（少額・追加工事）」・アルファベット `JB`・部門長は住宅事業部と同じ人）。仕組みを増やさずに紙の連番をそのまま引き継げ、過去分の取り込み（11.2）もシート名のとおりに進む。申請の種類の「使える部門」（5.5.1）も系統ごとに設定できる。
- 系統を分けないと、**過去分の取り込みで決裁No がぶつかる**。08 年度は `Ｊ・住宅` も `ＪＢ・住宅` も ＮＯ が 1 から始まっており、1 つの部門にまとめると `R8-J-001` が 2 件できてしまう。
- 系統を分けると、その事業部の社員は 2 つの部門に所属することになり（兼務。12.3）、申請のたびにどちらで出すかを選ぶ（5.1）。紙でも受付簿を選んでいたため、運用は変わらない。
- Ｂ 系統が何を指すかは**部門ごとに違う可能性が高い**（`ＭＢ` はシート名が「マンション」で、`Ｍ`（ミツワ不動産）とは事業名が違う）。16.3 の部門の一覧をいただくときに、系統ごとに確かめる。

### 6.2 年度の数え方（会社ごとの期）

| 会社 | 期の始まり | 例 |
|------|-----------|-----|
| ミツワ都市開発 | 5 月 1 日 | 2026/05/01〜2027/04/30 に決裁 → R8 |
| DAD | 6 月 1 日 | 2026/06/01〜2027/05/31 に決裁 → R8 |
| ZEAL | 6 月 1 日 | 2026/06/01〜2027/05/31 に決裁 → R8 |

- 部門がどの会社に属するかは、部門の設定で決める。

### 6.3 番号を付けるタイミング

- 社長が「可」「条可」「否」を選んだ時点で付ける（否にも番号を付ける）。
- 下書き・回覧中・差戻し中・取り下げの申請には付けない。

### 6.4 年度途中の開始（開始番号）

- 紙の番号と重ならないよう、決裁の管理者が部門ごとに「今年度の開始番号」を設定できる（例: 紙で J-020 まで使っていたら 21 を設定 → 次は R8-J-021）。
- 開始番号は、その年度にすでに使った番号より小さくできない（番号の重なりを防ぐため）。
- 番号を付けた申請がある部門は、会社とアルファベットを変えられない（同じ年度の番号の続きが崩れるため）。

### 6.5 押し間違いの取り消しと番号

- 社長の判断を取り消した場合、付いていた番号はその申請に残し、次に社長が判断したときにそのまま使う（新しい番号は付けない）。年度をまたいで判断し直した場合も同じ番号を使う（例: 4/30 に付いた R8 の番号を取り消し、5/2 に判断し直しても R8 のまま）。
- その申請が最終的に取り下げで終わった場合、その番号は欠番として台帳に「取り下げ」と表示して残す。

| 見る人 | 見られる申請 |
|--------|-------------|
| 申請者 | 自分の申請（下書きを含む） |

- 社長は上の表のとおり「社長決裁の段階に届いた申請」を見る役割で、回覧の途中の申請や過去の申請は含まれない。**社長を全件閲覧者にも指定しておく**と、いつでもすべての申請を見られる（指定は基幹の管理者が行う。3.2）。

### 8.2 メールに書く内容

- 書くのは「件名・申請者・申請部門・決裁No（付いていれば）・必要な対応・画面へのリンク」だけ。**金額・本文・添付は書かない**（転送や誤送信での漏えい防止）。
- 送信元は会社のドメインの決裁専用アドレス（例: kessai@mitsuwat.co.jp）。
- メールは、決裁の管理者が許可した会社のドメインのアドレスにだけ送る（個人のメールアドレスには送らない）。

### 8.3 催促のルール

| 項目 | 内容 |
|------|------|
| 対象 | 自分の番が来てから 3 日（72 時間）以上経った申請。承認者の対応待ちに加え、申請者の「差戻し中」「条件確認待ち」も含む |
| 送る時刻 | 平日の朝 9 時（日本時間） |
| 送らない日 | 土曜・日曜・祝日（自動で判定する）と、**決裁の管理者が登録した「送らない日」**（年末年始・会社の休業日など） |
| 送り方 | 1 人につき 1 通にまとめる（対象の申請の一覧と、それぞれの待ち日数） |
| 繰り返し | 対応されるまで、送る日の朝ごとにまとめメールに載り続ける |

- 年末年始のように会社ごとに違う休みは、決裁の管理者が管理画面（13 章の⑫）で登録する。**開始日と終了日の期間**で登録し、**「毎年繰り返す」を選べる**（毎年同じ日なら 1 回登録すればよい。年によって変わるときは、その年の分だけ登録し直す）。
- 登録を忘れた場合に起きるのは、休みの日にも催促メールが届くことだけで、決裁そのものは止まらない。

## 9. 電子印と PDF

### 9.1 電子印（日付入りデータ印）

- 形: 赤い丸印の中を 3 段に分け、上段＝部署、中段＝日付、下段＝苗字。
- 上段の表示: 部門長は部門の略称（例: 住宅）、審査担当者は審査部門の略称、**社長は「社長」**。
- 日付: 押した日を和暦で表示（例: R8.9.11）。
- 苗字: 氏名の空白より前を自動で使う。空白の無い氏名などは、決裁の管理者が利用者ごとに「印に使う文字」を直せる。
- 画面（申請の詳細）と PDF の両方に、同じ印を表示する。印はシステムが自動で描く（印鑑の画像の登録は不要）。

### 9.2 PDF

- 現行の決裁申請書に近いレイアウト（A4 縦）で出力する。欄の対応は 5.6 のとおり。
- 申請を見られる人は、いつでも出力できる。決裁が確定する前は、決裁No と決裁日の欄が空欄になる。
- 押された印（部門長・審査担当者・社長）と、各コメントを載せる。申請者が部門長のため部門長確認を省略した場合は、承認欄に「申請者が部門長のため省略」と表示する。
- 本文が長い場合は 2 ページ目以降に続ける。
- 各ページの下に「決裁申請システムから出力（出力日時・出力者）」を入れる。

## 10. 決裁台帳と Excel 出力

- 見られる範囲（7 章）の申請と、取り込んだ紙の決裁を一覧にする。
- 絞り込み: 年度（会社ごとの期）・部門・申請の種類・**申請者**・**決裁日の期間**・状態（既定は決裁No の付いたもの＝決裁済み・条件確認待ち・否決。進行中・取り下げも選べる）・判断（可・条可・否。取り込んだ紙の決裁は「不明」。11.2）・キーワード（件名・本文・備考）・区分（システム / 紙）。
- 並び順: 決裁No の新しい順（既定）。
- Excel 出力: 絞り込んだ結果をそのまま出力する。
- 「金額」の出どころ: 5W2H の種類は申請者が入れた金額、金額の明細表の種類は**明細表の「合計金額」行の販売金額**（5.5.4）。どちらも税抜（2026/09/17 に確認済み）。
- 「契約予定日」の列: 契約予定日を使う種類（5.5.5）の申請だけ値が入る。使わない種類と、取り込んだ紙の決裁（11 章）は空欄。
- 「工事原価・粗利益金額・粗利率」の列: 金額の明細表を使う種類（5.5.2）は**明細表の「合計金額」行**の値、取り込んだ紙の決裁は**金額の控えから取り込んだ値**（11.3）。5W2H の種類は空欄。紙の台帳が「金額の控え」のシートで契約金額と並べて記録していた項目のため、システムでも同じものを見られるようにする。
- 申請者と決裁日の期間で絞り込めるようにする理由: 取り込んだ過去の紙の決裁は「年度・部門・日付・申請者・件名から目当ての決裁を探すための索引」として使う（11.5）。この 2 つが無いと、紙の台帳でできていた探し方がシステムでできなくなる。

## 11. 過去の紙の決裁の取り込み

### 11.1 台帳の形

取り込む元になる Excel 台帳の形は、08 年度の台帳を実物で調べて確かめた（調査の記録は `docs/決裁申請_過去台帳の調査.md`）。**過去の年度も同じ形**なので、取り込みの仕組みは一度作れば全年度に使える。

| 項目 | 内容 |
|------|------|
| 単位 | 年度ごとに 1 ファイル（例: `08年度・決裁申請書契約状況.xls`） |
| シート | 部門ごとに 1 枚。**シート名の先頭が部門記号**（Ｈ本部・Ｃ賃貸・Ｓサ高住・Ｊ住宅・Ｍミツワ不動産・Ｔ特建と、それぞれの Ｂ 系統） |
| 列 | ＮＯ・日付・申請者・件名の 4 つ |
| 件数 | 08 年度は 204 件 |
| ほかに | 住宅の金額の控えのシートがある（11.3） |

読み取りで気をつける点（外すと取りこぼす）。

- **1 枚の中が 2 段組み**。同じ 4 列が左右に並び、右段は 31 番以降。素直に行を読むと右段を丸ごと落とす。
- **見出し行が 34 行ほどおきに繰り返される**。読み飛ばす。
- **ＮＯ は空の行にも印字済み**（1〜120）。ＮＯ の有無ではなく、**日付の有無**で実際に使われた行かを判定する。
- 日付は**和暦のドット形式**（`8.05.07` ＝ 令和 8 年 5 月 7 日）。西暦に直して取り込む。
- ファイルは古い形式（`.xls`）。基幹システムに入っている PhpSpreadsheet で読む。

### 11.2 取り込む項目

| 項目 | 台帳のどこから取るか |
|------|-------------------|
| 決裁No | 部門のシートの**ＮＯ**・シート名の**部門記号**・ファイルの**年度**を組み立てる |
| 決裁日 | 「日付」列 |
| 件名 | 「件名」列 |
| 申請部門 | **シート名から** |
| 申請者名 | 「申請者」列（姓のみ。利用者と結び付けず、文字のまま持つ） |
| 金額・工事原価・粗利益 | 金額の控えから補う（11.3） |
| 判断（可・条可・否） | 台帳に列が無いため、**「不明」**として取り込む |
| 備考 | 台帳に列が無いため、空 |

- 判断が「不明」になるため、決裁台帳（10 章）で判断を絞り込むと、取り込んだ紙の決裁は対象から外れる。

### 11.3 金額の控え

住宅の決裁は、受付のシートとは別に「金額の控え」のシートがあり、契約金額・工事原価・粗利益・入金予定日が入る。

- **決裁No は受付のシートのＮＯが正**。控えのＮＯは使わない（控えは別の連番を持っている）。
- 控えは**日付と件名で受付のシートに突き合わせ**、金額を補う。
- 突き合わせは完全にはできない（08 年度では 9 件中 4 件）。書き方のゆれがあるため。**突き合わなかった分は取り込みの確認画面に出し、決裁の管理者が結び付ける**。
- 取り込むのは**契約金額・工事原価・粗利益**の 3 つで、決裁台帳（10 章）の同じ列に並ぶ。粗利（累計）は計算で出せるため取り込まない。入金予定日は取り込まない（決裁を取るときの情報ではなく、契約後の管理の情報のため。2026/09/17 利用者判断）。

### 11.4 取り込みの進め方

- 決裁の管理者が年度ごとのファイルを選んで一括で取り込む。取り込む前に、**列の対応・取り込み結果（件数・エラー行）・金額が結び付かなかった行**を確認する画面を出す（基幹システムの既存の取り込みと同じ方式）。
- 1 件ずつの登録・修正もできる（決裁の管理者）。
- 取り込んだ記録は台帳に「紙」の印付きで並び、検索と「関連する決裁No」から参照できる。回覧の操作はできない。
- 何年分を取り込むかは運用で決める（稼働後も追加できる）。

### 11.5 スキャンした PDF

現在、紙の決裁申請書はスキャンされておらず、**紙の原本だけ**が保管されている。そのため過去分の中身を見るには紙を見ることになり、取り込んだ台帳は「年度・部門・日付・申請者・件名から、目当ての決裁を探すための索引」として使う。

将来スキャンしたときのために、ファイル名を決裁No（例: `R7-J-015.pdf`）にしてまとめてアップロードすると同じ番号の記録に自動で紐づく仕組みは用意しておく（あとから足すほうが手間がかかるため）。紐づかなかったファイルは一覧で知らせる。

## 12. 利用者とログイン

### 12.1 ログイン

- ログイン画面は基幹システムと共通。**社員番号またはメールアドレス**とパスワードでログインする（基幹を使う人も同じ）。
- 社員番号はグループ全体で重複しない（**ミツワ・DAD・ZEAL は 3 社共通の 1 つの体系で振っていることを 2026/09/17 に確認済み**）。形式は**英数字とハイフン・20 文字まで**。先頭の 0 はそのまま保つ（文字列として扱う）。全角で入れても半角に直し、前後の空白を除き、英字は大文字にそろえてから照合する。`@` は使えない（メールアドレスと区別するため）。
- 既存の仕組みをそのまま使う: ログインの記録、初回ログイン時のパスワード変更、「ログインしたままにする」。
- ログイン試行の制限は数え方を変える。同じログイン ID・同じ IP からの失敗は 1 分に 5 回まで、同じ IP からの失敗はログイン ID を問わず 1 分に 30 回まで。成功は数えない。止まったときはログイン画面に日本語で「〇秒後にもう一度お試しください」と出す。
  - 変えた理由: 今の仕組みは、まだログインしていない人を **IP だけ**で数え、**成功も 1 回に数える**。会社のパソコンは外から同じ IP に見えるため、切り替え日に 100 人がログインすると 1 分に 5 人しか入れず、6 人目から英語のエラー画面になる。

### 12.2 決裁のみ利用者

- ログインすると、決裁のホーム（13 章 ①）に入る。
- 決裁以外の画面（基幹システムのダッシュボードや各事業の画面）には**サーバー側で入れないようにする**（メニューを隠すだけでなく、画面の入口に鍵をかける）。
- 基幹を使う人には、左のメニューに「決裁」が加わり、対応待ちの件数が表示される。基幹のダッシュボードにも「決裁の対応待ち N 件」を表示する。これらは**段階 2 以降**に作る（段階 1 では、一般の利用者に見える変化をログイン画面だけにとどめるため。16.1）。

### 12.3 社員の一括登録（CSV）

| CSV の列 | 必須 | 内容 |
|---------|------|------|
| 社員番号 | 必須 | ログイン ID。重複不可 |
| 氏名 | 必須 | |
| メールアドレス | 任意 | 会社のドメインのみ。部門長・審査担当者・社長になる人は必須 |
| 所属部門 | 必須 | 部門のアルファベット（兼務は複数指定可） |

- 取り込む前に、内容とエラー（重複・未登録の部門・会社以外のドメインなど）を確認する画面を出す。
- 新しい社員は「決裁のみ利用者」として登録する。すでに登録済みの利用者（社員番号またはメールアドレスが一致）は、社員番号と所属部門だけを更新する（基幹の権限は変えない）。

### 12.4 初期パスワードとログイン案内

- CSV で新しく登録した社員には、1 人ずつ別の初期パスワードを自動で作る。形は **10 文字・英小文字と数字だけ**で、見間違えやすい文字（0 o 1 l i）は使わない。
- 「ログイン案内」を 1 人 1 枚で印刷して手渡しする。案内には、システムの URL と QR コード（スマホで読み取ってすぐ開ける）・ログイン ID（社員番号）・初期パスワード・初回ログイン時にパスワードを変える手順を載せる。
- 印刷は**ブラウザの印刷機能**で行う（PDF の作成部品は段階 4 で入れるため。15.4）。登録や再発行の直後の画面に、1 人 1 ページ（A4）の案内を人数分並べて表示し、そのまま印刷する。QR コードはサーバー側で作る。
- 初期パスワードはシステムに残さない（案内の画面に出るのはその場の 1 回だけ）。案内を印刷する前に画面を閉じてしまった場合や、案内をなくした場合は、**選んだ人・絞り込んだ全員をまとめて再発行**して印刷し直せる。案内の画面を閉じようとしたときは、ブラウザの確認を出す。
- 初回ログイン時には、必ずパスワードを変更させる（既存の仕組み）。

### 12.5 パスワードの再発行

- パスワードを忘れた社員は管理者に依頼する（メールでの自己再設定は作らない）。
- 決裁のみ利用者は決裁の管理者が、基幹を使う人は基幹の管理者が再発行する（3.2）。基幹の管理者は、どちらの利用者も再発行できる。
- ただし、社長・全件閲覧者・決裁の管理者に**指定されている人**は、決裁の管理者では再発行できない（基幹の管理者だけ。理由は 3.2）。
- 再発行したときは、メールアドレスのある本人にメールで知らせる（身に覚えのない再発行に気づけるように）。

### 12.6 退職・異動

- 退職者は**無効化**する（ログインできなくなる）。過去の申請・操作の記録と印はそのまま残る。画面の言葉は基幹にそろえて「有効・無効・無効化・有効化」と表示する（v1.0 の「利用停止」と同じもの）。
- 無効にした人がそのときログインしていても、**その場で締め出す**（次に画面を開いた時点でログアウトさせる）。これは基幹を使う人にも効く。
  - 必要な理由: 今の仕組みはログインの瞬間しか確かめないため、「ログインしたままにする」を使っている端末では、無効にしたあとも最長 400 日そのまま使えてしまう。
- 決裁のみ利用者の無効化と有効化は決裁の管理者が行える（3.2 の範囲）。利用者そのものの削除は基幹の管理者だけ。
- 部門長の交代は部門の設定で行う（回覧中の申請の扱いは 4.3 のケース 5）。
- 部門長・審査担当者・社長に設定されている人を無効化・削除しようとした場合や、メールアドレスを空にしようとした場合は、先に後任を設定するよう画面で知らせる（社長に指定されている人は、そもそも決裁の管理者では無効化できない。3.2）。

## 14. 安全対策と非機能要件

### 14.1 アクセスの制御

- すべての画面・操作・ダウンロード・PDF・Excel 出力で、サーバー側で「見てよい人か」「今その操作をしてよい人か」を毎回確かめる。
- 決裁のみ利用者は、決裁以外のすべての画面に入れない（12.2）。基幹に画面が増えても自動で締め出される作り（許可した決裁の画面以外はすべて拒否する方式）にする。
- 権限に関わる設定は 3.2 の線引きに従う。

### 14.2 記録の改ざん防止

- 提出・承認・差戻し・意見・決裁・条件確認・取り下げ・取り消し・付け替えのすべてを、「誰が・いつ・何を・どの状態からどの状態へ・コメント・操作した端末の情報」とともに記録する。
- 記録は後から変更も削除もできない（画面にも仕組みにも、変更・削除の手段を作らない）。
- 決裁が確定した申請は、中身（件名・金額・本文・添付）を変更できない。
- 設定の変更（部門長・審査担当者・権限など）も記録する。
- PDF と Excel の出力、添付ファイルのダウンロードも、誰がいつ行ったかを記録する（情報の持ち出しを後から確かめられるように）。

### 14.3 添付ファイルの保管

- 添付ファイルと取り込んだ PDF は、ブラウザから直接開けない非公開の保管場所に置く。
- ファイルを開くときは、毎回 7 章の範囲を確かめてから渡す。
- 保存するファイル名はシステムが付け直す（元のファイル名は画面表示とダウンロード時に使う）。

### 14.4 スマホ対応と動作環境

- 利用者向けの画面（①〜⑥）は、スマホで操作しやすい表示にする。管理画面（⑦〜⑫）はパソコンでの利用を前提とする（スマホでも表示は崩さない）。
- 横に長い表は、幅の狭い画面では**行ごとのカードに変えて縦に並べる**（横スクロールにしない）。金額の明細表もこの形にする（5.5.6）。
- 対象ブラウザ: 最新の Chrome・Edge・Safari（iPhone を含む）。
- 文字の大きさ・色のコントラスト・キーボードでの操作に配慮する（押せないボタンには理由を表示する）。

### 14.5 性能と容量

- 利用者 100〜200 人、申請は年間数百件を想定する。
- 通常の画面は 3 秒以内、PDF は 5 秒以内に表示されることを目安とする。
- 申請・記録・添付は削除せずに保存し続ける。

### 14.6 バックアップ

- さくらの自動バックアップ（バックアップ＆ステージング）の対象は公開フォルダ（www）のファイルだけで、データベースと基幹システム本体（www の外）は対象外。基幹システムにも、データベースを自動でバックアップする仕組みは現在ない。
- そのため毎日 3:00〜3:04 の回で、次を自動でバックアップする（15.3 の定期実行）。5 分の幅を持たせているのは、定期実行の起動が 5 分おきで時刻がわずかにずれるため。1 分ちょうどを指定すると、起動がずれた日に無言で飛んでしまう。幅を持たせたうえで、その日にちょうど 1 回だけ動くようにしている。

| 対象 | 送り方 | 残す期間 |
|------|--------|---------|
| データベース全体（決裁だけでなく、基幹システムのすべてのデータ） | 毎日まるごと圧縮して送る | 30 日分 |
| サーバーに保存されたファイル（決裁の添付・取り込んだ PDF・基幹システムの既存の添付ファイル） | 新しく増えたファイルだけを送る（添付は後から変わらないため） | 期限なし |

- 送り先は、契約済みの「さくらのオブジェクトストレージ」に新しく作るバックアップ専用の保管場所（バケット）。サーバーとは別の場所で、費用はバケット 1 つにつき月 495 円（100GiB まで含む。2026/09 時点）。
- 送る前にこちらで暗号化する（保管先の石狩サイトには、保存時に暗号化する機能が無いため）。方式は OpenSSL の AES-256-GCM（本番の PHP には暗号化の新しい部品（sodium）が入っていなかったため。2026/09 に実物で確認）。復元に使う鍵（パスワード）は、本番サーバーの設定ファイルに加えて、サーバーの外（紙に書いて金庫に保管するなど）にも保管する。
- 接続用の鍵は、バックアップ専用のバケットだけを扱えるものにする（他のバケットには触れられない）。古いバックアップを消すため、そのバケットの読み書きの権限を持たせる。
- オブジェクトストレージには古いデータを自動で消す機能が無いため、30 日を過ぎたデータベースのバックアップは、定期実行の処理が自分で消す。消すのはバックアップ用の場所の中の、期限を過ぎたものだけに限る作りにする。
- 鍵やパスワードは本番サーバーの設定ファイルに直接書く（この文書やプログラム、git には書かない）。
- バックアップに失敗した日は、あらかじめ決めた宛先（設定ファイルで指定）にメールで知らせる。
- 稼働前に 1 回、バックアップから別の環境へ復元できることを確かめ、復元の手順書を用意する。→ **2026/09/14 に確認済み**（手順書: `docs/運用_バックアップとメール.md`）。
- バックアップは決裁の稼働を待たずに、できあがりしだい先に本番で動かす（16.1 の段階 0）。→ **2026/09/14 から本番で稼働している**。

### 15.1 全体構成

- 基幹システム（`manage`・Laravel 12・PHP 8.3・MySQL 8）の中に「決裁」機能を追加する。本番は同じさくらのサーバーで動く。
- 画面の URL は基幹と同じ場所の下に置く（`/approvals` 以下）。メールのリンクも本番の URL の形式（`/system/manage/index.php/…`）に合わせる。

### 15.2 基幹システムへの改修点

| 改修 | 内容 |
|------|------|
| ログイン | ログイン ID 欄を「社員番号またはメールアドレス」に変更（`@` を含めばメールとして照合） |

| 部門と許可するドメイン | 会社（期の始まりの月）・部門・所属部門（兼務可）・許可するメールのドメインの表と登録画面を追加。基幹の既存の部門とは別の表にする（段階 1 に前倒し。16.1） |
| 無効化したときの締め出し | 無効にした人がログイン中でも、その場で締め出す（12.6） |
| 決裁のみの締め出し | 許可した画面（決裁・パスワード変更・ログアウト）以外をすべて拒否する仕組みを、全画面の入口に追加 |
| ログイン後の行き先 | 決裁のみ利用者は決裁のホームへ |
| メニュー | 決裁のみ利用者に決裁のメニューだけを表示するのは段階 1。左メニュー（パソコンの展開表示・アイコン表示・スマホのメニューの 3 か所）への「決裁」と対応待ちの件数の追加は**段階 2 以降** |
| ヘッダー | お知らせのベルマーク（未読の件数）を追加（**段階 2 以降**） |
| ダッシュボード | 「決裁の対応待ち N 件」を表示（**段階 2 以降**） |
| 利用者管理（基幹の管理者用） | 社長・全件閲覧者・決裁の管理者の指定を追加 |

### 15.3 メール送信と定期実行

**さくらのサーバーの制約（2026/09 調査）**

| 制約 | 内容 | 対応 |
|------|------|------|
| 常駐プログラムの禁止 | 利用規約で、常に動き続けるプログラム（daemon）は禁止 | メールは「送信待ちに積み、定期実行で送る」方式にする |
| 定期実行（CRON）の登録数 | 最大 10 件 | 1 件だけ使う |
| 定期実行の最短間隔 | 毎分は不可（公式の記載はなく、2 分おきまでは動いたという報告あり） | 5 分おきにする |
| 定期実行の PHP | 既定は PHP 7.4 | PHP 8.3 をフルパス（`/usr/local/php/8.3/bin/php`）で指定する |
| 定期実行の出力 | 何も指定しないと管理者あてにメールされる | ログファイルに書き出す |
| 重い処理 | サーバーに高い負荷をかける処理は強制終了されうる | 1 回の処理時間に上限を設け、同じ処理を重ねて動かさない |
| メールの送信上限 | 15 分ごとに 250 通程度（宛先の数で数える） | 催促は 1 人 1 日 1 通にまとめるため、上限には届かない |
| 迷惑メール対策 | SPF・DKIM はコントロールパネルで有効にする必要がある | 有効にしてから送信を始める（16.3 の準備物） |

**メールの送り方**

- 送信元は、さくらのコントロールパネルで作る決裁専用のメールアドレス（例: kessai@mitsuwat.co.jp）。
- さくらのメールサーバーへ SMTP 認証で送る（サーバー名は初期ドメイン `〇〇.sakura.ne.jp`、ポート 587）。この方法で送ると DKIM の署名が付く。
- メールは画面の操作と同時には送らず、いったん「送信待ち」に積む。定期実行が 5 分おきに送信待ちを処理する（メールは最大 5 分ほど遅れて届く。システム内のお知らせは即時）。
- 送信に失敗したメールは自動で再送する（3 回まで）。それでも送れないものは記録に残す。
- メールサーバーのパスワードなどの秘密情報は、本番サーバーの設定ファイルに直接書く（この文書やプログラムには書かない）。

**定期実行**

コントロールパネルに登録するのは「5 分おきに Laravel の定期実行を起動する」1 件だけとし、個々の予定はプログラムに書く（変更の記録が git に残る）。

| 何を | いつ |
|------|------|
| 送信待ちのメールを送る | 5 分おき |
| 催促のまとめメールを送る | 平日 9:00（土日祝はプログラム側で判定し、そのほかの送らない日は設定から読む。8.3） |
| バックアップ（14.6） | 毎日 3:00〜3:04 の回（起動のずれで飛ばないよう幅を持たせ、1 日 1 回だけ動く） |

### 15.4 PDF

- サーバーに特別なソフトを入れず、PHP だけで動く PDF 作成部品を使う（候補: mPDF / TCPDF。実装計画で最新の資料を確認して決める）。
- 日本語フォントは無料で使えるもの（IPAex フォントまたは Noto フォント）を同梱する。
- ログイン案内は PDF ではなく**ブラウザの印刷機能**で出す（12.4）。QR コードは、そのための小さな部品をサーバー側に 1 つ足して作る。PDF 作成部品を段階 1 に前倒しすると、日本語フォントの同梱と本番のメモリの確認まで前倒しになり、100 人分の初期パスワードが入った PDF が管理者のパソコンに残ってしまうため。申請書の PDF は予定どおり段階 4 で作る。

### 15.6 テスト

- 自動テスト（PHPUnit）で、次を確かめる。
  - 状態の移り変わり（4.8 の表のすべて）と、状態に合わない操作が拒否されること
  - 閲覧の範囲（7 章の表のすべて）と、添付・PDF・Excel にも同じ範囲が効くこと
  - 決裁No（会社ごとの期・和暦・開始番号・同時採番・取り消し時の扱い）
  - 例外ケース（4.3 の表のすべて）
  - 催促（72 時間・土日祝・登録した送らない日〈「毎年繰り返す」の指定を含む〉・1 人 1 通）
  - 社員番号ログイン、CSV 一括登録、権限設定の線引き（3.2）
  - 決裁のみ利用者が、決裁以外の**すべての画面**で拒否されること（全画面を機械的に列挙して確かめ、画面が増えても自動で検査対象に入る形にする）
- 基幹システムの既存のテスト（全件検査型のテストを含む）がすべて通ること。
- 本番に関係者限定で載せ、スマホを含めて受け入れ確認を行う（16.2）。

### 15.7 本番への反映

- 既存の手順（`deploy.sh`）で反映する。テーブルの追加・変更は SQL ファイルを本番で実行してから反映する。
- 新しく使う部品（PDF 作成、オブジェクトストレージへの送信など）は、手元でインストールしてから `vendor` ごと本番へ送る（本番では `composer install` を行わない既存の方式）。
- 稼働前に、本番の php.ini（アップロードの上限・メモリ。アップロードの初期値は 2MB という報告がある）と PHP の拡張（PDF に必要な gd など）を確認し、10MB の添付と PDF の作成ができるよう調整する。

## 16. 進め方と稼働までの流れ

### 16.1 開発の順番

決裁の稼働は一括だが、開発は次の順で進め、段階ごとに確認する。段階 0 のバックアップは、できあがりしだい先に本番で動かす（今の基幹システムのデータもすぐに守るため）。段階 1 も、できあがりしだい本番へ反映する（一般の利用者に見える変化はログイン画面だけのため）。段階 2 もできあがりしだい本番へ反映するが、申請を回す画面は使い始める日まで誰にも見せない（部門・申請の種類の登録は本番で先に行える）。

| 段階 | 内容 |
|------|------|
| 0 | 定期実行とメール送信の土台、バックアップ（毎日暗号化して外部へ）。**2026/09/14 から本番で稼働中（完了）** |
| 1 | 基幹の改修（社員番号ログイン・ログイン試行の制限・決裁のみの締め出し・利用者の設定・CSV 一括登録・ログイン案内・**部門と許可するメールのドメイン**）。できあがりしだい本番へ反映する。**2026/09/25 に本番へ反映済み（完了）** |
| 2 | 決裁の本体（部門・種類・申請・回覧・閲覧範囲・添付・記録・変更点・取り消しと付け替え）。**2 回に分けて作る**（2a: 申請を出して社長の決裁まで一通り回る ／ 2b: 変更点と履歴・進行中の申請の管理・基幹のメニューの件数） |
| 3 | 通知（システム内のお知らせ・メール・催促） |
| 4 | 電子印・PDF・決裁台帳と Excel |
| 5 | 過去の決裁の取り込み、申請の種類ごとの作り込み（5.5。部門専用の様式は住宅・不動産の契約用だけで、確定済み） |
| 6 | 本番への先行公開と受け入れ確認 |

### 16.2 稼働までの流れ

1. 開発の最初に、バックアップを本番で先に動かす（段階 0）。
2. ご用意いただくもの（16.3）をそろえる。
3. 本番に関係者限定で載せ、スマホを含めて受け入れ確認をする。
4. 社員を一括登録し、ログイン案内を配る。
5. 切り替え日から全社で使い始める。切り替え日より前に紙で出した申請は、紙のまま最後まで回す。

### 16.3 ご用意いただくもの

| # | もの | 用途 |
|---|------|------|
| 1 | 部門の一覧（部門名・略称・アルファベット・会社・部門長） | 部門の設定・決裁No。アルファベットは過去の台帳のシート名から分かる（Ｈ・Ｃ・Ｓ・Ｊ・Ｍ・Ｔ と、それぞれの Ｂ 系統）。**Ｂ 系統が何を指すかは部門ごとに違う**ため（住宅は少額・追加工事、ミツワ不動産はマンション）、系統ごとに独立した部門として登録するかを一緒に確かめる（6.1） |

| 7 | 決裁専用のメールアドレス（さくらのコントロールパネルで作成） | 通知の送信元 |
| 8 | 各部門の今年度の開始番号 | 紙の番号との重複防止 |
| 9 | 部門専用の様式 | **受領済み**（2026/09/16）。部門専用の様式は `住宅・不動産決裁申請書.xls`（契約用）だけで、ほかは汎用の様式（2026/09/24 確認） |
