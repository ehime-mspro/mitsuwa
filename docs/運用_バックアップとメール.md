# 運用手順書: バックアップとメール送信

対象: 基幹システム（本番: さくらのレンタルサーバ ビジネスプロ）
関連: 要件定義書 `docs/決裁申請_要件定義書_v1.md`（14.6・15.3）

## 1. この仕組みでできること

| いつ | 何をする |
|------|---------|
| 5 分おき | 送信待ちのメールを送る（決裁の通知メールの土台） |
| 毎日 3:00 ごろ（日本時間） | データベース全体と添付ファイルを暗号化して、さくらのオブジェクトストレージへ送る。データベースは 30 日分を残し（最新の 1 件は必ず残す）、添付は消さずに残す |
| 失敗したとき | `BACKUP_NOTIFY_TO` のアドレスへメールで知らせる |

## 2. 最初に一度だけ行う設定

画面の名前は、さくらの画面変更で少し違うことがあります。

### 2.1 決裁専用のメールアドレスを作る
1. さくらのコントロールパネル → メール → メール一覧 → 新規追加
2. ユーザ名を決める（例: `kessai` → `kessai@mitsuwat.co.jp`）
3. パスワードを決める（2.5 で本番の .env にだけ書く。ほかには書かない。`'`（半角のシングルクォート）と空白は使わない）

### 2.2 迷惑メール対策（SPF・DKIM）を有効にする
1. コントロールパネル → メール → メールドメイン → `mitsuwat.co.jp` の設定 → DKIM 設定を有効にする
2. コントロールパネル → ドメイン/SSL → `mitsuwat.co.jp` の設定 → メールドメイン設定で SPF を有効にする
- さくらのネームサーバーを使っていない場合は、1・2 の画面に表示される TXT レコードを、使っている DNS にも登録する

### 2.3 バックアップ専用のバケットと鍵を作る（さくらのクラウド オブジェクトストレージ）
1. サイトは「石狩第1」。バケット名は小文字・数字・ハイフンだけ（例: `mitsuwa-manage-backup`）
2. 「パーミッション」を作り、**このバケットだけ**を「READ/WRITE」にする
3. アクセスキーを発行する（シークレットキーは発行したときにしか表示されない）
- 費用: バケット 1 つにつき月 495 円（100GiB まで含む。2026/09 時点）

### 2.4 暗号化キーを作る
本番に入って次を実行する（ターミナル）。

```
ssh mitsuwa-ud@www3586.sakura.ne.jp
cd ~/apps/manage && /usr/local/php/8.3/bin/php artisan ops:backup-key
```

表示されたキー（1 行目。英字の大文字・小文字、数字、`+` `/` `=` の 44 文字）を、①紙に控えて金庫などに保管し、②次の 2.5 で .env に書く。紙は手で書き写すより、画面の文字をコピーして印刷するほうが確実です（印刷に使ったファイルは保存せずに閉じ、別の文字をコピーしてクリップボードからも消す。手で書くときは l（エル）と 1、O（オー）と 0 などを区別する）。一緒に表示される「キーの識別番号」も同じ紙に控える。紙の写しが正しいかは 3 の 4 で確かめる。
**このキーを失くすと、バックアップを復元できません。**

### 2.5 本番の .env に書く（ご自身で）
`/home/mitsuwa-ud/apps/manage/.env` に次を書く（同じ名前の行がすでにあれば、その行を書き換える）。
- （ ）の部分は、**かっこごと**実際の値に置き換える
- **値の中に空白を入れない**（`"` で囲んである MAIL_FROM_NAME の空白はそのままでよい）。空白が 1 つでもあると .env 全体が読めなくなります（下の確認で気づけます）。宛先が複数のときは `a@mitsuwat.co.jp,b@mitsuwat.co.jp` のように、空白を入れずにカンマで区切る
- パスワードだけは前後を `'`（半角のシングルクォート）で囲む（`#` などの記号を含んでいても正しく読まれるように。囲まないと `#` から後ろが黙って切り捨てられ、メールが送れなくなる）

```
MAIL_MAILER=smtp
MAIL_HOST=（さくらの初期ドメイン。例: xxxx.sakura.ne.jp。独自ドメインの mitsuwat.co.jp ではない）
MAIL_PORT=587
MAIL_USERNAME=kessai@mitsuwat.co.jp
MAIL_PASSWORD='（2.1 で決めたパスワード）'
MAIL_FROM_ADDRESS=kessai@mitsuwat.co.jp
MAIL_FROM_NAME="ミツワ都市開発 基幹システム"
QUEUE_CONNECTION=database
BACKUP_ENCRYPTION_KEY=（2.4 のキー）
BACKUP_NOTIFY_TO=（失敗を知らせる宛先。複数なら空白を入れずにカンマで区切る）
BACKUP_S3_BUCKET=（2.3 のバケット名）
BACKUP_S3_ACCESS_KEY=（2.3 のアクセスキー）
BACKUP_S3_SECRET_KEY=（2.3 のシークレットキー）
BACKUP_MYSQLDUMP_BINARY=/usr/local/bin/mysqldump
```

`BACKUP_MYSQLDUMP_BINARY` は必ず書く（定期実行では PATH が短く、書かないと夜間だけ「mysqldump: not found」で失敗する）。

書いたら、まず次の 1 行で .env に書き間違いがないかを確かめる（この確認ではサイトは止まりません）。

```
cd ~/apps/manage && /usr/local/php/8.3/bin/php -r 'require "vendor/autoload.php"; try { $v = Dotenv\Dotenv::createArrayBacked(getcwd())->load(); preg_match_all("/^\s*([A-Za-z_][A-Za-z0-9_.]*)\s*=/m", file_get_contents(".env"), $m); $lost = array_diff(array_unique($m[1]), array_keys($v)); echo $lost ? "NG: " . implode(", ", $lost) . "\n" : "OK\n"; } catch (Throwable $e) { echo $e->getMessage(), "\n"; }'
```

- 「OK」と出れば次へ進む
- 「Failed to parse dotenv file.」と出たときは、その後ろの `[ ]` の中に出ている値（空白などの書き間違い）を .env で直し、「OK」と出るまでこの確認を繰り返す（`[ ]` の中にはパスワードなどがそのまま出ることがあるので、画面を人に送るときはその部分を隠す）
- 「NG: 」の後に名前が並んだときは、それらの行が読み捨てられています。並んだうちの最初の名前の行で `"` が閉じられていない（例: `MAIL_FROM_NAME="ミツワ都市開発 基幹システム` の最後の `"` が無い）ので、直して「OK」と出るまでこの確認を繰り返す（このまま進むと、読み捨てられた設定が無いものとして動き、エラーが出ないまま動かなくなります）
- どれでもない英語（「Unable to read …」など）が出たときは、`config:cache` に進まずに開発担当へ連絡する

「OK」と出たら、設定を反映する。

```
cd ~/apps/manage && /usr/local/php/8.3/bin/php artisan config:cache
```

「Configuration cached successfully.」と出れば完了です。
**「The environment file is invalid!」と出たときは、その時点でサイト全体が止まっています。** すぐに .env を開き、エラーの `[ ]` の中に出ている値を直してから、もう一度 `config:cache` を実行してください（「Configuration cached successfully.」と出れば元に戻ります）。

この後も .env を直したときは、毎回この順番（書き間違いの確認 → `config:cache`）で反映する。

### 2.6 定期実行を登録する（コントロールパネル → スクリプト設定 → CRON 設定）
- 実行間隔: 5 分おき（分に `*/5`、ほかは `*`）
- コマンド（1 行）:

```
cd /home/mitsuwa-ud/apps/manage && /usr/bin/nice -n 19 /usr/local/php/8.3/bin/php artisan schedule:run >> /home/mitsuwa-ud/apps/manage/storage/logs/scheduler.log 2>&1
```

- 登録したら 10 分以内に `storage/logs/scheduler.log` ができ、`queue:work` の行が `DONE` で出ることを確かめる（`tail ~/apps/manage/storage/logs/scheduler.log` で見られる。出ないときは CRON の書き間違い。その日のうちに気づける）。この `DONE` は CRON が動いている印で、処理の成否ではありません（今の Laravel では失敗しても `DONE` と出る）。メールが本当に送れるかは 3 の 1 で確かめる

## 3. 動作の確かめ方
1. テストメール: `cd ~/apps/manage && /usr/local/php/8.3/bin/php artisan ops:mail-test`（宛先を省略すると、失敗通知の宛先 `BACKUP_NOTIFY_TO` の全員へ送る）
   → 最初に「今の設定: …」の 1 行が出る。「送信待ち（キュー）= database」「送信方式 = smtp（2.5 の MAIL_HOST:587）」「差出人 = kessai@mitsuwat.co.jp」になっていること（sync や log と出たら .env を直して、2.5 の確認と `config:cache` をやり直す）
   → 全員に 5 分以内に届くこと、迷惑メールに入っていないこと。「形式の誤ったアドレス」「有効な宛先がありません」と出たら .env の `BACKUP_NOTIFY_TO` を直して、2.5 の確認と `config:cache` をやり直す（.env を直しただけでは反映されない。複数の宛先は空白を入れずにカンマで区切る）
   → 5 分たっても届かないときは `storage/logs/laravel.log` の「テストメールを送れませんでした」の行に理由が出ている。分からなければ開発担当へ連絡する
2. 手動バックアップ: `cd ~/apps/manage && /usr/local/php/8.3/bin/php artisan ops:backup`
   → 「バックアップ完了」と出ること（通知の宛先についての注意が出たら直す）。バケットに `db/` と `files/` ができていること
   - 初回は添付をすべて送るため、数分〜数十分かかることがあります（2 回目からは新しい添付だけを送ります）
   - SSH が切れて止まったときは、もう一度同じコマンドを実行する（送り終えた添付は送り直さず、続きから送ります。途中の作業ファイルは、次の実行の最初に自動で消えます。作業ファイルにはデータベースの中身が入っているので、切れたらすぐにやり直す）
3. 取り出しの確認: `cd ~/apps/manage && /usr/local/php/8.3/bin/php artisan ops:backup-restore ~/restore-check`
   → `gzip -t ~/restore-check/db/*.sql.gz` がエラーなく終わること、`gunzip -c ~/restore-check/db/*.sql.gz | tail -1` が `-- Dump completed` で始まること（途中で切れていない印）。確認したら `rm -rf ~/restore-check` で消す
   - 添付をすべて取り出すので、添付が多いと数分〜数十分かかります（100 件ごとに進み具合が出ます）
   - SSH が切れるなどして途中で止まったときも、`rm -rf ~/restore-check` で消してからやり直してください（途中のファイルにお客様の個人情報が含まれます）
4. 紙のキーの確かめ（2.4 の紙を金庫にしまう前に）: `cd ~/apps/manage && /usr/local/php/8.3/bin/php artisan ops:backup-restore ~/key-check --without-files --ask-key` を実行し、キーを聞かれたら、紙を見ながら入力する
   → 「入力したキーの識別番号: …」が紙の識別番号と同じで、「データベース: …」と出れば、紙のキーで復元できます。確認したら `rm -rf ~/key-check` で消す
   → 「暗号化キーが違います」または「入力したキーの形式が正しくありません」と出たら、紙の写し間違いか打ち間違い。.env の `BACKUP_ENCRYPTION_KEY` と見比べて紙を直し、`rm -rf ~/key-check` してからもう一度確かめる

## 4. ふだんの見方
- 失敗メールが来なければ、ほぼ正常に動いています。バックアップの処理が途中で強制終了された場合も知らせが届きます
- ただし、定期実行（CRON）やサーバーそのものが止まった場合（さくら側のメンテナンスなど）や、メールが送れなくなった場合（決裁用メールアドレスのパスワードを変えた・消した など）は、システムから知らせられません。**月に 1 回**、コントロールパネルでバケットの `db/` に 30 件前後のバックアップがあり、日付（`manage-YYYYMMDD-03…` の YYYYMMDD）が抜けていないかを確かめてください（保存は 30 日分なので、1 回見れば 1 か月分の抜けが分かります）
- 記録: `storage/logs/backup-command.log`（夜間バックアップの画面の出力。「バックアップ完了」や注意）、`storage/logs/laravel.log`（完了・失敗・警告。記録の設定が日ごとの場合は `laravel-YYYY-MM-DD.log`）、`storage/logs/scheduler.log`（定期実行）
- **`laravel.log`・`scheduler.log` の時刻は UTC（日本時間の 9 時間前）**です。3:00 のバックアップは、前日の 18:00 台として記録されます。メールの日時は日本時間です
- `backup-command.log` の行には日時が付きません。最後の行が直近の回です（「バックアップ完了」の行は、保管先の名前 `manage-YYYYMMDD-HHMMSS`（日本時間）で日付が分かります）
- `scheduler.log` は 5 分ごとに少しずつ増えます（1 年で 25MB ほど）。大きくなったら `rm ~/apps/manage/storage/logs/scheduler.log` で消して構いません（次の定期実行で新しく作られます）

## 5. 失敗したとき

メールの「理由」の中に、左の列の言葉が**含まれている**行を探してください（英語の長い文の中に含まれていることもあります）。どの行にも当てはまらないときは、メールを開発担当へ転送してください。

| メールの「理由」 | 考えられる原因と対処 |
|----------------|--------------------|
| 暗号化キーが正しくありません | .env の `BACKUP_ENCRYPTION_KEY` を確認し、2.5 の確認と `config:cache` をやり直す |
| オブジェクトストレージの設定（…）がありません | .env の `BACKUP_S3_*` を確認し、2.5 の確認と `config:cache` をやり直す |
| NoSuchBucket | .env の `BACKUP_S3_BUCKET`（バケット名）が違う |
| InvalidAccessKeyId / SignatureDoesNotMatch | .env の `BACKUP_S3_ACCESS_KEY` / `BACKUP_S3_SECRET_KEY` が違う（貼り付け時の空白・改行にも注意） |
| AccessDenied | 鍵にそのバケットの READ/WRITE の権限が無い（パーミッションの設定を確認する） |
| cURL error 6 | 保管先のサーバー名が見つからない（一時的な障害のことが多い。.env に `BACKUP_S3_ENDPOINT` を書いている場合はその書き間違い。ふだんは書かない項目。翌日も続くなら開発担当へ連絡） |
| cURL error 28 | 通信が時間内に終わらなかった（一時的な障害のことが多い。翌日も続くなら開発担当へ連絡） |
| cURL error 60 | 通信の証明書を確かめられない（.env に `BACKUP_S3_ENDPOINT` を書いている場合はその書き間違い。書いていなければ開発担当へ連絡） |
| cURL error 7 など、上の表に無い番号 | 保管先に接続できなかった（一時的な障害のことが多い。翌日も続くなら開発担当へ連絡） |
| InternalError／ServiceUnavailable／SlowDown | 保管先の一時的な不調。翌日も続くなら開発担当へ連絡 |
| 保管先の一覧を最後まで取得できませんでした | 保管先の不調。翌日も続くなら開発担当へ連絡 |
| mysqldump が失敗しました／mysqldump が時間内に終わりませんでした | 理由に「not found」とあれば .env の `BACKUP_MYSQLDUMP_BINARY`（2.5）の書き間違い（直して 2.5 の確認と `config:cache` をやり直す）。「errno 28」「No space」とあればサーバーのディスク容量を確認する。それ以外（Access denied・接続できない など）は .env のデータベースの設定には触らず、翌日の結果を見る（さくら側のデータベースのメンテナンスのことがある）。翌日も続くなら開発担当へ連絡 |
| 空き容量を確認してください | サーバーのディスク容量を確認する |
| データベースは保存済みです（…）。添付 … 失敗しました／中断しました | データベースのバックアップはできている。添付の送信だけが失敗した。（ ）内や「:」の後の理由をこの表で確認する。翌日の夜に自動でやり直す |
| バックアップは保存済みです（…）。古いバックアップの削除に失敗しました | 今夜のバックアップはできている。30 日を過ぎた古いものを消せなかっただけ。「:」の後の理由をこの表で確認する。翌日の夜に自動でやり直す |
| 別のバックアップが実行中です | 夜間の自動バックアップと手動実行が重なった。終わるのを待ってからやり直す（翌日も続くなら開発担当へ連絡） |
| 作業フォルダを、バックアップの対象フォルダの中や別の場所へのリンクにはできません | `.env` の `BACKUP_WORK_DIR` を確認する（ふだんは書かなくてよい） |
| 作業フォルダをロックできません／バックアップ対象のフォルダが 1 つもありません | 開発担当へ連絡する |
| 保管先のキーが長すぎます | 名前（パス）が非常に長い添付ファイルがある。開発担当へ連絡する（直るまで新しい添付がバックアップされない） |
| 夜間バックアップの処理が途中で止まりました（終了コード …） | 処理が最後まで行かずに止まった（サーバーのメモリ不足・強制終了・予期しないエラーなど）。翌日の夜も自動でやり直す。翌日も届いたら、このメールを開発担当へ転送する（開発担当向けの目安: 129〜254＝強制終了（137・143 など）、255＝PHP の致命的なエラー（メモリ不足など）、1＝予期しないエラー。詳しくは laravel.log の同じ時刻（UTC）の行と、backup-command.log の末尾（行に日時は付かない。最後が直近の回）を見る） |

直したら、3 の 2（手動バックアップ）で確かめる。

## 6. 復元の手順（サーバーが壊れたときなど）
1. 新しい環境にアプリを置き、.env に `BACKUP_*` を書いて、2.5 の確認と `config:cache` をやり直す。暗号化キーは金庫の紙から。バケット名はさくらのコントロールパネルで確かめる。アクセスキーとシークレットキーは元のサーバーの .env にしか無いため、2.3 の 3 と同じ手順で新しく発行する（使わなくなった古い鍵は、復元が終わったら削除する）
2. `cd ~/apps/manage && /usr/local/php/8.3/bin/php artisan ops:backup-restore /path/to/restore`（さくら以外の環境では PHP 8.3 の php で実行する）。何も指定しないと、いちばん新しいバックアップを取り出します。データを誤って消した・壊したときは、いちばん新しいものにはすでに消えた後の状態が入っていることがあるので、その前の日のものを `--db=db/manage-YYYYMMDD-HHMMSS.sql.gz.enc` で指定する（無い名前を指定すると、使えるバックアップの一覧が新しい順に 10 件まで出ます。それより古いものは、コントロールパネルでバケットの `db/` を見て名前を確かめる）
3. データベース: `gunzip -c /path/to/restore/db/*.sql.gz | mysql -h ホスト名 -u ユーザー名 -p データベース名`（ホスト名・ユーザー名・データベース名は、.env の `DB_HOST`・`DB_USERNAME`・`DB_DATABASE` の値に置き換える。パスワードを聞かれたら `DB_PASSWORD` の値を入力する。`-h` を省くと「Can't connect to local MySQL server」で止まります）
4. ファイル: `/path/to/restore/files/public/` を `storage/app/public/` へ、`files/private/` を `storage/app/private/` へコピーする
   - 取り出したファイルは、本人だけが読める権限（ファイル 0600・フォルダ 0700）になっています。さくらのように PHP がサーバーのユーザー本人の権限で動く環境ではそのままで構いません。別のユーザーで PHP が動く環境では、コピーした後に権限を合わせてください
5. 復元の作業中に 3:00 をまたぐと、メンテナンスモードの間でも夜間バックアップが動き、途中の状態のバックアップが 1 つ増えます（それまでの 30 日分のバックアップは残ります）。この後で取り出しをやり直すときは、最初に使ったバックアップの名前を `--db=` で指定してください（指定しないと、この途中の状態のバックアップが「いちばん新しいもの」として選ばれます）

## 7. 注意
- 暗号化キーを変えた場合、それまでのバックアップは古いキーでしか復元できません。古いキーも保管してください
- キーを変えた後の最初のバックアップでは、添付ファイルを全部、新しいキー用の置き場所（`files/<キーの識別番号>/`）へ送り直します（容量が一時的に倍になります）。キーを変えたら（.env を書き換えて、2.5 の確認と `config:cache` をやり直したら）、その場で手動バックアップ（3 の 2）を実行して「バックアップ完了」を確かめ、バケットに新しい `files/<新しいキーの識別番号>/` ができていることも確かめてください（`config:cache` を忘れると、古いキーのままバックアップされます）。そのあと、新しいキーの紙も 3 の 4 で確かめてください（3 の 4 はいちばん新しいデータベースのバックアップで確かめるため、この手動バックアップの後に行う）
- 古いキーの置き場所は、データベースの保存期間（30 日）が過ぎてから消してください（それまでのデータベースのバックアップと組になっているため）
- 取り出し（`ops:backup-restore`）は、`.env` に設定されているキーの置き場所から添付を取り出します。以前のキーで作った添付を取り出すときは、`.env` は変えずに、空の取り出し先（例: `~/restore-old`）を指定して `cd ~/apps/manage && /usr/local/php/8.3/bin/php artisan ops:backup-restore ~/restore-old --without-db --ask-key` を実行し、以前のキーを入力してください（`.env` を書き換えると、戻し忘れたときに夜間のバックアップが以前のキーで動いてしまいます）。済んだら `rm -rf ~/restore-old` で消してください
- `ops:backup-key` はキーと一緒に「キーの識別番号」を表示します。バケットの `files/<識別番号>/` がどのキーの置き場所かを見分けるのに使うので、キーと一緒に紙に控えてください
- バックアップにはお客様の個人情報も含まれます。取り出したファイルは確認が済んだらすぐ消してください
