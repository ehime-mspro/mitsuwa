# 419 の画面から「前の画面に戻る」で戻った画面を送り直せるようにする（短い設計メモ）

日付: 2026-11-18 ／ 利用者の承認: 2026-11-18（「この設計で進めてください」）
元: docs/BACKLOG.md の「ログインが切れたとき（419）に日本語の理由を出す（Bug #137）」の節の範囲外
「419 の画面の「前の画面に戻る」で戻った画面は古い鍵のままで、そのまま送り直すとまた 419 になる」

## なぜ

画面を開いたまま時間がたってから送ると、419 の画面（`resources/views/errors/419.blade.php`）が出る。
緑のボタン「前の画面に戻る」（`history.back()`）を押すと、ブラウザは読み直さずに手元の画面を出す（bfcache か HTTP のキャッシュ）。
その画面の鍵は古いままなので、そのまま送るとまた 419 になる。開き直すまで抜けられない。
2026-11-18 の深夜に、ログイン画面で利用者が実際にこれを踏んだ（ログインの送信だけは Bug #138 で直した）。ほかの画面には残っている。

## 今（2026-11-18 にコードを読んだ）

- 419 の応答を出した時点で、サーバーには新しい鍵がある。セッションが切れていれば、新しいセッションとその鍵ができている
  （419 の画面の `<meta name="csrf-token">` はその鍵）。古いのは、戻った画面に書かれた鍵だけ
- 419 になる場合は 3 つ
  1. セッションが切れた（2 時間）・ほかの画面でログアウトした → ログインも切れている
  2. ほかの画面でログアウトしてログインし直した → ログインしたまま、鍵だけ変わった
  3. 1 で、ログインのときに「ログイン状態を保持」にしていた → 次の要求で自動でログインし直す
     （`SessionGuard::updateSession()` が `regenerate(true)` を呼ぶので鍵も変わる）
- 鍵の確かめ（`VerifyCsrfToken`）は web グループにあり、ルートの `auth` より前に走る。鍵が合えば、ログインが切れていても `auth` が
  ログイン画面へ送る。ログインのあとの行き先はその人のホーム（`AuthController` は `intended` を使わない）
- 画面の鍵の持ち方: フォームの hidden の `_token`（`@csrf`）と、レイアウトの `<meta name="csrf-token">`。
  Ajax の多くは送る時にメタを読む（31 か所）。画面を開いた時に読んで変数に持つものと、Blade で直に書くもの（7 か所）もある
- 419 の画面とログイン画面は `components/guest-layout`、ほかの画面（決裁を含む 186 本）は `layouts/app`

## やること（案 A・利用者の選択 2026-11-18）

419 の画面が新しい鍵をそのタブの中だけに一時的に覚え、「戻る」で表示した画面の鍵をその鍵に差し替える。サーバーの鍵の確かめは変えない。

- **419 の画面**
  - 自分のメタの鍵を `sessionStorage` に書く（キーは 1 つ。私の判断で `freshCsrfTokenAfter419`）。try で包む（書けなくても画面は今どおり）
  - ログインしているか（`auth()->check()`）で 2 つめの段落とボタンを出し分ける。⚠ 判定はメタの鍵を描くより前に行う
    （「ログイン状態を保持」の人はここで自動でログインし直し、鍵が変わるため。Blade のコンポーネントは中身を先に描くので、
    419 の画面の中で判定すれば、レイアウトのメタは判定のあとの鍵になる。テストで固定する）
    - ログインしている: 「「前の画面に戻る」で戻ると、そのまま送り直せます。入力した内容が消えていたら、入れ直してください。」
      ボタンは「前の画面に戻る」「トップページへ」（今のまま）
    - ログインしていない: 「ログインが切れています。「前の画面に戻る」で戻って入力した内容を控えてから、ログインし直して、もう一度入力してください（戻った画面から送ると、ログイン画面に移ります）。」
      ボタンは「前の画面に戻る」「ログイン画面へ」（私の判断。行き先は今の「トップページへ」と同じくログイン画面）
  - 1 つめの段落（「画面を開いてから時間がたったか、ほかの画面でログアウトしたため、送れませんでした（何も保存していません）。」）は今のまま
- **2 つのレイアウトの head**（メタの直後・`@vite` より前。新しい部品 `resources/views/_partials/_fresh_csrf_token.blade.php` を両方が読む）
  - 読み込みのたびに `sessionStorage` の鍵を読んで消す。その読み込みが「戻る・進む」（`performance` の navigation の type が `back_forward`）のときだけ、
    メタを差し替え、`DOMContentLoaded` で `input[name="_token"]` をすべて差し替える
  - `pageshow` で `event.persisted`（bfcache から出した）なら、同じく読んで消して、メタと `_token` を差し替える
  - ふつうの読み込みでは消すだけ（419 の画面のあと、戻らずにほかの画面へ進んだ場合に、あとの「戻る」で古い鍵を当てないため）。
    419 の画面自身も head で前の鍵を消してから、本文で新しい鍵を書く
  - `sessionStorage` が使えない（例外）・鍵が無いときは何もしない

戻ったあとの流れ:

| 場合 | 戻った画面から送ると |
|---|---|
| 2（ログインしたまま鍵が変わった）・3（自動でログインし直した） | そのまま保存される（入力が残っていれば打ち直し不要） |
| 1（ログインが切れた） | 鍵は通り、ログイン画面に移る → ログインするとホームへ（入力は消える。419 の画面で控えるよう案内している） |

## 採らなかった案

- B（鍵を返す URL を作り、どの画面でも「戻る」で表示したときに取り直す）… 419 の前にも効くが、URL が増え、決裁のみの人・初回パスワード変更の人の
  門番と走査テストの分類に手が入る。「戻る」のたびに通信が 1 回増える
- C（Bug #138 と同じく、419 の画面を出さずに入力を控えて元の画面へ戻す）… ログインが切れていると間にログインが挟まり入力が消える・
  戻り先が POST の画面だと 405（Bug #64）・Alpine の画面は入力が戻らない・検査していない入力を戻すので 500 の恐れ（Bug #121）
- ログインのあとの行き先を元の画面（`intended`）にする … ログイン全体の振る舞いが変わる（今はいつもホーム）

## 範囲外

- 419 になる前の「戻る」（ほかのタブでログインし直したあとに「戻る」で開いた画面）
- 画面を開いた時に鍵を変数に持つ Ajax（bfcache から出したとき）と、Blade で鍵を直に書く 7 か所の Ajax … 古い鍵のままで、保存すると
  JSON の 419 の日本語の文（Bug #137）が出る
- 新しいタブで開いた 419 の画面の「前の画面に戻る」が何もしない件（フォームを新しいタブで送るときだけ。まれ）
- ログインのあとの行き先・入力の控えをサーバーが持つこと
- 決裁の画面も `layouts/app` なので鍵の差し替えは入る（動きは基幹と同じ。決裁の画面のコードは変えない）

## 検証

- 部品の script を node で動かす: 戻る・進むで差し替えて消す／ふつうの読み込みでは消すだけ／bfcache から出したとき差し替える／
  鍵が無い・`sessionStorage` が例外のとき何もしない
- 構造: 部品が 2 つのレイアウトの head でメタの直後・`@vite` より前にあること・419 の画面が鍵を書くこと
- 本物の 419（`EnforcesCsrfToken`）で: ログインしている／していない／「ログイン状態を保持」の 3 つの場合の文とボタン、
  419 の画面のメタの鍵で送り直すと鍵の確かめを通ること（2・3 は保存される・1 はログイン画面へ）
- 新しいテストは直す前に赤を確かめる・全件・変異（落ちたテストの組と理由まで）・コンパイル済みビューの lint
- 実ブラウザ（使い捨ての環境・Playwright）: 2（ほかのタブでログアウトしてログインし直す）と 1（cookie を消す）で、
  419 → 「前の画面に戻る」→ そのまま送る。Chromium が bfcache と HTTP のキャッシュのどちらで出すかも記録する
