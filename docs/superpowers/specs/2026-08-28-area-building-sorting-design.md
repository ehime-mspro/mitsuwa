## 1. 背景と依頼

利用者からの依頼は 2 つ:

> テナント管理の「周辺ビル調査」のテーブルを並び替えできるようにして下さい。
> 「部屋一覧」のテーブルと同様にして下さい。
> 並び替えしたい項目は「総階数、営業、空き、入居率、最終調査」です。

> 前回もテナント管理のテーブルを並び替えできるように改修しましたが
> 「並び替えができる列がわかりにくい」です。

**依頼①は前設計書の規約をそのまま 3 画面目へ広げる話**で、新しい流儀は要らない。
**依頼②は前回作った意匠そのものの欠陥**で、共通部品 `x-sortable-th` を直すため
**物件一覧・部屋一覧・周辺ビル調査の 3 画面すべてに同時に効く**。

対象列は確認のうえ **7 列**に決めた（§4.1）。依頼の 5 列に「空室率」「不明」を足している。
「営業・空きは押せるのに不明だけ押せない」「入居率は押せるのに真隣の空室率は押せない」が
画面で説明できないため。

## 2. 調査で分かった事実（2026-08-28 実測）

### 2.1 周辺ビル調査の一覧はすでに PHP で全件並べ替えている

`AreaBuildingListService::rows()` は **SQL で最新調査回を引き → PHP で率を計算 →
PHP で絞り込み → PHP で並べ替え → `paginateRows()` でページを切る**という構造で、
前設計書 §3.2 が物件一覧に選んだ方式と同じ。**並び替えの追加は `rows()` に分岐を 1 つ足すだけ**で、
SQL は 1 行も触らない。

- 既定順は `sortByDesc([$row['rate'] === null ? 0 : 1, $row['rate'] ?? 0.0])`
  ＝ **空室率の降順・未調査は末尾**。同点は `baseQuery()` の `ORDER BY name, id` が
  安定ソートで残る（サービスの docblock に明記済み）
- 全件をメモリに載せる件は計測済みで **数万棟まで問題ない**（同 docblock の表。実運用は 187 棟）
- `rows()` の呼び出し元は `AreaBuildingController::index()` **1 箇所だけ**（実測）
  ＝ シグネチャを変えても波及しない

### 2.2 「—」になる条件は列ごとに 2 種類ある

| 列 | 値の出どころ | `null` の画面表示 |
|---|---|---|
| 総階数 | `area_buildings.total_floors`（`INT NULL`） | `—`（`totalFloorsLabel()`） |
| 営業 / 空き / 不明 | `$row['operating'] / ['vacant'] / ['unknown']` | `—`（ビューの `?? '—'`） |
| 入居率 / 空室率 | `$row['rate']`（`VacancyRate::percent()`） | `—`（`label()` / `occupancyLabel()`） |
| 最終調査 | `$row['month']` | `—` |

⚠ **「調査回はあるが総区画が 0」という行がありうる。** `VacancyRate::percent()` は
総数 0 で `null` を返すので、そのとき **`rate` だけ `null`** になり、
`operating` / `vacant` / `unknown` は **`0`**（画面も「0」）、`month` は実在する日付のまま。
つまり同じ行が「入居率・空室率では末尾／営業・空き・不明・最終調査では普通に並ぶ」。
これは前設計書 §4.4 の原則（**揃える相手は NULL ではなく画面の表示**）どおりで正しい。
§8 でテストに固定する。

⚠ 総階数だけは調査回と無関係に `null` になりうる（Bug #55 の取込で総階数が空のまま入った経緯がある）。

### 2.3 現状の矢印はコントラストが 1.41:1 しかない（ブラウザで実測）

見出しの背景 `#F9FAFB`（gray-50）に対して:

| 色 | 用途 | コントラスト比 | 判定 |
|---|---|---|---|
| `#D1D5DB` gray-300 | **現状**の未使用 ⇅ | **1.41:1** | UI 部品の要件 3:1 を大きく下回る |
| `#9CA3AF` gray-400 | — | 2.43:1 | まだ不足 |
| `#6B7280` gray-500 | **案A** の未使用 ⇅ | **4.63:1** | 満たす |
| `#059669` emerald-600 | 並び替え中の矢印（現状のまま） | 3.61:1 | 満たす |

**「分かりにくい」の実体はこれ。** 手掛かりは他に「ホバーすると背景が薄く変わる」しか無く、
**マウスを乗せるまで押せると気づけない**。既定順のときはどの列にも印が出ないので、
**今どう並んでいるかも画面のどこにも出ていない**。

### 2.4 共通部品の現状

- `x-sortable-th` を使うビューは **2 本**（`tenant/properties/index` / `tenant/units/index`）
- `x-sort-hidden` も同じ 2 本
- `ListSort` を使うのは `UnitController` / `PropertyController` / `Unit`
- `resources/css/app.css` に **`.sortable-th-link:focus-visible` が既にある**（84-93 行）
  ＝ この部品用の CSS の置き場所は決まっている
- 両コントローラに `private const SORTABLE` があるが **形が違う**
  （`UnitController` は `[SQL 式, 「—」を末尾へ]`、`PropertyController` は属性名の文字列）

### 2.5 テストヘルパの制約

`tests/Concerns/ParsesSortLinks.php::sortLinkFor()` は

```
/<a\b[^>]*\bhref="([^"]*)"[^>]*>\s*ラベル\s*</u
```

＝ **`<a>` の直後にラベルのテキストが来ること**を要求する。
案A の点線下線はラベルだけに掛けたいので `<span>` で包む必要があり、この正規表現は 1 トークン広げる（§7）。

⚠ 「`<a>` 自身に `text-decoration` を掛けて `<span>` を足さない」案は**採らない**。
`<a>` は flex コンテナで、矢印は flex アイテム。**装飾が flex アイテムへ伝播して
矢印の下にも線が出るかどうかがブラウザ挙動に依存**し、しかも
`getComputedStyle` は伝播した装飾を子孫に対して必ず `none` と報告するため
**DOM 実測では決着しない**（2026-08-28 に確認）。決められないものに賭けない。

## 3. 方式の決定

| 論点 | 決定 | 理由 |
|---|---|---|
| 並び替えの実行場所 | `AreaBuildingListService::rows()` の中（PHP） | 既にそこで全件並べ替えている。SQL に写すと率の二重実装になる（Bug #41） |
| URL / 3 状態 / hidden / ページャ | **前設計書のまま流用** | 3 画面目で流儀を変えない |
| 意匠 | **案A ＋ 案C のバー**（見出しの塗り分けはしない） | モックで実物を比較して利用者が決定 |
| ラベルの持ち方 | **画面ごとに 1 つのマップへ統合** | 見出しとバーで別々に持つと食い違う（Bug #41 / #46） |

## 4. 設計① 周辺ビル調査の並び替え

### 4.1 対象列と URL

```
/tenant/area-buildings?sort=occupancy&dir=desc
/tenant/area-buildings?sort=month&dir=asc&occupancy=under75&year=2026
```

| `sort` の値 | 列 | 降順（1 回目）の言い方 | 昇順（2 回目） |
|---|---|---|---|
| `floors` | 総階数 | 多い順 | 少ない順 |
| `operating` | 営業 | 多い順 | 少ない順 |
| `vacant` | 空き | 多い順 | 少ない順 |
| `unknown` | 不明 | 多い順 | 少ない順 |
| `occupancy` | 入居率 | 高い順 | 低い順 |
| `vacancy` | 空室率 | 高い順 | 低い順 |
| `month` | 最終調査 | 新しい順 | 古い順 |

並び替え**しない**列: ビル名 / 位置 / 操作。

⚠ 「多い / 少ない」「高い / 低い」「新しい / 古い」を**列ごとに持つ**。
率に「大きい順」、日付に「多い順」は日本語として不自然で、バー（§6）にそのまま出る。

### 4.2 「—」は昇順でも降順でも末尾

前設計書 §4.3-2 の規約どおり。§2.2 のとおり **7 列すべて画面表示が `—`** なので、
判定は「その列の並べ替えキーが `null` か」で一致する。

実装は**フラグ付きの複合キーではなく分割**で書く:

```php
[$known, $blank] = $rows->partition(fn (array $r) => $this->sortValue($r, $sort->key) !== null);

$rows = ($sort->isAscending()
        ? $known->sortBy(fn (array $r) => $this->sortValue($r, $sort->key))
        : $known->sortByDesc(fn (array $r) => $this->sortValue($r, $sort->key)))
    ->concat($blank)
    ->values();
```

⚠ `[null 判定, 値]` の複合キーを `sortBy` / `sortByDesc` に渡す形は
**向きによって null フラグの 0/1 を反転させないと末尾に行かない**（降順では
「値あり」を 1、昇順では 0 にする必要がある）。**書いた本人しか気づけない取り違え**なので、
分割して連結する形にする。読んだだけで正しいと分かることを優先する。

### 4.3 入居率は空室率の符号を反転して並べる（値を 2 本持たない）

```php
'occupancy' => $row['rate'] === null ? null : -$row['rate'],
'vacancy'   => $row['rate'],
```

⚠ **`VacancyRate::occupancyPercent()` を並べ替えに使わない。**
入居率 = 100 − 空室率 なので順序は **厳密に一致**する（`VacancyRate` が
1/10% 単位の同じ整数から両方を作っており、和が 100.0% になることは構造で保証されている）。
別々に計算して比べる形にすると、**画面に並ぶ 2 つの数字と並び順が食い違う余地**を自分で作る（Bug #46）。

### 4.4 既定順と同点

- **既定順は変えない**（空室率の降順 → 未調査は末尾 → ビル名 → id）
- 並び替えは**既定順に並べ終えた列に対して**掛ける。PHP 8 のソートは安定なので、
  **同点の行は既定順のまま残る**（前設計書 §4.3-3。これが無いとページをまたいで行が重複/消失する）
- 日付は `Carbon` のまま比べず **`format('Y-m-d')` の文字列**にしてから並べる（辞書順で一致し、
  比較の意味がオブジェクトの実装に依存しない）

### 4.5 フィルタ・ページャ・地図タブ

- フィルタとの共存・`page` を落とす・「クリア」は全部初期化 … **前設計書 §4.3 のまま**
- ページャは既存の `paginateRows()` がそのまま効く（`array_map(fn ($v) => $v ?? '', ...)` 済み。Bug #31）
- フィルターフォームに `<x-sort-hidden :sort="$sort" />` を足す（並び替え中にフィルタを変えても消えないように）

**地図タブ（`?view=map`）の扱い:**

`rows()` は地図タブでも同じものを使うので、並び替えは
`mapPins()`（描画順・見た目に影響なし）と **`mapUnlocated()`（位置登録モードの作業リストの順番）**に効く。

- 並び順は**タブを切り替えても持ち回す**（`view` を足すだけの既存のタブリンクをそのまま使う）
- ただし地図タブには見出しが無いので、**並び替え中のときだけ**バー（§6）を出す。
  既定順のときの地図タブは今までと 1 ミリも変わらない

⚠ 持ち回さずに落とす案は採らない。作業リストの順番が変わっているのに
**画面のどこにもその事実が出ない**状態（＝ 本設計が避けたい無音の食い違い）になるため。

## 5. 設計② 見出しの視認性（案A）

`x-sortable-th` と `app.css` だけで完結する。**3 画面に同時に効く。**

| | 現状 | 変更後 |
|---|---|---|
| 未使用の ⇅ | `#D1D5DB`（1.41:1） | **`#6B7280`**（4.63:1） |
| 並び替え中の矢印 | `#059669` | 変えない |
| ラベル | 装飾なし | **点線の下線**（`underline dotted #9CA3AF` / `text-underline-offset: 4px`） |
| ホバー | 背景 `gray-100` | 背景はそのまま ＋ **下線が `#4B5563` に濃くなる** |
| 並び替え中 | 文字 `#047857` | そのまま ＋ **下線が `#059669`** |

- ラベルは `<span class="sortable-th-label">` で包む（§2.5）
- 色の状態変化は **`app.css` の `.sortable-th-link` 配下**に書く。
  部品の docblock が警告しているとおり、`color` は inline style なので
  `hover:text-*` の Tailwind クラスは効かない（inline が勝つ）。**下線の色は CSS に置けば効く**
- **`<th>` の当たり判定は今までどおりセル全体**（padding は `<a>` 側のまま。Bug #43）

⚠ 点線下線そのものは `#9CA3AF` で **2.43:1** ＝ 3:1 に届かない。
これは承知のうえで、**手掛かりの本体は 4.63:1 の矢印**、下線は「文字がリンクである」ことを
補強する装飾として扱う。濃くすると 10 列の見出しが騒がしくなるため、モックで選ばれた濃さを採る。

## 6. 設計③ 現在の並び順バー（案C のバー）

表の**すぐ上**（フィルターバー・タブより下）に 1 行足す。新しい部品 `x-sort-bar`。

```
並び替え: 既定（空室率が高い順）        ⓘ 見出しをクリックすると並び替えできます
並び替え: 入居率 高い順 ▼   [解除]      ⓘ 見出しをクリックすると並び替えできます
```

| 状態 | 出るもの |
|---|---|
| 並び替えなし | グレーのピル「並び替え: 既定（〜順）」＋ ヒント文 |

| 物件一覧 | 既定（稼働中が先・コード順） |
| 部屋一覧 | 既定（物件・階・部屋番号順） |

## 7. 実装の構造

### 7.1 ラベルは画面ごとに 1 つのマップへ集約する

見出し（§5）とバー（§6）が同じ列名を出すので、**2 箇所に文字列を置かない**。
既に各コントローラにある `SORTABLE` を、ラベルと向きの言い方まで持つ 1 つのマップに拡張する。

```php
// AreaBuildingListService
public const SORT_COLUMNS = [
    'floors'    => ['label' => '総階数',   'desc' => '多い順',   'asc' => '少ない順'],
    'operating' => ['label' => '営業',     'desc' => '多い順',   'asc' => '少ない順'],
    'vacant'    => ['label' => '空き',     'desc' => '多い順',   'asc' => '少ない順'],
    'unknown'   => ['label' => '不明',     'desc' => '多い順',   'asc' => '少ない順'],
    'occupancy' => ['label' => '入居率',   'desc' => '高い順',   'asc' => '低い順'],
    'vacancy'   => ['label' => '空室率',   'desc' => '高い順',   'asc' => '低い順'],
    'month'     => ['label' => '最終調査', 'desc' => '新しい順', 'asc' => '古い順'],
];
```

既存 2 画面も同じ形へ揃える（`UnitController` は `expr` / `nullsLast` を、
`PropertyController` は `attribute` を同じ配列の中へ入れる）。
許可リストは従来どおり `array_keys(...)` を `ListSort::fromRequest()` へ渡す。

`x-sortable-th` は **`label` プロップをやめ、`columns` から引く**:

```blade
<x-sortable-th column="occupancy" :sort="$sort" :columns="$sortColumns" align="center"
               link-class="px-4 py-3 lg:px-5 lg:py-3.5" />
```

⚠ 代償: ビューを見ただけでは列の日本語が読めなくなる。また
**`column` を打ち間違えるとその画面が 500 になる**（従来は黙って既定順に落ちていた）。
これは承知のうえで採る —— 3 一覧とも画面を描画する Feature テストがあるので
デプロイ前に必ず落ちるし、この規約の最大の敵は**無音の食い違い**のほうである。

## 8. テスト計画

前設計書と同じ流儀（**挙動と構造を対で見る** / **走査が空振りして緑にならないよう下限を固定する** /
**変異を当てて赤になることを実測する**）。

### 8.1 周辺ビル調査の並び替え（新規 `AreaBuildingListSortTest`）

1. **7 列すべてが自分の列で並ぶ**。⚠ **期待順を既定順と食い違わせる**データで作る
   （揃えると式を取り違えても緑になる。前設計書で実測済みの罠）
2. **3 状態の往復**（既定 → 降順 → 昇順 → 既定）を、画面が描画したリンクを実際に辿って確認。
   ⚠ URL を自分で組み立てない（リンクが壊れていても緑になる。Bug #31 の注記）
3. **「—」が昇順・降順の両方で末尾**（総階数 null の棟／調査回が無い棟）
4. **「調査回はあるが総区画 0」の行**が、入居率・空室率では末尾／営業・空き・最終調査では
   普通に並ぶ（§2.2）。**画面表示と並び順が一致していることの固定**
5. **入居率の降順と空室率の昇順が完全に同じ並びになる**（§4.3 が守られていることの証明）
6. **同点は既定順**（空室率降順 → ビル名）
7. **フィルタ・ページ送りとの共存**（絞り込んだ中で並び、2 ページ目でも維持される）
8. **既定順が変わっていない**（既存 `test_default_order_is_vacancy_rate_desc_with_unsurveyed_last` を壊さない）
9. **不正な `?sort=` で 500 にならない**（`?sort[]=a` の配列を含む）
10. 地図タブで並び順が持ち回されること／**登録モードの作業リストの順番も一致する**こと

### 8.2 意匠（案A）

- `sortable-th` の矢印が **`#6B7280`**、並び替え中は `#059669` であること
- ラベルが `sortable-th-label` で包まれていること（**バーと見出しの両方に効く構造**）

## 10. やらないこと

- **ビル名での並び替え**（利用者の選択どおり対象外）。日本語の並び順は DB の照合順序に依存し、
  PHP 側で並べると SQL の既定順と食い違うため、やるなら SQL 側の別扱いが要る
- **既定の並び順の変更**（空室率が高い順のまま）
- **見出しの塗り分け**（案C の片方。モックで比較して不採用）
- 位置・操作列の並び替え
- 所在地の再表示（2026-08-20 に画面から外した判断は維持）
