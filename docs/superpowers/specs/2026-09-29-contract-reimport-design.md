## 1. 背景と依頼

Bug #69（2026-09-28）で、取込の確定を「確認画面 1 つにつき 1 回だけ」にした。そのとき範囲外に残したのが
**同じ CSV を上げ直したときの二重**（案 C）。上げ直すと新しいプレビュー＝新しい鍵になるので、鍵では止まらない。
2026-09-28 の実測（設計書 `2026-09-28-import-double-submit-design.md` §2.1）では、契約系の 4 経路はどれも上げ直すと取り込めてしまい、
テナントの過去契約は注意すら出ない。

利用者の依頼（2026-09-29）: 契約系の 4 経路で、上げ直しても二重にしない。

対話で決まったこと（2026-09-29。質問 3 つ・設計の 3 節・コードを読んで出た細部 A〜E。どれも承認済み）:

| 論点 | 決定 |
|---|---|
| 登録済みと同じ契約の行 | **自動でスキップ**（質問 1 の案 1）。確認画面に「既に登録済みのためスキップ」と出し、その行は取り込まない。同じ画面の物件・顧客・入居者タブと同じ振る舞い |
| 「同じ契約」の見分け方 | **どこ＋誰＋開始日**（質問 2 の案 A。§4.2）。賃料・状態・解約日・メモは見分けに使わない。削除した契約とは突き合わせない |
| 作り方 | **各経路の行の検査に照合を足す**（質問 3 の案 1）。コントローラごとに非公開メソッド。新しいクラス・DB の変更は無し。確定のときも同じ検査が走り直す |
| 画面の振る舞い | 設計の節 1（§4.7・§4.8）|
| 見分けの実装 | 設計の節 2（§4.2〜§4.6）|
| テストと確かめ方 | 設計の節 3（§5）|
| A 照合の位置 | 日付と、区画・顧客（部屋・駐車場・入居者）が決まったあと、金額の検査の前。駐車場契約は日付の検査を金額の検査より前へ移す（§4.4）|
| B テスト用スキーマ | `contracts.customer_id` を空欄可にする。やり方は計画の段で実測して決める（§4.9）|
| C 構造のテスト | 契約を作る取込のもう 1 つ（ZEAL 会員の取込）を、理由つきで「対象外」に分類する（§5.2）|
| D 顧客の無い契約の書き方 | スキップの理由の文で「顧客 空欄」と書く（§4.7）|
| E タブの説明 | 契約の 4 タブの説明に 1 行ずつ足す（§4.7）|

### 2.2 行の検査の順番（いま）

どの経路も、行の中で最初に見つかった誤りを 1 つだけエラーにして `continue` する。太字は途中で積む警告。

| 経路 | 順番 |

### 2.4 モデルとスキーマ

- `Contract` は論理削除（`app/Models/Contract.php:18`）。`MsContract`・`MsParkingContract` は物理削除（`SoftDeletes` を持たない）。
  `Customer` は論理削除、`MsTenant` は持たない
- 日付の列はどれも `date` キャスト（`contract_date`・`move_in_date`・`start_date`）

## 3. 方針

| 論点 | 採った案 | 理由 | 退けた案 |
|---|---|---|---|
| 登録済みと同じ契約の行 | 自動でスキップ | 同じ画面のほかのタブと同じ振る舞い。上げ直しても新しい行だけが入る | エラーの行にする（直すべき行に見える）／重複候補にしてチェックで取り込む（毎回の手間。チェックのまま送ると二重）|
| 見分け方 | どこ＋誰＋開始日（案 A）| 取り込んだあとに賃料を改定・解約しても、古い CSV の上げ直しで二重にしない | どこ＋開始日（案 B。移行で仮の日付をそろえると、別の人の契約までスキップする）／全項目一致（案 C。改定・解約のあとの上げ直しで二重になる）|
| 作り方 | 各経路の行の検査に照合を足す（案 1）| 形が物件タブと同じ。新しいクラスが要らない（`composer dump-autoload` も要らない）| 新しいクラスに切り出す（形がほかのタブと離れる）／DB の一意制約（空欄の列と論理削除で制約にできない・当たると取込全体が巻き戻る）|

### 4.2 見分けのキー

| 経路 | 見分けに使うもの | 使わないもの |
|---|---|---|
| テナント 契約 | 区画・顧客（テナント名が空欄なら「顧客の無い契約」）・契約日 | 賃料開始日・金額・屋号・備考・状態・解約日 |
| テナント 過去契約 | 区画・顧客・契約日（契約と同じ）| 賃料開始日・解約日・金額・屋号・備考・状態 |
| 部屋契約 | 部屋・入居者・契約日・入居日 | 退去日・金額・担当者・メモ・状態 |
| 駐車場契約 | 駐車場・入居者・契約日・開始日 | 終了日・月額料金・敷金・紐付部屋番号・担当者・メモ・状態 |

- 区画・部屋・駐車場・顧客・入居者は、行の検査で引いたレコードの id で比べる（名前の書き方の違いは、引いた時点で同じレコードになる）
- 賃貸マンションの日付は任意の列なので、**空欄どうしは同じ**とみなし、片方だけ空欄なら違う契約とみなす。
  契約日と入居日（開始日）が 2 つとも空欄の行は、部屋（駐車場）と入居者だけで見分けることになる
- テナントの 2 経路は同じキーで照合する。契約タブで入れて、あとで解約した契約を過去契約タブで上げ直してもスキップ。逆向きもスキップ
- 突き合わせる相手は、状態（契約中・解約済み）も、どの画面で登録したか（取込・画面）も問わない
- **削除した契約とは突き合わせない**（テナントの `Contract` は既定の絞り込みが論理削除を除く。賃貸マンションの 2 つは物理削除）。取り込み直せば入る
- **登録済みの契約は書き換えない**（スキップするだけ。CSV の賃料が違っても上書きしない。直すときは契約の画面で）

### 4.3 照合のメソッド

```php
// TenantImportController（契約・過去契約で共用）
private function findRegisteredContract(int $unitId, ?int $customerId, string $contractDate): ?Contract
{
    return Contract::where('unit_id', $unitId)
        ->where(fn ($q) => $customerId === null
            ? $q->whereNull('customer_id')
            : $q->where('customer_id', $customerId))
        ->whereDate('contract_date', $contractDate)
        ->orderBy('id')
        ->first();
}

// MansionImportController（日付は、null なら whereNull、値があれば whereDate）
private function findRegisteredRoomContract(int $roomId, int $tenantId, ?string $contractDate, ?string $moveInDate): ?MsContract
private function findRegisteredParkingContract(int $parkingId, int $tenantId, ?string $contractDate, ?string $startDate): ?MsParkingContract
```

（形の見本。名前と書き方の細部は計画で決める）

- 日付は `whereDate` で比べる（§2.4。前例は ZEAL 会員の取込）
- 一致が 2 件以上あるとき（以前の二重送信で入った重複など）は、id のいちばん小さいもの（最初に登録されたもの）を理由の文に出す
- ⚠ **過去契約で、顧客がまだ無い（取込で自動作成する予定の）行は照合しない。** `$customerId` に null を渡すと「顧客の無い契約」と取り違える。
  まだ無い顧客の契約は、登録済みにありえない
- 1 行につき問い合わせが 1 本増える（区画・部屋・駐車場で絞るので軽い）

### 4.4 行の検査の順番（新しい）

**決まり**: CSV 内の重複 → 登録済みの照合 の順に、見分けに使う値（区画・部屋・駐車場／顧客・入居者／日付）が決まったところで見る。

- 照合より前に置くのは、必須・物件・区画（部屋・駐車場）・顧客（入居者）・日付の検査。日付の検査はまとめて照合の前に置く
  （見分けに使わない賃料開始日・解約日・退去日・終了日も含む。日付の検査を 2 つに分けないため）
- 照合より後ろに置くのは、金額の検査と、取り込むと決めたあとの処理
- ⇒ **登録済みの行は、金額に誤りがあってもスキップ**（物件タブも、登録済みの確かめを値の検査より前に置いている）。
  **日付に誤りがあればエラー**（日付が読めないと見分けられない）。必須・物件・区画・顧客の誤りも今までどおりエラー

| 経路 | 新しい順番（**太字**が足すもの・動かすもの。（ ）は途中で出す警告）|
|---|---|
| 契約 | 必須 → 物件 → 階 → 区画 → 顧客 →（契約中の契約）→ 契約日 → 賃料開始日 → **CSV 内の重複** → **登録済みの照合** → 金額 → 取り込むと決める |
| 過去契約 | 必須 → 物件 → 階 → 区画 → 契約日 → 解約日 → 解約日 ≥ 契約日 →（解約日が未来）→ 賃料開始日 → 顧客 → **CSV 内の重複** → **登録済みの照合（顧客がいる行だけ）** →（期間の重なり）→ 金額 →（削除済みの区画の注意）→ 取り込むと決める |
| 部屋契約 | 必須 → 物件 → 部屋 → 入居者 →（担当者）→ 契約日 → 入居日 → 退去日 → 状態 → **CSV 内の重複** → **登録済みの照合** →（契約中の契約）→ 金額 → 取り込むと決める |
| 駐車場契約 | 必須 → 物件 → 駐車場 → 入居者 →（紐付部屋番号）→（担当者）→ **契約日 → 開始日 → 終了日**（金額の前へ移す）→ 状態 → **CSV 内の重複** → **登録済みの照合** →（契約中の契約）→ **月額料金 → 敷金**（照合の後ろへ移す）→ 取り込むと決める |

- 警告の検査の位置は変えない（駐車場は日付と金額の入れ替えだけ）。警告は行の中に貯めるので（§4.6）、位置に関係なく、スキップ・エラーの行には出ない
- 駐車場の入れ替えで変わるのは、日付と金額の両方に誤りがある行で先に出るエラーの文言だけ（どちらでも行はエラー）。
  必須の「月額料金が未入力です」は今までどおり最初に見る

### 4.5 CSV の中の重複

- 見分けのキー（§4.2）が同じ行が CSV に 2 つ以上あれば、2 つ目からをエラーにする（物件タブの CSV 内の重複と同じ扱い）。
  文言: 「CSV内で行{N}と同じ契約が重複しています」（N は最初の行。画面には「行{今の行}: CSV内で行{N}と同じ契約が重複しています」と出る）
- キーの作り方:
  - 区画・部屋・駐車場・入居者は id、日付は正規化したあとの `Y-m-d`（`2026/4/1` と `2026-04-01` は同じ）、空欄の日付は空欄として比べる
  - 顧客: 契約タブは顧客の id（テナント名が空欄なら「顧客なし」）。過去契約タブは、顧客がいれば id、まだ無ければ名前
  - 区画を id で比べるので、表示名の書き方の違い（階 `3`＋部屋番号 `A` と、階なし＋部屋番号 `3A`）も同じ区画とみなす（Bug #60 の教訓）
- 最初の行を覚えるのは、重複の確かめのすぐあと（照合の前。物件タブと同じ）。最初の行がそのあとスキップ・エラーになっても、2 つ目はエラー
  - 例: 登録済みの契約が CSV に 2 行あれば、1 行目はスキップ、2 行目は「CSV内で行N と同じ契約が重複しています」のエラー

### 4.6 警告を行ごとに貯める

- 4 経路とも、行の検査の中で出す警告（削除済みの区画の注意も含む）は、いったんその行の中に貯め、**取り込むと決めたとき**
  （正常な行の一覧に入れる直前）にだけ画面の警告の一覧へ移す
- スキップ・エラーで `continue` した行の警告は捨てる。⇒ スキップした行に今の警告（「既にアクティブな契約が存在します」など）を出さない
  （1 つの行に理由を 2 つ並べない）。エラーの行にも出さない
- これで直るもの:
  - BACKLOG の範囲外の「過去契約の『解約日が今日より未来です』の警告が、エラーになる行にも出る」
  - 賃貸マンションの「警告: N 件」「※ 警告のある行（N件）もそのまま登録されます」が、エラーになる行の警告まで数えていたこと（§2.2）
- 変えないもの: 警告の文言・取り込む行に出す今の警告（別の契約が同じ区画にあるときの警告など）

### 4.7 画面

**(1) スキップの一覧** — 今の部品のまま（灰色の一覧・「スキップ: N 件」・ボタンの下の「※ 既存データ（N件）はスキップされます」）。理由の文:

| 経路 | 理由の文（全文。{ } は値）|
|---|---|
| 契約・過去契約 | 区画「{物件名} {区画の表示名}」の契約（契約日 {Y-m-d}・顧客 {テナント名 または 空欄}）は既に登録済み（{契約番号}）のためスキップ |
| 部屋契約 | 部屋「{物件名} {部屋番号}」の入居者 {入居者名} の契約（契約日 {Y-m-d または 空欄}・入居日 {Y-m-d または 空欄}）は既に登録済み（既存契約 ID: {id}）のためスキップ |
| 駐車場契約 | 駐車場「{物件名} {駐車場番号}」の入居者 {入居者名} の契約（契約日 {Y-m-d または 空欄}・開始日 {Y-m-d または 空欄}）は既に登録済み（既存契約 ID: {id}）のためスキップ |

画面の例:
- 行3: 区画「本町ビル 3A」の契約（契約日 2026-04-01・顧客 山田商事）は既に登録済み（C-2026-012）のためスキップ
- 行4: 部屋「ミツワハイツ 101」の入居者 山田太郎 の契約（契約日 空欄・入居日 2026-04-01）は既に登録済み（既存契約 ID: 12）のためスキップ

- 物件名・部屋番号・駐車場番号・テナント名・入居者名は CSV に書かれた値。日付は正規化したあとの値
- 区画は表示名（`display_name`）。過去契約で削除済みの区画でも同じ（今の警告と同じ書き方）
- 契約番号・既存契約 ID は、一致した契約のうち id のいちばん小さいもの（§4.3）

**(2) すべての行がスキップで、エラーも無いとき** — 確定のフォームを出さない（今のまま）。赤字の文の代わりに灰色で:

> すべての行が登録済みです（スキップ N 件）。取り込む行はありません。

```blade
@if($validCount > 0)
    …確定のフォーム（今のまま）…
@elseif(count($rowErrors ?? []) === 0)
    <div style="font-size: 13px; color: #6b7280;">すべての行が登録済みです（スキップ {{ count($skippedRows ?? []) }} 件）。取り込む行はありません。</div>
@else
    <div style="font-size: 13px; color: #dc2626;">インポート可能なデータがありません。CSVを修正してください。</div>
@endif
```

（形の見本）

- 条件は「正常 0 件・エラー 0 件」。確認画面に来る CSV は必ず 1 行以上あるので（§2.3）、このときスキップは 1 件以上ある
- エラーが 1 件でもあれば、今までどおり赤字の「インポート可能なデータがありません。CSVを修正してください。」
- テナントと賃貸マンションの**共通部品に入れる**。物件・顧客・入居者のタブで全部スキップのときも同じ文になる（どのタブもスキップの理由は「既に登録済み」なので、意味は同じ）
- 色は一覧と同じ `#6b7280`（白地で約 4.8:1）。inline の style で書く（新しい Tailwind のクラスは使わない）

**(3) タブの説明**（取込の画面の、契約の 4 タブの箇条書き）に 1 行ずつ足す:

| タブ | 足す 1 行 |
|---|---|
| テナント 契約・過去契約 | 同じ区画・テナント名・契約日の契約が登録済みなら、その行はスキップされます（家賃などが違っても書き換えません）|
| 部屋契約 | 同じ部屋・入居者名・契約日・入居日の契約が登録済みなら、その行はスキップされます（家賃などが違っても書き換えません）|
| 駐車場契約 | 同じ駐車場・入居者名・契約日・開始日の契約が登録済みなら、その行はスキップされます（月額料金などが違っても書き換えません）|

### 4.8 確定

- 確定のときも、同じ検査（CSV 内の重複・登録済みの照合）を最初からやり直す（`loadCsv()` が CSV を読み直し、同じ行の検査を通る。今の仕組みのまま）
- プレビューのあとで同じ契約が登録されていれば（別の画面・別のタブの取込）、その行は確定でスキップされ、書かれない
- 完了の文は今のまま（「契約インポート完了: N件を登録しました」など。N は登録した件数。物件タブと同じく、スキップの件数は出さない）
- スキップした行は何も書き込まない。区画・部屋・駐車場を「入居中」「使用中」にする処理も走らない（取り込む行のループの中にあるため）
- 副産物（契約系の 4 経路）:
  - 2 つのタブで別々にプレビューした同じ CSV を**順に**確定すると、2 つ目は確定のやり直しでスキップされる（Bug #69 §6 の範囲外の 1 つが、順に届く場合は閉じる）
  - 鍵の記録が消えた（12 時間より古い）確認画面から送り直しても、登録済みの契約はスキップされる
- 変えないもの: 鍵（確定は確認画面 1 つにつき 1 回だけ）・戻り先・断りの文言・DB・ルート

### 4.9 テスト用スキーマ

- `contracts.customer_id` を本番と同じ**空欄可**にする。これが無いと「顧客の無い契約」をテストで作れず、テナント名が空欄の行の照合（§5.1 の 3・7）を確かめられない
- やり方は計画の段で実測して決める（候補は 2 つ）:
  1. 新しい migration で列を変える（`->nullable()->change()`）。SQLite はテーブルを作り直すので、状態・部署の CHECK・外部キー・索引が黙って消えることがある（Bug #60）
  2. 作成の migration（`0001_01_01_000007_create_contracts_table.php`）の行を直す。users の前例（§2.4）。テーブルの作り直しが起きない
- どちらでも、カナリアのテストで確かめる（§5.3）
- `rent_start_date` の食い違い（テストは NOT NULL・本番は空欄可）は、今回の照合に関係しないので触らない（テストは賃料開始日を埋める）
- migration はテスト用（SQLite の鏡）で、本番では流さない
