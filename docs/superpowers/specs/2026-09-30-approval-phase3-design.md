## 1. 目的と範囲

**目的**: 自分の番が来たことや決裁の結果を、システムを見に行かなくても知らせて、申請が止まったままにならないようにする。

**できたと言える状態**（利用者と確かめた）
- 要件 8.1 の場面（と D1 の場面）ごとに、届くべき人にだけ 1 回ずつ届く（届かない・二重に届く・関係ない人に届く、が起きない）
- 催促は送る日の朝に 1 人 1 通だけ届き、送らない日には 1 通も出ない
- 使い始める前の本番では、見た目も届くものも変わらない

## 2. 決定事項（2026-09-30 の対話で確定）

D1〜D5 は選択式で個別に決めた（すべて推奨の案）。D6〜D20 は設計の各節の中で「要件定義書に無く、開発側で決めた点」として示し、利用者が承認した。

| # | 論点 | 決定 |
|---|---|---|
| D1 | 担当が入れ替わったとき | 待っている申請が新しい人の番に移る **3 つの場面（部門の管理で部門長を変えた・基幹の管理者が社長の指定を変えた・審査担当者を足した）でも、新しい担当に「自分の番が来た」を出す**（要件 8.1 に行が無い。付け替えと同じ扱い）。待っている申請ごとに 1 通 |
| D2 | メールが送れないとき | **決裁の管理者のホームと管理の画面の上に表示する**（最後に送れなかった日時と宛先）。そのあと 1 通でも送れたら自動で消える。送れなかったメールの送り直しはしない（止まった申請は朝の催促で拾われる） |
| D3 | 作り方 | 2 回に分ける（3a・3b。§1.1） |
| D4 | 祝日の判定 | **部品（`azuyalabs/yasumi`・日本の祝日に対応）を入れる**。振替休日・春分の日・秋分の日も部品が計算する。法律で祝日が変わったら部品を新しくする。年末年始・会社の休業日は⑫で登録する |
| D5 | 催促に載せる申請 | **画面の「3 日待ち」以上**（待ち日数＝番が来た日から数えた暦の日数・日本時間。段階2 の D20 と同じ数え方）。要件 8.3 の「3 日（72 時間）以上」から変える（§3） |
| D6 | パスワード再発行のメール（段階1） | 送り直しを **3 回**にそろえる（今は 1 回で要件 15.3 と合わない）。D2 の表示の対象にも入れる |
| D7 | 場面 4・6 の「部門長」「社長」 | その申請で**実際に判断した人**（段階の `actor_user_id`）。承認のあとで部門長が交代しても、承認した人に届く |
| D8 | 管理者の代理の取り下げ | **申請者にも知らせる**（要件の表は「その時点の担当者」だけ） |
| D9 | 付け替え・交代で外れた前の担当 | 知らせない（要件の表のとおり） |
| D10 | 決裁のあとの取り消し | 場面 4 を受け取った部門長・審査担当者には知らせない（要件の表のとおり、取り消された操作をした人と申請者だけ） |
| D11 | 審査担当者の誰か 1 人が意見を入れた | ほかの審査担当者には知らせない（ホームの対応待ちから消える） |
| D12 | メールの差出人の名前 | **「ミツワ都市開発 決裁システム」**（今の全体の設定「ミツワ都市開発 基幹システム」は、決裁だけを使う人に分かりにくい）。アドレスは今の設定（kessai@）のまま |
| D13 | 既読になるとき | お知らせを押したとき・「すべて既読にする」に加えて、**その申請の詳細を開いたとき**（メールのリンクから開いたあとにベルの数が残らないように） |
| D14 | ベルを押したとき | プルダウン（最新の数件）は出さず、**お知らせ一覧（⑥）へ移る**（スマホでも同じ動き・小窓のキーボードの宿題を増やさない） |
| D15 | ⑥の絞り込み | 「未読だけ」の絞り込みは作らない（未読は太字で分かり、「すべて既読にする」がある） |
| D16 | お知らせの保存 | 消さずに残す（1 年で 1 万件ほどの見込み。画面の速さに響かない） |
| D17 | 9:00〜9:04 に定期実行が動かなかった日 | その日は送らない（次に送る日のメールに載る） |
| D18 | まとめメールの件数 | 1 通に **20 件まで**。多いときは「ほか N 件はホームで確かめてください」 |
| D19 | 毎年繰り返す送らない日 | **月と日だけで比べる**。12/29〜1/3 のように年をまたぐ期間も登録できる |
| D20 | 朝のメールのリンク | 画面の操作が無いので、**設定から作る**（本番の URL の形 `/system/manage/index.php/…`）。本番の設定（`APP_URL`）を読み取りで確かめてから決める（§5.8） |

## 4. 調べて分かった事実（2026-09-30 に実物で確認。13.x `4012cb0d`）

### 4.1 無いもの

- **`notifications` 表・`approval_holidays` 表・祝日の部品と判定のコードは無い**（migrations・`database/sql`・`composer.json` のどれにも無い）。`User` は `Notifiable` を使っている（`app/Models/User.php`）
- 決裁の部分にイベント・リスナー・ジョブ・通知のクラスは無い（`app/Events`・`Listeners`・`Jobs`・`Notifications` のフォルダ自体が無い）。`config/queue.php` の `after_commit` はどれも false

### 4.2 メールとキューと定期実行

- メールは `app/Mail` の 3 本（`BackupFailedMail`・`OpsTestMail`・`PasswordReissuedMail`）。本文はどれもテキスト（`resources/views/mail/*.blade.php`）。差出人は全体の設定（本番は `MAIL_FROM_NAME="ミツワ都市開発 基幹システム"`・`MAIL_FROM_ADDRESS` は kessai@。`docs/運用_バックアップとメール.md`）
- **前例**: `App\Support\Approval\PasswordReissuer` は **トランザクションの中で `Mail::to()->queue()`** する。キューが database なので、`jobs` の行も一緒に巻き戻る（「起きなかった再発行の通知だけが届く」を防ぐ。redis などに替えると崩れる。テストの `Mail::fake()` はキューへの挿入を飛ばすので、この巻き戻りはテストでは測れない。同クラスの docblock）
- 既存のキューに積むメールは `$tries = 1`（1 回の失敗で `failed()` へ。laravel.log に残す）。要件 15.3 は「3 回まで再送」
- 定期実行（`routes/console.php`）: バックアップ（`cron('0-4 3 * * *')`・`withoutOverlapping(180)`）→ キュー処理（`queue:work --stop-when-empty --max-time=240 --tries=3 --backoff=60`・`everyMinute()`・`withoutOverlapping(10)`）の順。**決まった時刻の仕事は 5 分の幅を持たせ、キュー処理より前に置く**（CLAUDE.md。`schedule:run` は上から順に前の予定を待つ）。`ScheduleTest` が順番とオプションと「CRON が何分に起動しても 1 日 1 回」を固定している
- `config/app.php` の `timezone` は UTC、`schedule_timezone` は Asia/Tokyo。日本時間の部品は `App\Support\JapanTime`（`format()`・`today()`）
- **キューや定期実行の中で `route()` を呼ぶと、`APP_URL` に頼るので本番で `/index.php` が抜ける**（要件 15.1・段階1 設計 §5.13）。`PasswordReissuedMail` は、再発行の画面のリクエストで作ったログイン画面の URL を受け取って使う

### 4.3 回覧と「いま誰の番か」

- 状態を変えるのは `App\Support\Approval\Workflow` の public メソッド（`submit`・`judgeHead`・`judgeReview`・`judgePresident`・`confirmCondition`・`withdraw`・`withdrawByAdmin`・`headChanged`・`reassignHead`・`undo`）。どれも `DB::transaction` の中
- **Workflow の外で担当が変わる場面が 2 つ**: 社長の指定（`Admin\UserController::setPresident`。トランザクションも申請の記録も無く、`president.changed` の設定の記録だけ）と、審査担当者の入れ替え（`Approval\OrganizationController::syncReviewers`。部門の更新のトランザクションの中）。部門長の交代は `OrganizationController` が部門の行を更新する**前に** `Workflow::headChanged()` を呼ぶ（中で今の部門長を引くと前の部門長が出る）
- 取り下げは `cancelRest()` で待ちの段階を打ち切ってから記録を書く → 「その時点の担当者」は打ち切る前に取る
- 段階（`approval_steps`）は 1 回の提出で 3 行（部門長・審査・社長）。審査は**審査部門ごとに 1 行**で、担当者は `approval_reviewers`。`assignee_user_id` は付け替えたときだけ入る。社長の段階は担当を持たず、毎回今の設定から引く。申請者の番（差戻し中・条件確認待ち）は申請の `status` で表し、番が来た日時は `status_changed_at`
- **「いま誰の番か」の規則が 3 か所にある**: `RequestPermissions::isAssigneeOf`（権限の正本）・`PendingWork::waitingSteps`（SQL 版・自分の申請を除く）・`CurrentHandler`（表示用・名前だけ・申請者本人を除かない）。**人（`User`）の集合を返す部品は無い**
- **「有効な審査担当者」の条件も 3 か所**（`SubmitChecker`・`TypeController`・`AdminRequestController`）。段階2 の最後の点検で「段階3 の着手時に `activeReviewers()` に寄せる」とされた
- 待ち日数は `PendingWork::waitingDays()`（日本の暦の日数。起点は段階の `arrived_at`、申請者の番は `status_changed_at`）。取り消し・付け替え・交代のあとも元の届いた日から数える
- `ApprovalSetting::current()` は行が無ければ作り、コンテナに覚える。`queue:work`（最長 240 秒）はジョブごとに捨てないので、**ジョブの中で社長や使い始めたかを判定すると古い値を読むおそれがある** → 宛先は操作の時点で決める。`ApprovalSetting::launchedForMenu()` は行を作らずに読む

### 4.4 画面

- **ヘッダー（`layouts/partials/header.blade.php`）は基幹の利用者と決裁のみ利用者で共通**。ベルは右側の塊（利用者のメニューの左）に置ける
- 件数を 1 リクエストに 1 回だけ数える形は `App\Support\Approval\ApprovalMenu`（`request()->attributes` に覚える・使い始める前は null）
- ホームは `approvals/home-launched.blade.php`（対応待ち → 自分の申請の進み具合 → リンクの行）

**呼ぶ所**（どれも操作のトランザクションの中）

| 呼ぶ所 | 場面 |

### 5.4 知らせる場面と宛先

**場面**（どれもお知らせとメール。場面 6 だけお知らせのみ）

| 場面 | きっかけ | 届く人 |
|---|---|---|
| 1 自分の番が来た | 提出・出し直し・部門長の承認・審査の意見 | 次の段階の今の担当（部門長／審査担当者全員／社長） |
| 2 担当が入れ替わった | 付け替え・部門長の交代・社長の交代・審査担当者の追加（D1） | 新しい担当（待っている申請ごとに） |
| 3 差戻しされた | 部門長の差戻し・社長の差戻し | 申請者 |
| 4 決裁が出た（可・否） | 社長の可・否 | 申請者・部門長として判断した人・意見を入れた審査担当者（D7） |
| 5 条可が出た | 社長の条可 | 申請者には「条件の確認のお願い」、部門長・審査担当者には場面 4 と同じ知らせ |
| 6 条件が確認された | 申請者の条件の確認 | 決裁した社長・部門長として判断した人（D7） |
| 7 取り下げられた | 申請者の取り下げ・管理者の代理の取り下げ | その時点の担当（待っていた部門長／審査担当者全員／社長）。代理なら申請者も（D8） |
| 8 操作が取り消された | 管理者の押し間違いの取り消し | 取り消された操作をした人・申請者。戻った段階の今の担当には「もう一度お願いします」 |

**共通の決まり**（宛先を人でまとめてから作る）

1. **操作した本人には届かない**（管理者の操作なら管理者本人。例: 自分を新しい部門長にした管理者）
2. **1 回の操作で同じ人に届くのは 1 通だけ**。2 つの立場に当たるときは 1 通にまとめる。対応が要る知らせを先にし、取り消しと番が重なったら「取り消されました。もう一度お願いします」とする
3. 無効の人と削除した人には何も届かない
4. メールは、メールアドレスがあり `ApprovalMailDomain::allows()` が通す人にだけ。ほかの人にはお知らせだけ
5. **担当が申請者本人のときは、場面 1・2 を出さない**（自分の申請には判断できない。段階2 の D16）。例: 社長に指定した人が、指定の前に出していた申請
6. 件名は**最後に提出した中身**（提出ごとの控え）のものを使う（差戻し中の直しかけは出さない。段階2 の D26）
7. 使い始める前は何も作らない（§5.2）

**場面ごとの細部**

- 場面 1（提出）: 申請者が申請部門の部門長なら部門長の段階は省かれ、審査担当者に届く。部門長が社長を兼ねていても部門長の段階は省かない（段階2 のまま）
- 場面 2（部門長の交代）: その部門の待ちの部門長の段階（付け替えたものも移る。段階2 の D23）ごとに新しい部門長へ。（社長の交代）社長決裁待ちのすべての申請ごとに新しい社長へ。（審査担当者の追加）足した人（前後の差）だけに、その部門の待ちの審査の段階ごとに。これから届く段階（まだ待ちでないもの）は、届いたときに場面 1 で知らせる
- 場面 4・5・6 の「判断した人」は、その回の段階の `actor_user_id`（部門長の段階を省いた回は部門長の宛先なし。申請者に届く）
- 場面 7: 差戻し中（申請者の番）に申請者が取り下げたときは、届く人がいない（本人の操作）
- 場面 8: 取り消した操作ごとの「取り消された人」は取り消した記録の操作者（`UndoTarget` が返す記録の `actor_user_id`）。戻った段階の今の担当（部門長の段階なら付け替えた人か今の部門長／審査なら審査担当者全員／社長なら今の社長）に「もう一度お願いします」。条件の確認の取り消しでは、取り消された人＝申請者なので 1 通（「条件の確認が取り消されました。もう一度確認してください」）。決裁のあとの取り消しで、場面 4 を受け取った人には知らせない（D10）
- 知らせないもの: 外れた前の担当（D9）・審査の意見が入ったときのほかの審査担当者（D11）・申請者への途中経過

### 5.5 お知らせとメールの作り方

- **操作と同じトランザクションの中で**、お知らせの行を作り（その場で出る）、メールを送信待ち（`jobs`）に積む。キューが database なので、操作が失敗して巻き戻ればどちらも残らない（`PasswordReissuer` と同じ。§4.2 の注意も同じ: キューを redis などに替えると崩れる・`Mail::fake()` では巻き戻りを測れない）
- **宛先と文の材料は操作の時点で決めて持たせる**（キューの中で設定や `route()` を読まない。§4.2・§4.3）。リンクは操作の画面のリクエストで `route()` から作る（`/index.php` 入り）
- メールはテキストだけ。Laravel 標準の通知メールの雛形（英語の「Hello!」などが出る。Top trap #10）は使わない
- 差出人は「ミツワ都市開発 決裁システム」＋今の `MAIL_FROM_ADDRESS`（D12）
- 書くのは件名・申請者（申請部門）・決裁No（付いていれば）・必要な対応・リンクだけ。金額・本文・添付・コメント（差戻しの理由・条件）は書かない（要件 8.2）
- **送り直しは 3 回・60 秒あけ**（`$tries = 3`・`$backoff = 60`。キュー処理の起動のオプションと同じ）。3 回だめなら laravel.log に残し、「送れなかった日時と宛先」を記録する。送れたら「送れた日時」を記録する（D2 の表示に使う）。パスワード再発行のメールも同じにする（D6）

**件名と「必要な対応」**（メールの件名の頭は【決裁】。お知らせの文も同じ表から作る）

| 場面・宛先 | メールの件名 | 必要な対応 |

### 5.8 催促（3b）

**送る日と時刻**
- 定期実行に催促を足す: `cron('0-4 9 * * *')`（日本時間。5 分の幅）・キュー処理より前（積んだメールが同じ回のキュー処理で送られる）
- コマンドの中で順に確かめ、当たれば何もしないで終わる: 使い始める前 → 送らない日（土日・祝日・⑫で登録した日。§5.10）→ **今日の分をもう送った**（`approval_reminder_runs` に今日の行を入れられなければ送らない。一意の日付で 2 回を防ぐ）
- 今日の行を入れることと、まとめメールを積むことは **1 つのトランザクション**で行う（途中で止まれば両方残らない。「送ったことになっているのにメールが無い」を作らない）。コマンドは重ねて動かさない（`withoutOverlapping`）
- 9:00〜9:04 に動かなかった日は送らない（D17）

**載せる申請**
- **ホームの「対応待ち」（`PendingWork::for()`）と同じもの**のうち、待ち日数（`PendingWork::waitingDays()`）が **3 以上**のもの（D5）。古い順
- 全員分を 1 回の問い合わせでまとめる部品を作る（1 人ずつ `for()` を呼ばない）。**全員について `PendingWork::for()` と同じ結果になることを突き合わせる試験で守る**
- 対応されるまで、送る日の朝ごとに載り続ける

**まとめメール**
- 1 人 1 通。宛先は有効でメールアドレスのある人（`allows()` が通すもの）だけ。催促はメールだけ（要件 8.1。お知らせは作らない）
- 1 件ごとに件名・申請者（部門）・必要な対応・待ち日数・リンク。1 通 20 件まで、多いときは「ほか N 件はホームで確かめてください」（D18）。最後に決裁のホームへのリンク
- 送り直し・送れたかの記録は §5.5 と同じ（D2 の表示の対象）
- **リンクの作り方（D20）**: 画面の操作が無いので、設定（`config/approval.php` に足す）から作る。既定は `APP_URL` に `/index.php` を足したもの（本番の形 `https://www.mitsuwat.co.jp/system/manage/index.php/…`）。**3b の計画の最初に本番の `APP_URL` を読み取りで確かめて決める**（秘密の値ではないが `.env` は読まない。`config('app.url')` を tinker で読む。了承を取ってから）

### 5.9 催促の設定（⑫・3b・`approvals.admin.holidays.*`）

- 「決裁の管理」（決裁のみ利用者のサイドバーと、基幹のサイドバー 3 か所）に「催促の設定」を足す。使い始める前から使える
- 画面の上に「次に催促を送る日: 10/1（水）」と「前回の催促: 9/30（3 人・5 件）」（`approval_reminder_runs`）
- 送らない日の一覧（開始日の順）・追加・修正・削除。1 件ごとに開始日・終了日・毎年繰り返すか・説明（例: 年末年始 12/29〜1/3・毎年）
- 入力の決まり: 終了日は開始日より前にできない。毎年繰り返す期間は 1 年より短く（計画で細部を決める）。説明は必須かどうかも計画で決める
- 追加・修正・削除は設定の変更の記録（`SettingLogger`）に残す

### 5.10 祝日の判定（3b）

- 送らない日 ＝ 土曜・日曜 ／ 日本の祝日（部品 Yasumi の日本の祝日。振替休日・国民の休日を含む。D4）／ `approval_holidays` の期間
- 期間の比べ方: 毎年繰り返さないものは日付の範囲。毎年繰り返すものは**月と日だけ**で比べ、開始の月日が終了の月日より後なら年をまたぐとみなす（12/29〜1/3。D19）
- 判定は日本の日付で行う（`JapanTime::today()`）
- 部品は手元で入れてから `vendor` ごと本番へ送る（段階1 の QR の部品と同じ手順。本番では `composer install` をしない）。**3b の計画で、最新版が PHP 8.3（本番）と手元の PHP で動くこと・日本の祝日の中身を確かめる**（Context7 と実測）

## 9. 実装計画で決めること

- お知らせを Laravel の通知のクラス（`database` はその場・`mail` はキュー。`viaConnections()`）で作るか、`notifications` の行と自前のメールのクラスを直接作るか。どちらでも §5.5 の「同じトランザクション・宛先は操作の時点で決める」を守る
- `notifications` の索引（未読の数・その申請の未読）と、`data` の中身の形。「その申請の未読」の引き方（`data` の中の申請の ID）
- メールが「送れた」ことの拾い方（メールのイベントか、送るジョブの中か）と、`approval_settings` に足す列の形
- `StepHandlers` の置き場所と、`CurrentHandler`・`PendingWork` との関係（規則を 4 か所目に書かない形）
- 各 Workflow のメソッドのどこで Notifier を呼ぶか（取り下げは `cancelRest()` の前・部門長の交代は `$newHeadId`）と、`setPresident` をトランザクションで囲む形
- お知らせの文言の全部（§5.5 の表を元に）と、場面 2 のわけの文
- 全員分の対応待ちをまとめる問い合わせ（3b）と、`PendingWork::for()` との突き合わせの作り方
- 催促のコマンドの名前・予定の書き方（`ScheduleTest` に足す内容）・`approval_reminder_runs` の列
- リンクの設定の名前と既定値（本番の `APP_URL` を確かめてから。D20）
- Yasumi の版（PHP 8.3 と手元の PHP）と、日本の祝日の確かめ方（2026〜2027 年の実際の祝日と突き合わせる）
- ⑫ の入力の決まりの細部（1 年より短い・説明は必須か）と画面の配置
- 走査テストへの登録（§4.5）・`lang/ja/validation.php` に足す和名・テスト用の作り方（factory）・変異テストの一覧
