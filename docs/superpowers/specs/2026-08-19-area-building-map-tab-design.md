# 周辺ビル調査 一覧地図タブと位置登録 — 設計書

作成日: 2026-08-19
対象: `tenant/area-buildings`（周辺ビル調査 **第2段の一部**）
前提: @docs/superpowers/specs/2026-08-12-tenant-area-building-survey-design.md（§6.0 / §6.2 / §7.4）

---

## 1. 背景

2026-08-19 に実運用の「営業（空室）状況調査表」187 棟を Excel 取込で投入した（調査年月 2026-07）。
**座標は 1 件も入っていない**（`latitude IS NULL` が 187 件）。

利用者からの追加要件はこうだった:

> 所在地は分かりませんので所在地の入力・表示は必要ありません。すべてマップ上で表示します。

つまり **住所は今後も入らない**。位置は地図上でピンを置いて登録する。

第1段（2026-08-17 本番投入）で作った座標の入力手段は次の 2 つで、どちらも今の状況では使えない:

| 手段 | なぜ使えないか |
|---|---|
| 住所からの座標一括取得（§7.4） | 対象が「住所あり かつ 座標なし」の行だけ。住所 0 件なので**ボタン自体が出ない** |
| 登録・編集フォームの地図 | 地図クリックでピンは置けるが **1 棟ずつ**。187 棟を編集画面の開閉で回すのは現実的でない |

一覧地図は §6.2 に設計済みだが第1段では未実装で、§6.2 は色分け閾値について
**「閾値は第1段で実データを入れてから確定する（想定で決め打ちしない）」**としていた。
本設計書はその宿題を実測で片付ける（§3）。

## 2. 決定事項（ユーザー確認済み 2026-08-19）

| # | 論点 | 決定 |
|---|---|---|
| 1 | 地図で一番やりたいこと | **地図上で位置を登録すること**。閲覧はその後 |
| 2 | 187 棟の進め方 | **上から順に一気に片付ける**（クリック → 保存 → 自動で次の棟へ） |
| 3 | 地図上でビルを見つける手段 | **追加の仕組みは作らない**（地元のエリアなので地図を見れば分かる）。ビル名での検索・ジオコーディングはしない ＝ **Geocoding の課金は 0 回** |
| 4 | 置き場所 | **一覧に「地図」タブを追加**（§6.0 が地図生成を許した 2 箇所目 `?view=map`）。閲覧と登録を同じ画面に持たせる |
| 5 | 所在地 | **画面から消す**。ただし **DB 列 / Excel 取込の「所在地」マッピング / 住所からの一括取得は温存**（表示だけ消す） |
| 6 | 空室率の閾値 | **0 / 25 / 50 に統一**。地図の凡例だけでなく**一覧の既存フィルタも揃える**（食い違わせない） |

**採らなかった案と理由:**

- **作業専用画面を別に作る** — 登録が終わったら用済みになり、閲覧マップをもう 1 画面作ることになる。
  地図を生成する箇所が 3 つに増え、§6.0 の「2 箇所に絞る」方針から外れる
- **一覧の行から「地図で指定」モーダル** — 変更は最小だが 187 回開閉するので #2 に合わない
- **ビル名でジオコーディングして下地を作る** — 利用者が不要と判断。
  ⚠ 技術的にも**外れたときに市中心へ寄った偽の座標が無警告で入る**（`partial_match` を見ない限り区別が付かない）ので、
  採るなら先に当たり率の実測が要る。§12.1 が Places について書いた「先に実測すること」と同じ理屈

## 3. 実測: 空室率の分布（閾値の根拠）

2026-08-19 時点の 187 棟（調査年月 2026-07）を `VacancyRate` と同じ式で集計した。

```
空室率(%) = (空き + 不明) × 100 ÷ (営業 + 空き + 不明)   ※1/10% 単位の切り捨て
```

- 中央値 **33.3%** / 平均 **32.4%** / 最大 100%（全空きが 5 棟）
- **区画数が 0 で率が出せない棟が 2 棟**（ウエル館・ふじビルディング。営業 0 / 空き 0 / 不明 0）

| 区切り | 0% | 1〜24% | 25〜49% | 50%〜 |
|---|---:|---:|---:|---:|
| **0 / 25 / 50（採用）** | 45 棟 (24%) | 33 棟 (18%) | 49 棟 (26%) | 58 棟 (31%) |
| 0 / 20 / 40（§6.2 の初期案） | 45 棟 (24%) | 23 棟 (12%) | 42 棟 (22%) | **75 棟 (40%)** |

初期案（20 / 40）では**赤が 4 割**を占め、地図が赤だらけで差が見えない。
**0 / 25 / 50 ならほぼ四等分**になるので、こちらを採る。

⚠ この閾値は**今回のデータで決めたもの**。調査回が数年ぶん貯まったら見直す前提で、
定数を 1 箇所に置いて動かしやすくする（§4.2）。

## 4. 画面

### 4.1 タブ

一覧 `/tenant/area-buildings` に表示切替を足す。**新しいルートは作らない**（`?view=map` のクエリだけ）。

- タブは「表」｜「地図」。**既定は「表」**
- 既存の絞り込み（空室率・調査年・キーワード）とページングは表タブのまま。
  タブを切り替えても絞り込みは維持する（リンクに現在のクエリを引き継ぐ）
- ⚠ **地図タブはページングしない。** 表は 20 件/頁だが、地図に 20 本だけピンが出ても意味がない。
  **絞り込み後の全件**を出す（現状 187 棟。ピン数が 4 桁になったら改めて考える）

### 4.2 閲覧モード（既定）

- 座標のある棟をピン表示し、**空室率で色分け**する

  | レベル | 空室率 | 色 | 現状の棟数 |
  |---|---|---|---:|
  | `full` | 0%（満室） | 緑 | 45 |
  | `low` | 1〜24% | 黄 | 33 |
  | `mid` | 25〜49% | 橙 | 49 |
  | `high` | 50%〜 | 赤 | 58 |
  | `unknown` | 調査が無い / 区画数 0 | 灰 | 2 |

- ピンクリックで InfoWindow（ビル名 / 総階数 / 営業・空き・不明 / 空室率 / 詳細へのリンク）
- 全ピンに `fitBounds`。**ピン 0 件なら松山市中心へフォールバック**（`33.8392, 132.7657` / zoom 13）
- 座標未登録の棟は地図に出せないので、**地図の外に「位置未登録 N 棟」と件数だけ出す**
  （黙って消えると「取り込んだのに出ない」と誤解される）

⚠ **`unknown` の棟は率で絞ると消える**（既存挙動。`matchesVacancy()` は `rate === null` を `false` で返す）。
「空室率: 全て」のときだけ灰ピンが出る。これは表タブと同じ振る舞いなので変えない。

⚠ **閾値の判定は PHP 側 1 箇所に置く。** `App\Support\VacancyRate`（`percent()` / `label()` は既存）に
`level(int $op, int $va, int $un): string` を足し、
**一覧のフィルタ・地図の色分け・凡例がすべてこれを見る**。JS 側で閾値を再実装しない。
割れると「フィルタで 25% 以上を選んだのに緑のピンが出る」が起きる（Bug #41）。

⚠ **一覧の既存フィルタの選択肢も 25% / 50% に変える**（決定事項 #6）。実測した現状:

```php
// app/Services/Tenant/AreaBuildingListService.php
public const VACANCY_OVER20 = 'over20';   // → VACANCY_OVER25 = 'over25'
public const VACANCY_OVER40 = 'over40';   // → VACANCY_OVER50 = 'over50'
```

`matchesVacancy()` の `match` に書かれた `>= 20.0` / `>= 40.0` の直値も **`VacancyRate::level()` 経由に寄せる**
（フィルタと凡例が別々に閾値を持たないようにする）。

⚠ 値の名前が変わるので、**古いブックマークの `?vacancy=over20` は「全て」に落ちる**
（`array_key_exists` に無い値は `return true`。実測）。エラーにはならないが、絞ったつもりで全件が出る。
運用が始まって日が浅いので影響は無いと判断する。

⚠ **Bug #31（`?vacancy=` がページ送りで飛ぶ）はこの画面では既に対処済み**（実測）。
`matchesVacancy()` が型ガードより先に `null` と `''` を「全て」として返しており、
既定も「全て」なのでキーが落ちても結果が変わらない。**この順序を崩さないこと。**

### 4.3 登録モード

閲覧モードの右上の「位置を登録」トグルで切り替える（**経営層＋管理者のみ表示**）。

- 左に**座標未登録の棟のリスト**（表と同じ並び）。**先頭が「今の棟」**として強調される
- 地図をクリック → その座標を**即保存** → **自動で次の棟へ**進む。進捗は「残り N 棟」
- ⚠ **保存しても地図の中心・ズームを動かさない。** 隣接する棟が続けて出てくるので、
  動かすと毎回同じ場所へ戻す操作が要る
- 置き直し: リストで棟を選び直してもう一度クリックする（**上書きされる**）
- 飛ばす: 「スキップ」で次の棟へ（座標は保存しない）
- 保存が失敗したら**画面のステータス行に理由を出し、次へ進めない**
  （黙って次へ行くと、置いたつもりの棟が未登録のまま残る。Bug #45）

⚠ **`<option>` を `<template x-for>` で作らない**（Bug #16）。リストは `@foreach` で静的に描く。
⚠ **`x-show` と `:style` を同じ要素に置いて `display` を書かない**（Bug #32）。
⚠ **押せないボタンの理由は `<span>` ラッパーの `title` に置く**（Bug #43）。

### 4.4 モバイル

768px 未満では左リストを地図の**上**に積む（横並びは `sm:` 以上）。
地図の高さは `60vh` 程度で固定し、リストは `max-height` + 縦スクロール。

⚠ インラインの `grid-template-columns` はメディアクエリより強い。レイアウトはクラスで組む
（memory「モバイル崩れは2類型」）。

## 5. ルートとデータの受け渡し

### 5.1 ルート

| メソッド | URI | 権限 | 用途 |
|---|---|---|---|
| GET | `/tenant/area-buildings?view=map` | 全ロール | 地図タブ（**既存 index に統合。新ルート無し**） |
| POST | `/tenant/area-buildings/{building}/coordinates` | `role:executive,manager` | **新規**。手で置いたピンを 1 棟保存 |

- 入力: `latitude`（`required|numeric|between:-90,90`）/ `longitude`（`required|numeric|between:-180,180`）
- **上書き可**。置き直しが目的なので `whereNull('latitude')` ガードは付けない
- 返す: JSON（`{ id, latitude, longitude }`）。失敗時は 422 とメッセージ
- ⚠ 既存の一括取得 `POST /tenant/area-buildings/geocode` は**役割が違うので温存**する。
  あちらは「住所から機械が引いた座標を、まだ座標が無い行にだけ入れる」= 二重課金の防止が本質。
  こちらは「人が地図を見て置いた座標を、何度でも入れ直せる」。**同じルートに寄せない**
- ⚠ ルートの宣言順は `/{building}` より `create` `import` `geocode` が先という既存規約に従う。
  本ルートは `/{building}/coordinates` なので衝突しないが、`{building}` の `where` 制約は既存に合わせる

### 5.2 ピンデータ

⚠ **ピン配列は必ずコントローラで組み立て、単一変数として Blade へ渡す**（§6.2 の再掲）。

- `@json()` に多行の配列リテラルやメソッド呼び出しを渡さない（Bug #26）
- `x-data="..."` 属性の中に `@json` を置かない。`<script>` 内の named function で受けるか
  `{{ \Illuminate\Support\Js::from($pins) }}` を使う（Bug #23）
- `<script>` 内の `//` コメントに `@json` `@if` などのディレクティブ名を書かない。書くなら `@@json`（Bug #30）
- Ajax は **POST の `fetch`** に `Accept` と `X-Requested-With` を付ける（Bug #35 は GET だけが対象だが、
  ヘッダーを付ける流儀に揃える）。エラーは**画面のステータス行に出す**（`console.error` だけにしない。Bug #45）

## 6. 所在地を画面から消す

### 6.1 消すもの

| 場所 | 変更 |
|---|---|
| 一覧の表 | 「所在地」列を削除 |
| 一覧のキーワード検索 | `area_buildings.address` の LIKE を外す。プレースホルダを「ビル名・テナント名」に |
| 詳細画面 | 「所在地」の表示を削除 |
| 登録・編集フォーム | 「所在地」入力欄を削除 |

### 6.2 残すもの（と理由）

- **`area_buildings.address` 列** — 消す理由が無い。既存データも将来の取込も壊さない
- **Excel 取込の「所在地」マッピング** — 住所付きの表が来たら入れられる
- **住所からの座標一括取得（§7.4）** — 対象は「住所あり かつ 座標なし」なので、
  住所が 0 件の今は**ボタン自体が出ない**（`pendingGeocodeCount()` が 0）。
  放っておいても画面には出ず、住所が入れば自動で復活する

### 6.3 フォームの地図の単純化

住所入力欄が無くなると、フォームの「マップで確認」は**必ず住所が空の分岐**に落ちる。
そのため地図パーツを次のように単純化する:

- ボタンを「**地図で位置を指定**」に変え、押したら常に地図を開く
  （保存済み座標があればそこ、無ければ松山市中心）
- ピンのドラッグと地図クリックによる座標の更新は**そのまま残す**
- 到達不能になる住所検索の JS を**削除**する:
  `areaGeocoder` / `buildAreaAddressFallbacks()` / `tryGeocodeAreaCandidates()` / `geocodeAreaAddress()` の住所分岐

⚠ **段階フォールバックを一括取得側へ移さない。** 一見もったいないが、
§6.1 に「**1 クリックで最大 5 回ジオコーディングを叩く。一括処理でこの関数を使い回さないこと（設計 6.1 / 7.4）**」と
明記されている。移すと 1 棟あたり最大 5 リクエストになり、一括取得の費用が 5 倍になりうる。

⚠ **`AreaBuildingAddressFallbackRegexTest` の第 1 ケースは `_form.blade.php` を名指しで見ている**（実測）。
一括取得側（`index.blade.php`）には段階フォールバックが**無い**（`areaGeocoder.geocode({address: item.address})` を直接呼ぶ）ので、
移送先も無い。**当該ケースは削除する**。同ファイルの他のケース（`resources/views` 全体を走査するもの）は残す。

## 7. 課金

§6.0 の方針を変えない。**地図を生成するのは 2 箇所だけ**:

1. 登録・編集フォームの「地図で位置を指定」を押したとき
2. **一覧の地図タブを開いたとき**（`?view=map`）

- **表タブで見ている限り課金は発生しない。** 既定が表であることが load-bearing（§9 でテストする）
- **Geocoding は本件で 0 回**（ビル名検索をしないと決めた。決定事項 #3）
- `streetViewControl: false`（利用者が開いた回数だけ課金されるため）
- 詳細画面には埋め込み地図を置かない（従来どおりリンクのみ）

## 9. テスト方針

**挙動と構造を対で見る**（Bug #28 / #35 / #47 の流儀）。

### 座標の保存
- 座標を保存できる / **既存座標を上書きできる**（`whereNull` ガードが混入したら落ちる）
- 範囲外（緯度 91 など）を弾く / 数値でない値を弾く
- staff は 403 / 未ログインは弾かれる
- **既存の一括取得は従来どおり `latitude IS NULL` の行しか触らない**（新経路を足したせいで
  二重課金ガードが緩んでいないこと）

### 地図タブ
- `?view=map` で地図の器とピンデータが出る
- **表タブ（既定）では Maps JavaScript API のスクリプトも地図の初期化も出ない**
  ← 課金方針そのものなので、混入したら落ちるテストを必ず置く
- 絞り込みがタブ間で維持される
- ピン 0 件でも 500 にならない（松山市中心へフォールバック）
- **地図タブはページングしない**（絞り込み後の全件がピンデータに入る）
- 座標未登録の件数が画面に出る

### 閾値
- `VacancyRate::level()` の境界（0 / 0.1 / 24.9 / 25 / 49.9 / 50 / 100 / 区画 0）
- **一覧フィルタと地図の凡例が同じ定数を見ている**こと
  ← 別々に持つと片方だけ直す事故が起きる（Bug #41）

### 所在地
- 一覧・詳細・登録編集フォームに「所在地」が**出ない**
- キーワード検索が住所を見ていない
- **DB 列と Excel 取込の「所在地」マッピングは生きている**（消しすぎの検出）
- フォームに `geocodeAreaAddress` などの到達不能 JS が**残っていない**

### 完了判定
⚠ **「テストが緑」は検証にならない。** 変異を入れて赤になることを実測してから完了とする（Bug #42 / #44 / #45）。
手順は Bug #44 のとおり: ①先にコミット ②各変異の前に `git status --porcelain` が空
③`git diff --stat` が非空で着弾を確認 ④**落ちた理由の文言まで**突き合わせる。

最低限、次の変異で赤になることを測る:
- 座標保存に `whereNull('latitude')` を足す（置き直しが死ぬ）
- 表タブでも地図スクリプトを出す（課金方針が死ぬ）
- 閾値を 20 / 40 に戻す（フィルタと凡例の一致が死ぬ）
- 地図タブでページングする（ピンが 20 本に減る）
- 所在地の列を戻す / 取込マッピングを消す（消しすぎ・消し足りないの両方向）

## 11. 本番反映

- Blade / ルート / コントローラの変更なので **`./deploy.sh`**（`route:cache` と `view:cache` の再生成が要る）
- **DB 変更は無い**（`area_buildings.latitude` / `longitude` は第1段で作成済み）
- ⚠ 新規 PHP クラスを足した場合のみ、main repo の cwd で `composer dump-autoload`
- 反映後、本番のブラウザで**実際にピンを 1 つ置いて保存し、置き直せること**まで確認する
  （「HTML に出るか」では地図の挙動は検証できない。Bug #28 / #32 / #43）
