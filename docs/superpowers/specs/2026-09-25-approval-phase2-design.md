## 2. 決定事項（2026-09-25〜26 の対話で確定）

D1〜D5 は選択式で個別に、D6〜D25 は設計の各節の中で「要件定義書に無く、開発側で決めた点」として示し、利用者が承認した（括弧内は対話のときの記号）。

| # | 論点 | 決定 |
|---|---|---|
| D1 | 本番への出し方 | 段階2 も**できたら本番へ出す**。申請を回す画面は、使い始める日まで**誰にも見せない（決裁の管理者にも）**。準備の画面（部門・申請の種類・利用者の管理）は決裁の管理者が本番で先に使える。動きの確認は手元で行い、画面の写真で利用者に見せる。試しのデータを本番に残さない |
| D2 | 社長決裁の付け替え | **作らない**（要件定義書 4.7 からの変更）。決裁の管理者が「最後に決裁する人」を 1 件ずつ選べると、社長の指定を基幹の管理者だけに限った 3.2（なりすまし防止）の意味が崩れるため。社長が長く不在のときは、基幹の管理者が社長の指定を変える（社長決裁待ちの申請はすべて新しい社長へ移る。4.3 のケース 6）。部門長の確認の付け替えは、要件どおり決裁の管理者ができる |
| D3 | 差戻しの取り消し | 申請者が**直し始めていたら取り消せない**（申請者の直しを守る）。その場合は申請者に出し直してもらう（最初から回り直し） |
| D4 | 社長の申請 | **社長に指定されている人は申請できない**（自分の申請を自分で決裁する形をなくす） |
| D5 | 作り方 | 2 回に分ける（2a・2b。§1.1） |
| D6 (a) | 部門長・審査担当者の条件（所属） | その部門に**所属していなくてもよい**（例: 住宅（少額・追加工事）の部門長を住宅事業部と同じ人にする） |
| D7 (b) | 部門長・審査担当者の条件（有効・メール） | 選べるのは**有効でメールアドレスのある人**（3.1）。許可していないドメインの人は選べるが「通知メールが届きません」と注意を出す |
| D8 (c) | 部門の会社・アルファベットの変更 | **番号を付けた申請がある部門は、会社とアルファベットを変えられない**（同じ年度の番号の続きが崩れるため） |
| D9 (d) | 開始番号 | 「次に付く番号」を設定する。**すでに使った番号より小さくできない**（番号の重なりを防ぐ） |
| D10 (e) | 停止した種類 | 新しい申請では選べない。**下書きは提出の前に種類を選び直してもらう**。差戻し中の申請は、そのまま出し直せる |
| D11 (f) | 審査部門の変更 | 回覧中の申請は**提出したときの審査部門のまま**。出し直すと新しい設定になる |
| D12 (g) | 本文が見出しのまま | **提出できない**（何も書き足していない） |
| D13 (h) | 下書き保存 | **入力の途中でも保存できる**（必須の項目がそろっていなくてよい） |
| D14 (i) | 添付の送り方 | **下書きを 1 回保存したあとに追加**する。何枚かまとめて選べ、1 つずつ順に送る。**1 件の申請に 20 ファイルまで**。HEIC・HEIF はブラウザで開かずダウンロード（Safari 以外で表示できないため） |
| D15 (j) | 関連する決裁No | **10 個まで**。入力中に、見られる決裁の番号と件名を候補に出す。紙の時代の番号は形（例 `R7-J-015`）だけ確かめて受け付ける |
| D16 (k) | 自分の申請への判断 | **部門長・審査・社長のどの立場でも、自分の申請には判断できない**（例: 申請のあとで申請者本人が部門長になった）。管理者の付け替え（2b）か、取り下げて出し直す |
| D17 (l) | 申請者の取り下げのコメント | **任意**（管理者の代理の取り下げは要件どおり理由が必須） |
| D18 (m) | 出し直したときの回り方 | **出し直した時点の設定**（部門長・審査部門・審査担当者）で回る |
| D19 (n) | 審査担当者・社長の閲覧 | **一度自分の段階に届いた申請は、その後もずっと見られる**（出し直しの途中でも） |
| D20 (o) | 待ち日数 | **自分の番が来た日から数えた暦の日数**（日本時間） |
| D21 (p) | 取り消しで残った番号 | **年度をまたいで判断し直しても同じ番号**（6.5 の文字どおり。例: 4/30 に付いた R8 の番号を取り消し、5/2 に判断し直しても R8 のまま） |
| D22 (q) | 付け替えの理由 | **必須**（取り消し・代理の取り下げとそろえる） |
| D23 (r) | 付け替えた申請と部門長の交代 | 付け替えた申請も、部門の設定で部門長を変えると**新しい部門長へ移る**（4.3 のケース 5 の文字どおり） |
| D24 (s) | 取り消しの連続 | **続けて行えば 1 つずつさかのぼれる**（提出の手前まで） |
| D25 (t) | 管理者自身の申請 | 決裁の管理者でも、**自分が申請者の申請には、付け替え・取り消し・代理の取り下げができない**（自分の申請の回り方を自分で変えられないように） |

## 3. 要件定義書からの変更（v1.9 に反映する）

要件定義書 v1.8 は書き換えず、変更はこの設計書に記録する。設計書の承認のあと v1.9 を作り、読みやすい版も同じ URL のまま更新する。

| # | 要件定義書 | この設計 | 理由 |
|---|---|---|---|
| 1 | 4.7「担当の付け替え: 部門長確認・社長決裁の担当者を別の人に変える」／13 章⑩ | **部門長の確認だけ**（D2）。理由は必須（D22） | 3.2 の線引き（社長の指定は基幹の管理者だけ）と食い違うため |
| 2 | 8.1「担当を付け替えられた → 新しい担当者」 | 部門長の確認の付け替えだけが対象（D2） | 同上 |
| 3 | 3.1「申請者 = 全利用者」 | 社長に指定されている人は申請できない（D4） | 自分の申請を自分で決裁する形をなくす |
| 4 | 4.3 の例外の表 | 「自分の申請には、部門長・審査・社長のどの立場でも判断できない」（D16）を足す | 申請のあとで役割が変わった場合の穴を塞ぐ |
| 5 | 4.7「押し間違いの取り消し」 | 差戻しは申請者が直し始めていたら取り消せない（D3）／続けて行えば 1 つずつさかのぼれる（D24）／管理者は自分の申請に付け替え・取り消し・代理の取り下げをできない（D25） | 決めていなかった場面を決めた |
| 6 | 5.1・5.3・5.4 | 添付の送り方と上限（D14）・関連する決裁No の上限（D15）・本文が見出しのままでは提出できない（D12）・下書きは途中でも保存できる（D13） | 同上 |
| 7 | 5.5.1「停止した種類は新しい申請で選べない」 | 下書きは選び直し、差戻し中はそのまま出し直せる（D10） | 同上 |
| 8 | 6.4・6.5 | 開始番号は使った番号より小さくできない（D9）／番号のある部門は会社とアルファベットを変えられない（D8）／取り消しで残った番号は年度をまたいでも同じ（D21） | 同上 |
| 9 | 7 章 | 審査担当者と社長は、一度届いた申請をその後も見られる（D19） | 同上 |
| 10 | 16.1 | 段階2 を 2a・2b に分け、どちらもできたら本番へ出す（申請を回す画面は隠す。D1・D5） | 利用者の選択 |

- D6・D7・D11・D17・D18・D20・D23 は要件定義書の書き足し（食い違いではない）として v1.9 に入れる。

## 4. 調べて分かった事実（2026-09-25 に実物で確認）

### 4.1 段階1 で作られたもの

- 表: `approval_companies`（会社名・期の始まりの月・表示順）／`approval_departments`（会社・部門名 50・略称 6・アルファベット 1〜3・表示順。**部門長・開始番号の列は無い**）／`approval_department_user`（所属。兼務可）／`approval_members`（全件閲覧者 `can_view_all`・決裁の管理者 `is_admin`）／`approval_settings`（1 行だけ。社長 `president_user_id`）／`approval_mail_domains`／`approval_setting_logs`（追記のみ）
- 本番は `database/sql/2026-09-16-approval-phase1.sql` を **tinker の `--execute` で 1 文ずつ**流した。テストは同じ構造の migration（`2026_09_16_000001_create_approval_tables.php`）。**両方を対で維持**する
- ルート: `routes/approval.php`（`routes/web.php` の末尾から読む。`auth`・`password.change` のグループの中）。名前はすべて `approvals.` で始まる
  - 門番 `RestrictApprovalOnlyUsers` は、決裁のみ利用者に `approvals.` の名前のルートと `password.change`・`password.update`・`logout`・`guest` のルートだけを許す
  - 管理の画面は `approval.admin`（`EnsureApprovalAdmin`）。どちらも `SubstituteBindings` より前に並べてある（`bootstrap/app.php` の `appendToPriorityList`）
  - `ApprovalOnlyLockoutTest` が全ルートを機械的に分類する。`approvals.` を名乗れるのは `App\Http\Controllers\Approval\` のコントローラだけ（同テスト）
- ルートのパラメータ名は `{approvalCompany}` などモデル名の camelCase。`{department}` は基幹で別の意味（`CheckDepartmentAccess`）を持つので使わない
- `User`: `isApprovalOnly()`・`isApprovalAdmin()`・`canViewAllApprovals()`・`isApprovalPresident()`・`hasApprovalPrivileges()`・`approvalDepartments()`・`homeRouteName()`。`ApprovalSetting::current()` は 1 リクエストに 1 回だけ読む
- `SettingLogger::record()` / `recordChange()` が設定の変更を記録する（誰が・対象・変更前後・IP・端末）
- 社長の守り（無効化・削除・メールアドレスを空にする操作を断る）は `Admin\UserController` にある。決裁の管理者の側は `Approval\UserController`
- サイドバー: 決裁のみ利用者は `layouts/partials/sidebar_approval.blade.php`（`layouts/app.blade.php` がロールで出し分け）。基幹を使う人で決裁の管理者に指定された人には、基幹のサイドバー 3 か所に「決裁の管理」がある
- ホーム（`approvals.home`）は仮の「決裁の機能は準備中です」

### 4.2 基幹の決まりと部品

- 基幹の添付（`AttachmentController`）は `public` ディスク（`storage/app/public`）・10MB・`jpg,jpeg,png,gif,webp,heic,heif,pdf,doc,docx,xls,xlsx,csv,txt`。**決裁の添付は 14.3 の「非公開」を満たさないので使い回さない**。`local` ディスクの根は `storage/app/private`（`serve: true` は署名つき URL 用で、署名が無ければ開けない）
- 夜間バックアップは `storage/app/{public,private}` を「同じパス・同じ大きさなら送り直さない」判定で差分を送る → **添付は上書きしない**（新しい内容は新しい名前）
- 日時: 保存は `now()`、表示は `JapanTime::format()`、日本の今日は `JapanTime::today()`（Top trap #19）。年度の式は `JapanBusinessDayTest` が全件分類し、時計の読み取りは `ClockReadScanTest` が全件分類する
- 期: 汎用の年度・和暦の部品は無い（`ZealFiscalYear` は ZEAL 専用の 6 月始まり）
- 本番のキャッシュとセッションは `file`（2026-09-25 の段階1 の反映で確認）。`Cache::add` は `FileStore` の排他ロックで本当に排他的
- 本番の MySQL は 8.0.40・照合順序は `utf8mb4_unicode_ci`
- 本番の php.ini のアップロードの上限は未確認（初期値 2MB の報告あり）。要件定義書 16.3 の 15 で、使い始める前に利用者が調整する
- 守るべき過去のバグ: #16（`<option>` は `@foreach`）・Top trap #4（`x-data` にアロー関数を書かない）・#6（IME の Enter）・#35（GET の `fetch` に `X-Requested-With`）・#36/#37（`lang/ja` と和名）・#43（押せないボタンの理由は `span` で包む）・#45（走査テストは全件分類）・#53（view に `errors` を渡さない）・#56（展開サイドバーに `x-cloak` を付けない）・#61（日本時間）・#64（戻り先に `url()->previous()` と素の `back()` を使わない）・#65（一括操作のある絞り込みは `pageshow` で `reset()`）

### 5.2 使い始めるまでの隠し方（D1）

- `approval_settings` に `launched_at`（TIMESTAMP・NULL 可）を足す。**NULL のあいだは「準備中」**。`ApprovalSetting::current()->isLaunched()`
- 門番 `approval.launched`（`EnsureApprovalLaunched`）: 準備中なら、画面を開く GET・HEAD（Ajax でないもの）は `approvals.home` へ転送し、それ以外（POST・Ajax・JSON）は 404。**`SubstituteBindings` より前**に並べる（存在しない ID でも同じ応答にして、データの有無を漏らさない。段階1 の門番と同じ理由）
- 準備中のあいだ
  - ホームは今の「準備中」の画面のまま（決裁の管理者には管理の画面へのリンク）
  - サイドバー（決裁のみ利用者用・基幹の 3 か所）に、申請を回す画面へのリンクを出さない。管理の画面へのリンク（利用者・部門・申請の種類）は今までどおり
  - 部門長・審査担当者・開始番号・申請の種類の登録はできる（本番で先に準備できる）
- `launched_at` を入れる画面と、関係者だけで試す仕組みは段階6。それまで本番の `launched_at` は NULL のまま。手元とテストでは直接入れる
- 検査: `approvals.` のルートを機械的に列挙し、「準備中も使える」（`approvals.home`・`approvals.admin.users.*`・`approvals.admin.organization.*`・`approvals.admin.types.*`）と「準備中は止める」のどちらかに**全件分類**する。どちらにも無いルートは落とす（Top trap #13）。止める側は準備中に実際に要求して、転送か 404 になること・存在しない ID でも同じことを見る

### 5.4 部門の管理に足すもの（画面⑧）

- 部門の追加・編集のモーダルに **部門長**（1 人・空でもよい）と **審査担当者**（何人でも）の選択を足す
  - 選択肢は**有効でメールアドレスのある人**（D7）。基幹を使う人・決裁のみ利用者のどちらも。所属は問わない（D6）
  - 許可していないドメインの人には「通知メールが届きません」と添える（選べる）
  - 部門の一覧に部門長と審査担当者の人数を出す
- **今年度の開始番号**（部門ごと）: 「次に付く番号」を入れる。今年度＝その部門の会社の期で、日本の今日が入る年度（§5.9）
  - その年度にすでに番号を付けていれば、**使った番号より大きい数**しか入れられない（D9）。画面に「今年度（R8）は R8-J-005 まで使っています」と出す
  - 翌年度は 1 から始まる（翌年度の開始番号は、その年度に入ってから設定する）
- **部門長を変えたとき**: その部門で部門長の確認中の申請は新しい部門長へ移る（4.3 のケース 5）。付け替えた申請も移る（D23）＝その部門の待っている部門長の段階の `assignee_user_id` を空に戻し、申請ごとに記録（`head_changed`・変更前後の部門長）を残す
- **削除の歯止め**（段階1 の「所属者がいる部門は削除できない」に足す）: 申請（下書きを含む）がある部門・申請の種類の審査部門になっている部門は削除できない
- **変更の歯止め**: 番号を付けた申請がある部門は、会社とアルファベットを変えられない（D8）
- **無効化などの歯止め**（12.6）: 部門長・審査担当者に指定されている人は、無効化・削除・メールアドレスを空にする操作ができない。「〇〇さんは〈部門名〉の部門長（審査担当者）に指定されています。先に後任を設定してください。」と出す。基幹の利用者管理（`Admin\UserController`・社長の守りと同じ場所）と決裁の利用者管理（`Approval\UserController`）の両方
- 変更はすべて `SettingLogger` で記録する（部門長・審査担当者の追加と削除・開始番号）

### 5.5 申請種類の管理（画面⑨・`approvals.admin.types.*`）

- 一覧（表示順）＋追加・編集のモーダル（部門の管理と同じ型）
- 項目: 種類名（50 文字まで・重複不可）・5W2H の見出し（標準の 6 つ〈5.2〉を初期値に入れ、種類ごとに書き換えられる。2,000 文字まで＝技術上の上限）・審査部門（必須・部門から 1 つ）・表示順・利用中/停止
- 申請が 1 件でもある種類は削除できない（停止を使う）
- 審査部門を変えても、回覧中の申請は提出したときの審査部門のまま（D11）
- 変更はすべて記録する
- 段階5 で足す列（本文の形・件名の決まり文句・明細表の行・追加の入力欄・定型文・使える部門）は、ここでは作らない

### 5.6 申請書（画面②）・下書き・コピー

**入力**（5.1 のとおり）

| 項目 | 形 | 提出のときの検査 |
|---|---|---|
| 申請の種類 | 利用中の種類から選ぶ | 必須・利用中（差戻し中の申請は停止していてもよい。D10） |
| 申請部門 | 自分の所属部門から。1 つなら自動 | 必須・今も所属していること |
| 件名 | 1 行 | 必須・100 文字まで |
| 金額 | 数字（円・税抜）。表示は `28,500,000円` | 任意・0 以上 999,999,999,999 以下の整数（`value="0"` の既定値を入れない。上限は技術上のもの） |
| 実施時期 | 1 行 | 任意・50 文字まで |
| 本文（重点ポイント） | 5W2H の見出し入りの文章 | 必須・見出しのままではない（D12）・20,000 文字まで（技術上の上限。MySQL の TEXT に収まる長さ） |
| 関連する決裁No | 番号を入れる（候補を出す） | 任意・10 個まで・形（D15） |

- 種類を選ぶと本文に見出しが入る。**選び直したとき**、本文がまだ見出しのままなら新しい種類の見出しに入れ替え、書き始めていたら入れ替えるか確認する
- 「見出しのまま」の判定（`BodyTemplate`）: 見出しの行（`■` で始まる行）と、中身の無い `・` の行と空白を除いて何も残らなければ「書いていない」
- 関連する決裁No: 全角→半角・大文字にそろえ、`^[RH][0-9]{1,2}-[A-Z]{1,3}-[0-9]{3,}$` の形だけ確かめる。候補は `approvals.numbers.search`（見られる範囲の、番号の付いた申請の番号と件名。Ajax の GET なので `X-Requested-With` を付ける。Bug #35）。詳細画面では、見られる申請ならリンクにする
- **下書き保存**（D13）: 必須の項目がそろっていなくても保存できる（形の検査だけ行う）。初めての保存で申請の行ができ、編集の画面へ移る
- **提出**: 確認のモーダル（「この内容で提出しますか？」）→ 提出の検査（§5.8 の提出の条件）→ 断るときは理由を出して編集の画面に戻す
- **下書きの削除**: 一度も提出していない下書き（`round = 0`）だけ。添付のファイルも消す
- **コピーして作成**: 自分の申請（取り下げ・否決を含む）から、種類・申請部門・件名・金額・実施時期・本文・関連する決裁No を写した新しい画面を開く（保存するまで下書きはできない）。添付は写さない。種類が停止していれば空にして選び直してもらう。申請部門に今は所属していなければ空にする
- 戻り先は画面ごとに決めた固定のルートにする（`url()->previous()` や素の `back()` を使わない。Bug #64）
- 和名を `lang/ja/validation.php` に足す（Bug #37）

### 5.7 添付

- 追加できるのは申請者本人だけで、**下書き中と差戻し中だけ**（5.3）。下書きを 1 回保存したあとに追加する（D14）
- 画面: ファイルを何枚かまとめて選べる。JS が 1 ファイルずつ順に `approvals.requests.attachments.store` へ送り（進み具合を出す）、送れたものから一覧に並べる。送る前に 10MB を超えるものと 20 ファイルを超える分は断る（画面の理由つき）
- サーバーの検査: `file|max:10240|mimes:jpg,jpeg,png,gif,webp,heic,heif,pdf,doc,docx,xls,xlsx,csv,txt`（基幹と同じ）・元のファイル名が 255 文字まで（技術上の上限）・その申請の生きている添付が 20 未満・状態が下書きか差戻し中。応答は JSON（断るときは日本語の理由）。上限を超えた POST（`PostTooLargeException`）も JSON の日本語で返す
- 保存: `local` ディスク（`storage/app/private`）の `approvals/{申請の id}/{無作為な名前}.{拡張子}`。**上書きしない**。元のファイル名は表の `original_name` にだけ持つ
- 開く（`approvals.attachments.show`）: 毎回 `RequestVisibility` で確かめてから返す。`pdf・jpg・jpeg・png・gif・webp` は `inline`、それ以外（HEIC・HEIF を含む。D14）は `attachment`。`Content-Type` はこちらで決めた対応表から出す（送られてきた値を信じない）。`X-Content-Type-Options: nosniff`・日本語のファイル名は `filename*`（UTF-8）
- 開くたびに `approval_download_logs` に記録する（inline で開いた場合も。14.2）
- 削除: 一度も提出の控えに入っていない添付（その編集の回で足したもの）はファイルごと消す。控えに入っている添付は `removed_round`・`removed_at` を入れて一覧から外すだけ（ファイルは残し、履歴〈2b〉から開ける）
- 添付の追加・削除は、申請の記録（`approval_histories`）には残さない（提出の控えの差で分かる。§5.11）

### 5.8 回覧（状態・操作・自動で飛ばす・例外・同時操作）

**状態**（`ApprovalStatus`。4.8 のとおり）

| 値 | 表示 | 次に進める状態 |
|---|---|---|
| `draft` | 下書き | 部門長確認中・審査中（提出）/ 削除 |
| `head_review` | 部門長確認中 | 審査中（承認）/ 差戻し中 / 取り下げ |
| `review` | 審査中 | 社長決裁待ち（意見）/ 取り下げ |
| `president` | 社長決裁待ち | 決裁済み（可）/ 条件確認待ち（条可）/ 否決 / 差戻し中 / 取り下げ |
| `returned` | 差戻し中 | 部門長確認中・審査中（出し直し）/ 取り下げ |
| `condition` | 条件確認待ち | 決裁済み（条可） |
| `approved` | 決裁済み（`decision` が可か条可） | なし（2b の取り消しを除く） |
| `rejected` | 否決 | なし（2b の取り消しを除く） |
| `withdrawn` | 取り下げ | なし |

**提出・出し直し**（`Workflow::submit`）
1. 状態が下書きか差戻し中で、操作する人が申請者本人であること
2. 提出の条件（どれかに当たれば断り、理由を出す）
   - 申請者が社長に指定されている（D4）
   - 申請部門に今も所属していない（5.1）・所属部門が 1 つも無い
   - 種類が停止している（下書きのとき。D10）
   - 申請部門の部門長が未設定・社長が未設定・審査部門に**申請者本人以外の有効な審査担当者**がいない（4.3 のケース 4）
   - 入力の検査（§5.6 の表）
3. `round` を 1 増やし、中身の控え（`approval_revisions`）を作る（§5.11）
4. その回の段階を作る: 部門長（申請者が申請部門の部門長なら `skipped`。記録に「申請者が部門長のため省略」。4.3 のケース 1。部門長が社長を兼ねていても省かない。ケース 2）→ 審査（`department_id` は**この時点の**種類の審査部門。D11・D18）→ 社長
5. 最初の待ちの段階に `arrived_at` を入れ、状態を部門長確認中か審査中にする。`last_submitted_at`（初回は `first_submitted_at` も）

**判断**（4.2 のとおり）

| 段階 | 操作できる人 | 選べるもの | コメント必須 | 結果 |
|---|---|---|---|---|
| 部門長 | その段階の担当（`assignee_user_id`、無ければ申請部門の**今の**部門長） | 承認 / 差戻し | 差戻し | 承認 → 審査の段階が届く・審査中 ／ 差戻し → その回の残りの段階を打ち切り・差戻し中 |
| 審査 | その段階の審査部門の**今の**審査担当者のうち誰か 1 人 | 可 / 保留 / 否 | 保留・否 | どれでも社長の段階が届く・社長決裁待ち（否でも止めない） |
| 社長 | **今の**社長 | 可 / 条可 / 差戻し / 否 | 条可（＝条件）・差戻し・否 | 可 → 番号・決裁済み ／ 条可 → 番号・条件確認待ち ／ 否 → 番号・否決 ／ 差戻し → 差戻し中（番号は付けない） |
| 条件確認 | 申請者本人 | 条件を確認しました | 任意 | 決裁済み（条可）・`completed_at` |

- **自分の申請には判断できない**（D16）: 部門長・審査・社長のどの段階でも、操作する人が申請者本人なら断る（理由を画面に出す。審査は、ほかの審査担当者が入れる。4.3 のケース 3）
- コメント（判断・条件確認・取り下げ）と、2b の管理者の操作の理由は 2,000 文字まで（技術上の上限）
- 判断を確定する前に確認のモーダル（「〇〇で確定しますか？」）を出す（4.2）
- **取り下げ**（申請者）: 部門長確認中・審査中・社長決裁待ち・差戻し中のとき。コメントは任意（D17）。待ちの段階を打ち切る。番号が付いていれば残る（6.5。台帳〈段階4〉で「取り下げ」の欠番として出す）
- **同時操作**（4.2）: 申請の行の `lock_version` を条件にした 1 回の UPDATE で状態を進め、当たらなければ（0 行）「すでに処理されています」と出して詳細の画面へ戻す。番号の採番も同じトランザクションの中で行う
- **交代**: 部門長の段階の担当は、付け替えが無ければ申請部門の今の部門長を引く（ケース 5・D23 は §5.4）。社長は今の社長を引く（ケース 6）。審査担当者はその時点の担当者が操作できる（ケース 7）
- 差戻し中は申請者が中身と添付を直せる（§5.6・§5.7）。出し直すと最初（部門長）から回り直す（4.4）

### 5.9 決裁No（6 章）

- 付けるのは社長が 可・条可・否 を選んだとき（6.3）。**すでに番号がある申請（2b の取り消しで戻った申請）は、その番号をそのまま使う**（6.5。年度をまたいでも同じ。D21）
- 形: `{和暦}-{アルファベット}-{連番 3 桁以上}`（例 `R8-J-001`。999 の次は `R8-J-1000`）
- 年度（`ApprovalFiscalYear`）: 社長が判断した日（日本時間）と、申請部門の会社の `fiscal_start_month` で決める（ミツワ 5 月・DAD／ZEAL 6 月。6.2）。年度の値は期の始まりの年（2026-05-01〜2027-04-30 → 2026）
- 和暦: 期の始まりの日が属する元号・年（6.1）。2019-05-01 以降は令和（`R` ＋ 年−2018）、それより前は平成（`H`。段階5 の過去分の取り込みで使う）
- 連番（`ApprovalNumber`）: `approval_number_sequences` の（部門・年度）の行を**ロックして**（`lockForUpdate`）採る。行が無ければ作る。`next_number` を使って 1 進め、`last_issued` に入れる。開始番号（§5.4）はこの行の `next_number` を設定する
- 申請には番号の文字列と、部門・年度・連番を分けて持つ（台帳の並び替えと、アルファベットを変えた後も発番したときの文字列を保つため）
- `JapanBusinessDayTest`（年度の式の全件分類）に `ApprovalFiscalYear` を分類して加える

### 5.10 見られる範囲（7 章・`RequestVisibility`）

| 見る人 | 見られる申請 |
|---|---|
| 申請者 | 自分の申請（下書きを含む） |
| 申請部門の**今の**部門長 | その部門のすべての申請（過去分を含む） |
| 審査部門の**今の**審査担当者 | その審査部門の審査の段階が一度でも届いた申請（D19） |
| **今の**社長 | 社長の段階が一度でも届いた申請（D19） |
| 付け替えられた部門長の担当（2b） | 付け替えられた段階が届いた申請 |
| 判断した人 | 自分が判断した申請（担当を外れた後も。前の回の判断を含む） |
| 全件閲覧者・決裁の管理者 | すべて |

- **他人の下書きは誰も見られない**（管理者・全件閲覧者も）。下書きは申請者だけ
- 添付・候補の検索（`approvals.numbers.search`）・（段階4）PDF・台帳・Excel に同じ範囲を効かせる
- 画面の判定（`canView`）と一覧の絞り込み（`scopeVisibleTo`）は同じ規則から作り、テストで両方が同じ結果になることを確かめる

### 5.11 記録（14.2）

- **操作の記録**（`approval_histories`）: 提出・出し直し・承認・差戻し・意見・決裁・条件確認・取り下げ・部門長の省略・部門長の交代による移動、（2b）取り消し・付け替え・代理の取り下げ。誰が・いつ・何を・どの状態からどの状態へ・コメント（理由）・IP・端末の情報
- **提出ごとの中身の控え**（`approval_revisions`）: 種類（id と名前）・申請部門（id と名前）・件名・金額・実施時期・本文・関連する決裁No・添付の一覧（id・名前・大きさ）。2b の変更点と履歴はこれを使う（段階5 で明細表の行と追加の入力欄を足す）
- 記録と控えは、画面にも仕組みにも変更・削除の手段を作らない（モデルで更新と削除を拒む。段階1 の `ApprovalSettingLog` と同じ）
- 決裁が確定した申請（決裁済み・否決・条件確認待ち）と、回覧中の申請の中身は変えられない（変えられるのは下書きと差戻し中だけ）
- ダウンロードの記録は §5.7

### 5.12 ホーム・詳細・自分の申請一覧（画面①③④）

**ホーム（①）**（使い始める前は「準備中」のまま。§5.2）
- **対応待ち**（古い順・待ち日数つき。D20）
  - 部門長として: 部門長の段階が待ちで、担当が自分（付け替え）か、担当が空で申請部門の部門長が自分
  - 審査担当者として: 審査の段階が待ちで、その審査部門の担当者に自分がいる
  - 社長として: 社長の段階が待ちで、自分が社長
  - 申請者として: 自分の申請が差戻し中・条件確認待ち
  - ⚠ 自分の申請は、部門長・審査・社長としての対応待ちには出さない（判断できないため。D16）。止まったままになった申請は、管理者が⑩（2b）で見つける
- **自分の申請の進み具合**: 回覧中・差戻し中・条件確認待ちの自分の申請（いま誰の番か）と、最近の完了。一覧（④）へのリンク
- 待ち日数: 段階の `arrived_at`（申請者の番は `status_changed_at`）の日本の日付から、日本の今日までの暦の日数

**詳細（③）**
- 申請の中身・添付（開く・ダウンロード）・関連する決裁No（見られる申請はリンク）
- **回る順番と各人の判断**: 段階ごとに担当（氏名）・届いた日時・判断・コメント・日時。省略した段階は「申請者が部門長のため省略」。データ印は段階4
- 操作の記録（新しい順）
- **操作ボタン**: `RequestPermissions` がその人にその時できると判定した操作だけを出す。押せないけれど役割のある人には理由を出す（例「自分の申請には判断できません」。`disabled` のボタンは `span` で包んで理由を付ける。Bug #43）
- 判断のモーダル: 選んだ判断・コメント（必須のものは必須と表示）・「〇〇で確定しますか？」

**自分の申請一覧（④）**
- 絞り込み: 下書き・進行中（部門長確認中・審査中・社長決裁待ち）・差戻し中・完了（条件確認待ち・決裁済み・否決）・取り下げ。即時の絞り込み（プロジェクトの規約）
- 新しい順に 20 件ずつ。列: 決裁No・件名・種類・状態・提出日・いま誰の番か
- スマホの幅では 1 件 1 枚のカード（14.4。横スクロールにしない）

**サイドバー**
- 決裁のみ利用者（`sidebar_approval`）: 使い始めたら「新しい申請」「自分の申請」を足す。決裁の管理者には「申請種類の管理」（使い始める前から）と、2b で「進行中の申請の管理」
- 基幹を使う人で決裁の管理者に指定された人: 基幹のサイドバー 3 か所の「決裁の管理」に「申請種類の管理」を足す（使い始める前から）
- Bug #56 の決まり（展開版に `x-cloak` を付けない）を守り、`LayoutSidebarCloakTest` の対象に入れる

### 5.13 変更点の色付き表示と履歴（2b・4.4）

- 出し直した申請（`round` が 2 以上）の詳細で、**直前の回の控えと今の回の控え**を比べて色付きで出す: 件名・金額・実施時期・関連する決裁No・種類・申請部門（変わったものだけ、前 → 後）／本文は行ごとの差（増えた行・消えた行）／添付は足したもの・外したもの
- 行ごとの差は自前の小さな部品で作る（`sebastian/diff` は開発用の依存で本番の vendor に無いため）
- **履歴**: 提出の回ごとに、その回の控え（中身・添付）と、その回の各段階の判断を開ける。外した添付も履歴から開ける（範囲の確認と記録は §5.7 と同じ）

### 5.14 進行中の申請の管理（2b・画面⑩・決裁の管理者）

- **一覧**: 状態が部門長確認中・審査中・社長決裁待ち・差戻し中・条件確認待ちの申請を、待ち日数の長い順に。列: 決裁No・件名・申請者・申請部門・状態・いま誰の番か・待ち日数。「担当が申請者本人」（D16 で止まっている）・「審査担当者が申請者本人しかいない」を印で出す
- **部門長の確認の付け替え**（D2）: 部門長確認中の申請だけ。付け替え先は有効でメールアドレスのある人で、申請者本人ではないこと。**理由は必須**（D22）。記録（前後の担当・理由）
- **押し間違いの取り消し**（4.7）: 対象は今の回の最後の操作（承認・差戻し・意見・決裁・条件確認）。提出・取り下げ・省略は対象外。理由は必須。取り消した操作の直前の状態へ戻し、その操作の段階を待ちに戻す（後ろの段階は「まだ届いていない」へ）。取り消した記録を残す（元の記録は消さない）
  - 続けて行えば 1 つずつさかのぼれる（提出の手前まで。D24）
  - 差戻しの取り消しは、差戻しのあと申請者が中身か添付を変えていたら断る（今の中身を最後の控えと比べる。D3）
  - 社長の判断の取り消しでは、番号を残し、`decided_at`・`completed_at` を空に戻す（6.5・D21）
- **代理の取り下げ**: 申請者の取り下げと同じ状態のとき。理由は必須。記録（代理であること・理由）
- 決裁の管理者でも、**自分が申請者の申請にはこの 3 つをできない**（D25）
- 同時操作の見張りは §5.8 と同じ

### 5.15 基幹のメニューとダッシュボード（2b・使い始めてから）

- 基幹のサイドバー 3 か所（展開・折りたたみ・スマホのドロワー）に「決裁」と対応待ちの件数（§5.12 の対応待ちの数）。決裁のみ利用者のサイドバーにも件数
- 基幹のダッシュボード（経営層・部門）に「決裁の対応待ち N 件」とホームへのリンク
- 件数は 1 リクエストに 1 回だけ数える（サイドバー 3 か所で数え直さない）
- ベルマーク（お知らせ）は段階3
