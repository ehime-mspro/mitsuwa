## 1. 背景と依頼

周辺ビル調査のテナント明細の取込（`importTenants()`）は、ファイルの行を 1 行ずつ `AreaBuildingTenant::create()` するだけで、
登録済みの行と突き合わせない。同じファイルを上げ直すと行が二重になり、取込の画面にも
「同じファイルを 2 回取り込むと行が二重になります（既存行との突合は行いません）」と注意書きを出している。

Bug #69（2026-09-28）で「同じ取込の画面から 2 回送る」は 1 回限りの鍵で止めたが、取込の画面を開き直してファイルを選び直すと
新しい鍵になるので、上げ直しは止まらない。契約の上げ直し（Bug #70。2026-09-29〜30）の設計書 §6 でも、
このテナント明細を範囲外に残していた。

二重の行は、現況テナント数と調査回の件数を突き合わせる乖離の警告（`AreaBuildingController::divergence()`）に嘘の数字を出させる。

利用者の依頼（2026-10-01）: 周辺ビルのテナント明細を上げ直したときの二重登録を止める。

対話で決まったこと（2026-10-01。質問 3 つ・設計の 2 節。どれも承認済み）:

| 論点 | 決定 |
|---|---|
| 上げ直す場面 | ①同じファイル／一部が重なるファイルの上げ直し ②別のビルのファイルの追加 の 2 つだけ。③調査し直して現況を置き換える（同期・退去の扱い・状態の更新）は範囲外 |
| 同じ行 | ビル・階・部屋番号・テナント名が同じ（案 1）。業種・状態は見ない |
| 登録済みの行 | 書き換えない（スキップするだけ。業種・状態・確認日・退去日・備考はそのまま）|
| 突き合わせる相手 | そのビルの現況の行と退去済みの行の両方（案 A）。同じ区画に同じテナントが入り直したときは画面から追加する |
| 判定の場所 | サーバだけ。完了のメッセージで知らせる（プレビューには出さない）|
| 比べ方 | 部屋番号とテナント名は `AreaBuilding::normalizeName` で正規化して比べる。空欄（階・部屋番号・テナント名）は空欄どうしだけが同じ |
| 削除したビル | 今どおり対象外 |
| 重なりの数 | キーごとに、登録済みの行の数まではスキップし、超えた分だけ入れる（数で扱う）。ファイルの中で同じ行が並んでもエラーにしない |
| 検査の順番 | ビル名が空 → 台帳に無いビル → 階が読めない（「値が不正」）→ 登録済みの照合 → 登録 |
| 完了のメッセージ | 「登録済みのためスキップ N 件」を足す |
| 現況テナント数 | スキップした行のビルも並べる（全部スキップしたときも出る）|
| 注意書き | 書き換える（§4.6）|
| コードの形・テスト・本番 | 設計 その 2（§4・§5・§8）|

## 2. 調査で分かった事実

読んだのは `13.x` = `b6e0fa49`（この worktree の分岐元）。行番号はこの時点のもの。特に断りの無いものはコードを読んで確かめた事実。

### 2.1 いまの取込の流れ（`importTenants()`。269〜341 行）

1. 行が配列でない → 「ビル名が空」に数える（281-284）
2. ビル名を `AreaBuilding::normalizeName()` で正規化し、空なら「ビル名が空」（286-290）
3. 台帳（`buildingMapByNormalizedName()`）に無いビル名 → 「台帳に無いビル」に行と名前を数える（293-297）
4. 階を `parseTenantFloor()` で読み、読めない・範囲外なら「値が不正」（300-304）
5. `AreaBuildingTenant::create()`（308-315）。書く列は `floor`・`room_number`・`name`・`industry`・`status` だけ
6. 完了のメッセージ（320-326）:
   「取込が完了しました。テナント登録 %d 件 / ビル名が空でスキップ %d 件 / 値が不正でスキップ %d 件 / 台帳に無いビルでスキップ %d 行」
   ＋台帳に無いビル名（328-330）＋「取込後の現況テナント数: …」（336-338。登録した行のビル＝`$touched` だけ）

- `buildingMapByNormalizedName()`（398-410）は削除済みのビルを含めず、同じキーは id の小さいほうを採る
- `nullableString()`（558-565）は `text()`（`trim()`。**半角の空白だけ**を落とす）のあと、空なら null、そうでなければ列の長さで切る
  （`room_number` 50・`name` 255・`industry` 100）
- `execute()` は入力チェックの前に `OneTimeAction::claimFrom($request, 'import_token')` を使う（93-96。Bug #69）
- 取込全体を 1 つのトランザクションで囲まない理由が、クラスの docblock（31-38）にある
- クラスの docblock（40-45）と 332-335 行のコメントが「突き合わせる手がかりが無い」「再取込は行を二重にする」と書いている

### 2.2 モデルとスキーマ

- `AreaBuildingTenant`（`app/Models/AreaBuildingTenant.php`）は**論理削除を持たない**。退去は `moved_out_on` を入れて履歴として残す。
  `floor` は `integer` キャスト（null 可）
- 列: `area_building_id`・`floor`（INT・null 可・地下は負数）・`room_number`（50・null 可）・`name`（255・null 可。空き区画は null）・
  `industry`・`status`・`confirmed_on`・`moved_out_on`・`notes`
- `AreaBuilding::normalizeName()`（156-164）: 全角空白（U+3000）を半角に寄せ、続く空白を 1 つにし、前後の空白を落とす。
  英数字の全角・半角や大文字・小文字は変えない。null は `''` になる
- 画面から 1 件ずつ登録するとき（`AreaBuildingTenantController`）は `room_number` max:50・`name` max:255 の入力チェックがある

### 2.3 階の 0

`FloorNumber::parse('0', true)` と `FloorNumber::parse('0F', true)` は 0 を返し（2026-10-01 実測）、範囲（-10〜200）にも入るので 0 として保存される。
空欄は null。**キーで空欄（null）と 0 を区別する必要がある**。

## 3. 方針

| 論点 | 採った案 | 理由 | 退けた案 |
|---|---|---|---|
| 同じ行の見分け方 | ビル・階・部屋番号・テナント名 | 業種・状態を直したファイルを上げ直しても二重にしない（契約の上げ直しの「どこ＋誰」と同じ考え方）| 業種・状態まで含める（直した値で上げ直すと二重になる）|
| 突き合わせる相手 | 現況＋退去済み | 古いファイルを上げ直しても、退去したテナントが現況に戻らない | 現況だけ（古いファイルの上げ直しで退去したテナントが現況に戻る）|
| 判定の場所 | サーバだけ・完了のメッセージで知らせる | ビル＋調査の「同一年月のためスキップ」と同じ形 | プレビューに出す（登録済みの行をブラウザへ渡す仕組みが要り、大きくなる）|
| 重なりの扱い | 数で扱う | 空き区画（階だけで部屋番号も名前も空欄）はファイルの中で並ぶのが普通 | あるかないかだけで見る（2 行目以降の空き区画が全部消える）／ファイルの中の重複をエラーにする（普通のファイルが通らない）|
| 作り方 | コントローラの中で先読みしてキーごとに数える | 新しいクラスが要らない。問い合わせは 1 本増えるだけ | DB の一意制約（空欄の列があり、空き区画は並ぶので制約にできない）／行ごとに `exists()`（2000 行で 2000 往復）|

### 4.2 見分けのキー

```php
// 形の見本（名前と細部は計画で決める）
private function tenantKey(int $buildingId, ?int $floor, ?string $roomNumber, ?string $name): string
{
    return json_encode([
        $buildingId,
        $floor,                                   // null（空欄）と 0 を区別する
        AreaBuilding::normalizeName($roomNumber), // null と「空白だけ」はどちらも ''
        AreaBuilding::normalizeName($name),
    ], JSON_THROW_ON_ERROR);
}
```

- **区切り文字でつながず JSON にする。** `|` などでつなぐと、部屋番号や名前に区切り文字が入ったとき、別の行が同じキーになりうる。
  JSON なら階の null と 0 も区別できる（§2.3）。値はどれも正しい UTF-8（ファイルの行は `json_decode` を通っており、DB は utf8mb4）なので、
  `JSON_THROW_ON_ERROR` は通常の操作では投げない
- **ファイル側の値は、保存するときと同じ切り方（`nullableString()`。部屋番号 50・名前 255）にしてから正規化する。**
  登録済みの行は保存された値を正規化する。1 回目に入った長い値と、同じファイルの上げ直しの値が同じキーになる
- 正規化の結果として:
  - 全角空白・続く空白・前後の空白の違いは同じとみなす
  - 英数字の全角・半角と、英字の大文字・小文字は区別する（ビル名の突き合わせと同じ扱い）
  - null と「空白だけ」（例: 全角空白 1 つ）の値は、どちらも空欄として同じとみなす
  - 255 文字を超える名前は、切ったあとの 255 文字で比べる（保存される値が同じなので、同じ行とみなす）
- 業種・状態・確認日・退去日・備考は見ない

### 4.3 先読み

- 行を処理する前に、ファイルの行に出てくるビルのうち台帳で見つかったものの id を集める（行を一度なめる。判定は §2.1 の 1〜3 と同じ）
- そのビルのテナント明細を **1 本の問い合わせ**で読む。読む列は `area_building_id`・`floor`・`room_number`・`name` だけ。
  **退去済みの行も含める**（`moved_out_on` は問わない。論理削除は無いので `withTrashed()` は関係しない）
- キーごとの「残りの数」（`array<string, int>`）を作る。同じキーの行が登録済みに 2 行あれば 2
- 対象のビルが 1 棟も無ければ問い合わせを投げない

### 4.4 行の検査の順番（新しい）

1. 行が配列でない／ビル名が空 → 「ビル名が空」（今どおり）
2. 台帳に無いビル → 「台帳に無いビル」（今どおり）
3. 階が読めない・範囲外 → 「値が不正」（今どおり。**照合より前**）
4. 部屋番号・テナント名を `nullableString()` で整え、キーを作る
5. 残りが 1 以上 → 「登録済みのためスキップ」に数え、残りを 1 減らし、ビルを `$touched` に入れて次の行へ（書き込まない）
6. 残りが 0 → 今どおり `create()` して「テナント登録」に数え、ビルを `$touched` に入れる

- **この取込で入れた行は、残りに足さない。** ファイルの中で同じ行が並べば、登録済みの数を超えた分はすべて入る
  （例: 登録済みに「3 階・部屋番号なし・名前なし」が 1 行・ファイルに 2 行 → 1 行目はスキップ・2 行目は登録）
- 登録する行の値（`nullableString()` の結果）は、キーを作るのに使った値と同じものを使う（2 回切らない）

### 4.5 完了のメッセージと現況テナント数

- メッセージ: 「取込が完了しました。テナント登録 %d 件 / 登録済みのためスキップ %d 件 / ビル名が空でスキップ %d 件 / 値が不正でスキップ %d 件 / 台帳に無いビルでスキップ %d 行」
  （2 番目に足す。既存のテストは部分一致で見ているので崩れない）
- 台帳に無いビル名の並び（`（N 棟: …）`）は今どおり
- **現況テナント数（「取込後の現況テナント数: …」）には、スキップした行のビルも並べる。**
  全部がスキップされたときも「アルファビル 3 件」と出るので、件数が増えていないことがその場で分かる。数え方（`moved_out_on` が null の行）は今どおり

### 4.6 取込の画面の注意書き

> テナント明細は、台帳に既にあるビル名の行だけを取り込みます。台帳に無いビルは作成しません。登録済みと同じ行（ビル・階・部屋番号・テナント名が同じ。退去済みの行も含む）は取り込まずにスキップします。業種・状態が違っても書き換えないので、直すときは詳細画面から直してください。取込後に表示される件数と現況テナント数を確認してください。

## 6. やらないこと（BACKLOG に書く）

- ③調査し直して現況を置き換える（ファイルに無い行を退去にする・状態を更新する同期）
- プレビューにスキップの見込みを出すこと（登録済みの行をブラウザへ渡す仕組みが要る）
- 本番に今ある二重の行の片づけ（数で扱うので照合は壊れない。本番の数は反映の前に数える。§8）
- 画面から 1 件ずつ登録するときの重複の確かめ
- 2 つのタブでほぼ同時に取り込むこと（照合は読むだけで一意制約が無いので、両方が照合を通りうる。順に届けば 2 つ目はスキップ）
- 同じ区画に同じテナントが入り直したとき（退去済みの行と同じキーになるのでスキップする。画面から追加する）
- 英数字の全角・半角や大文字・小文字の表記ゆれを同じとみなすこと（ビル名の突き合わせと同じく区別する）

## 7. ついでに見つかったこと（直さない）

- 読み取り: `nullableString()` は `trim()`（半角の空白だけ）なので、全角空白だけのセルは null ではなく `'　'` のまま保存される
  （名前・部屋番号・業種）。照合では `normalizeName()` が空欄と同じに扱うので、この設計の判定には影響しない
- 読み取り: 取込のプレビュー（JS）はサーバの登録済みの行を見ないので、上げ直しでも「取り込める行」に数える。
  スキップは完了のメッセージで初めて分かる（§6 のとおり、プレビューには出さない）
