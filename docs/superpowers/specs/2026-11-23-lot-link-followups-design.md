# 契約済みの建売の削除で区画を戻す ／ 区画を足すときつなぐ変更の残り（短い設計）

日付: 2026-11-23
きっかけ: Bug #146（区画を足すとき、区画を選んでいない契約などをその区画につなぐ）の範囲外・後回しに残したもの。利用者の依頼「A と B を一緒に進めて」（2026-11-23）
関連: docs/superpowers/specs/2026-11-22-lot-link-on-add-design.md・docs/RULES.md の Bug #142・#146

## 何をなぜ直すか

| # | 今 | 困ること |
|---|---|---|
| A | 契約のある建売を削除すると、契約はデータベースの連鎖削除で消え、区画を販売中に戻す処理（`Housing\ContractController::destroy` の `updateLotStatusOnUnsold()`）が動かない。土地の区画も分譲地の区画も「成約」のまま残る | 土地は区画から集約して「販売済」のまま＝契約の登録画面の選択肢から消える。分譲地もステータスの集約がずれる。直すには区画の表で手で「販売中」に戻すしかない。Bug #146 で区画につながる建売が増えたので当たりやすい |
| B1 | 区画を足すとき、2 人がほぼ同時に同じ候補を選ぶと、後の保存が持ち主の区画を上書きし、先の区画が「成約・紐付けなし」で残る | A と同じく、空いていない区画が残る |
| B2 | 追加のフォームの候補の指紋（`ProcurementLotLinks::fingerprint()`）が候補のキーだけで、建売に契約が付いたかを含まない | 画面は「（区画は販売中）」と出したのに、保存すると「成約」になる（保存の値は正しい） |
| B3 | 区画を足して何かをつないだ直後に、その前から開いていた編集画面から保存すると断られる。文が「土地の紐付けは変えられません」「区画を選んでください」（選ぶ欄の無い画面で）で、利用者は何もしていない | 理由が分からない（開き直せば保存できる。データは壊れない） |
| B4 | 開いたあとで候補が 0 件になった土地から送ると、顔ぶれの断りに「ステータスは必須です。」が並ぶ | 開いた画面にステータスの欄が無いので意味が通らない |

## 決めたこと

- B3 は利用者の決定（2026-11-23・案 1）: **土地を変えられない画面**（建売の編集・契約済みの注文住宅の編集・契約一覧から開く契約済みの注文住宅の契約の編集）は、区画が空で届いても**紐づいている区画を残して保存を通す**。区画を選べる**不動産の契約の編集**は、理由の分かる文で断る
- A は分譲地の区画も直す（こちらの判断。同じ処理の抜けで、建売の契約の削除は両方を戻している）

## Approaches

| 件 | 考えた形 | 採ったもの |
|---|---|---|
| A | ①建売の削除の処理で、注文住宅の削除（`CustomOrderController::releaseLot()`）と同じく「契約があれば区画を販売中に戻す」 ②モデルの削除のフックで戻す | **①**（注文住宅の削除と同じ形。フックにすると、テストのデータの掃除などで黙って動く） |
| B1 | ①つなぐ書き込みを「まだ区画が空で、同じ土地のまま」に絞り、0 行なら区画の作成ごと取り消して断る ②候補を引くときに行をロックする | **①**（Bug #146 でロックは足さないと決めた。①なら MySQL の更新が先の書き込みを待ってから 0 行になり、閉じる） |
| B2 | ①指紋に区画のステータスも入れる ②画面の「（区画は販売中）」を出さない | **①**（画面の表示どおりに保存されるようにする） |
| B3 | ①土地を変えられない画面は区画を残して通す ②どの画面も断り文を変える ③今のまま | **①**（利用者の決定） |
| B4 | ①顔ぶれが変わったときはステータスの誤りを出さない ②顔ぶれの判定を入力チェックより前にする | **①**（今の入力チェックの形のまま 1 行で済む） |

## 中身

**A** 建売を削除するとき、契約があれば、その建売の土地の区画（`ReProcurementLot::markOnSale()`）と分譲地の区画（販売中にして分譲地のステータスを集約）を戻す。契約の削除（`ContractController::destroy`）と同じ処理を 1 か所にまとめて両方から呼ぶ。区画を戻すことと削除は 1 つのトランザクション。契約の無い建売の削除は今のまま（区画のステータスは動かさない）。

**B1** `ProcurementLotLinks::link()` の書き込みに「持ち主の区画の列が空」「持ち主の土地がその区画の土地」（住宅事業は種別が仕入れ案件）を足し、書いた行の数を返す。区画の追加（`ProcurementLotController::store()`）は 0 行なら区画の作成を取り消し、今の `LINK_STALE` の文で入力エラーにする（打った値は残り、戻った画面には今の候補が出る）。

**B2** 指紋を「キー=ステータスの値」をつないだ形にする（例 `property:3=on_sale`）。登録のときの比べ方は今のまま（違えば `LINK_STALE`）。⚠ 反映の前に開いていた追加のフォームは、指紋の形が違うので 1 回だけ断られる（開き直せば登録できる）。

**B3**
- 建売の編集・注文住宅の 2 つの編集（契約済みのとき）: 保存の前に、送られた区画が空で、送られた種別が仕入れ案件・送られた仕入れ案件が保存済みと同じ・保存済みの区画がある、のときだけ、送られた区画を保存済みの区画とみなす。そのあとの入力チェック（区画の必須・土地の紐付けの固定・区画を取る判定・土地原価）は今のまま
- 不動産の契約の編集: 同じ形（区画が空・仕入れ案件が保存済みと同じ・保存済みの区画がある）で必須に断られたときだけ、文を「区画を選んでください。この契約は今、区画（1号地）に紐づいています（画面を開いたあとで紐づけられた可能性があります）。」にする
- 見積り以前の注文住宅の編集は区画を選べる画面なので、今のまま（区画を空にすると必須で断る）

**B4** 顔ぶれが変わって `LINK_STALE` を出すときは、ステータスの誤りも消す（開いた画面にステータスの欄が無かったため）。

## 目標でないこと

- 区画の行の編集でつなぐこと・つないだときに土地原価を計算し直すこと（Bug #146 の決まり 6 のまま）
- 不動産の契約の編集で区画を自動で残すこと（区画を選べる画面なので、残すか空にするかを推し量らない）
- 本番のデータを書き換えること（本番に契約済みの建売の削除で残った成約の区画があるかは、反映の前の読み取りで数える）

## 作る人に任せること

- A の処理を置く場所（モデルのメソッドか、今のコントローラの私的メソッドを共用にするか）
- B3 の「保存済みの区画とみなす」を置く場所（trait `LocksLandAfterContract` か `ProcurementLotClaims`）
- テストの形（画面が描いたフォームを分解して送る往復・同時の保存は `DB::listen` などで書き込みの間に挟む）
