# テナント管理 一覧の並び替え — 設計書

作成日: 2026-08-25
対象: `/tenant/properties`（物件一覧）/ `/tenant/units`（部屋一覧）
モック: @docs/mockups/tenant/list-sorting.html

---

## 1. 背景と依頼

利用者からの依頼はこう:

> テナント管理の「物件一覧」「部屋一覧」のテーブルをソートできるようにしたいです。
> 並び替え希望の項目は「物件一覧」は"入居率・賃料収入"「部屋一覧」は"面積・家賃・月額合計"です。

**アプリ内に列見出しで並び替える実装は現在ひとつも無い。** 本件が最初の 1 本になるので、
ここで決めた形（URL 仕様・3 状態・「—」の位置・共通部品）が以後の一覧の前例になる。

## 2. 調査で分かった事実（2026-08-25 実測）

| | 物件一覧 `/tenant/properties` | 部屋一覧 `/tenant/units` |
|---|---|---|
| 件数（ローカル実測） | **16 件**（1 ページ） | **156 件**（8 ページ） |
| ページあたり | 20 件 | 20 件 |
| 希望列の実体 | 入居率・賃料収入とも **PHP で算出**（`PropertyController::calculatePropertyStats`、現状 354-380 行）。DB 列ではない | 面積・家賃は **DB 列**、月額合計は `Unit::getMonthlyTotalAttribute()`（現状 130 行）＝ 4 列の合計 |
| 既定の並び順 | `operation_status` 昇順（稼働が先）→ `code` 昇順 | `property_id` → `floor` → `room_number` |

### 2.1 実データの分布（同点がどれだけあるか）

**同点の行は実データに大量にある。** 第 2 キー（既定順）の指定は飾りではなく、無いとページ送りが壊れる（§4.3-3）。

| 対象 | 同点グループに属する行 |
|---|---|
| 物件一覧 入居率 / 賃料収入 | 16 件中 **14 件**が `0.0%` かつ `0円`（稼働 15・非稼働 1 のうち、稼働 14 件が全て 0） |
| 部屋一覧 家賃 | 156 件中 **103 件**（重複値 37 種） |
| 部屋一覧 面積 | 156 件中 **74 件**（重複値 24 種） |
| 部屋一覧 月額合計 | 156 件中 **65 件** |

### 2.2 NULL の実情とスキーマ

- `units.area_tsubo` … `decimal(8,2)` **nullable**。実データの NULL は **0 件**、`0` も **0 件**
- `units.rent` / `common_fee` / `garbage_fee` / `pest_control_fee` … `int` **nullable**（既定値 `0`）。実データの NULL は **0 件**
- 物件側の `occupancy_rate` / `rental_income` は DB 列ではなく、`calculatePropertyStats()` が
  **非稼働のときだけ `null`** を入れる。稼働なら坪数 0 でも `0` が入る（`null` にはならない）

⚠ **NULL は現在どの列にも 1 件も無い。** テストで意図的に作らないと NULL 経路は空振りして緑になる（§6.2-5）。

### 2.3 その他の実測

- `ORDER BY (col IS NULL) ASC, col DESC` は **MySQL と SQLite で同じ挙動**（NULL が両方向とも末尾）。
  実測（`(1,100) (2,NULL) (3,50) (4,NULL) (5,100)` を両エンジンで）:
  ```
  desc: 100 100 50 NULL NULL
  asc :  50 100 100 NULL NULL
  ```
- `Unit::$area_tsubo` は `decimal:2` キャストのため **PHP には文字列で返る**（`'32.33'`）。
  PHP 8 は数値文字列どうしを数値比較するので動くが、暗黙の挙動に頼る形になる ＝ **並べ替えは SQL 側でやる理由のひとつ**
- `Illuminate\Support\Arr::query(['a' => null, 'b' => '', 'c' => 'x'])` は **`b=&c=x`** を返す
  ＝ **null のキーは丸ごと消える**（Bug #31 の再確認。§5.2 の `url()` がこれを踏む）
- `number_format(null)` は **`'0'`** を返す（PHP 8.3 では Deprecated 警告つき）。§4.4 の前提
- `$sort` という変数名は `resources/views/tenant/` と `app/Http/Controllers/Tenant/` のどこでも未使用 ＝ 衝突なし（Bug #53）
- `tests/Concerns/ParsesForms.php` に `parseForm($html, $needle): [method, action, fields]` がある（往復テスト用）
- `app/Support/` に Support クラスの前例が多数ある（`VacancyRate` `TsuboPrice` `CsvDate` `FloorNumber` など）
- 両ビューとも `id="filter-form"` のフィルターフォームと、インライン番号付きページネーション
  （`hasPages` / `getUrlRange` / `nextPageUrl`）を持つ。`->links()` は使っていない（Bug #24 以来の規約）

## 3. 方式の決定

### 3.1 却下: クライアント側（JS）で表を並べ替える

部屋一覧は 156 件・8 ページあるため、「家賃が高い順」にしても **1 ページ目の 20 件の中で**並ぶだけで、
全 156 件の最高額は出てこない。**表示は正常に見えて答えだけが間違う**最悪の壊れ方をする。

物件一覧も今は 16 件（1 ページ）なので動いて見えるが、**21 件目を登録した瞬間に同じ壊れ方**をする。

### 3.2 採用: サーバ側で全件を並べ替えてからページを切る

画面ごとに素直な方をとる。

| 画面 | 方式 | 理由 |
|---|---|---|
| 物件一覧 | **全件取得 → PHP で計算 → PHP で並べ替え → 手動ページング** | 入居率・賃料収入は PHP にしか計算がない。SQL に写すと二重実装になり、「表示は正しいのに並び順だけ違う」という**画面から気づけない**食い違いを生む（Bug #41 / #46 の型）。物件は実在の建物なので件数の上限が現実的に小さい（現在 16 件） |
| 部屋一覧 | **SQL の `ORDER BY`** | 面積・家賃は生の列そのもの。`area_tsubo` の `decimal:2` 文字列問題（§2.3）も避けられる |

**利用者から見た動き（URL・矢印・「—」の位置・フィルタ併用）は 2 画面で完全に同一にする。**
共通化するのは**ヘッダー部品と並び替えパラメータの解釈**であって、並べ替えの実行方法ではない。

## 4. 設計① 画面の挙動

### 4.1 URL 仕様

```
/tenant/properties?sort=occupancy&dir=desc
/tenant/units?sort=monthly&dir=asc&property_ids[]=3&status=vacant
```

| 画面 | `sort` に取る値 |
|---|---|
| 物件一覧 | `occupancy`（入居率）/ `income`（賃料収入） |
| 部屋一覧 | `area`（面積）/ `rent`（家賃）/ `monthly`（月額合計） |

`dir` は `asc` / `desc` のみ。
**許可リストに無い値・不正な値はエラーにせず既定の並び順に落とす**
（`?sort=<script>` のような手入力や古いブックマークで 500 にしない）。

### 4.2 ヘッダークリックの 3 状態

```
（既定） → 1回目: 降順 ▼ → 2回目: 昇順 ▲ → 3回目: 既定に戻る
```

- **1 回目は降順**（金額と率なので「多い順」を先に見たい）
- 並び替え中の列は矢印を濃い緑、並び替え可能だが未使用の列は薄い上下矢印（⇅）、
  **並び替え不可の列には矢印を出さない**
- `<th>` に `aria-sort="ascending | descending | none"`

### 4.3 5 つの約束ごと

1. **既定の並び順は現状のまま。** `sort` 指定が無ければ今と 1 行も変わらない
2. **「—」は常に末尾。** 昇順でも降順でも、非稼働物件（入居率・賃料収入が「—」）と
   面積未入力の部屋を下にまとめる。末尾の中は既定順。⚠ **どの列が「—」を出すかは列ごとに違う** → §4.4
3. **同点の行は既定順で並べる。** §2.1 のとおり同点は実データに大量にあり
   （物件は 16 件中 14 件、部屋の家賃は 156 件中 103 件）、これが無いと
   **ページをまたいだときに同じ行が 2 ページに出たり、どのページにも出なくなったりする**
4. **並び替えとフィルタは共存する。** 絞り込んだ結果の中で並び替わり、ページを送っても両方維持される。
   逆方向も塞ぐ — **並び替え中にフィルタを変えても並び順が消えない**よう、
   フィルターフォーム（`id="filter-form"`）に `sort` / `dir` を hidden で持たせる。
   「クリア」ボタンは従来どおり全部（フィルタ＋並び順）を初期化する
5. **ヘッダーを押したら 1 ページ目に戻る**（リンクから `page` を落とす）

### 4.4 「—」の扱いは列ごとに違う（並び順は画面表示に合わせる）

⚠ **これは「NULL は常に末尾」という単純な規則ではない。**
同じ NULL でも、列によって画面に出る文字が違うため、揃えるべき相手は **NULL ではなく画面の表示**になる。
ここを取り違えると「画面は 0円 と出ているのに、その行だけ末尾に飛ぶ」という
**まさに本設計が避けたい種類の食い違い**（Bug #41 / #46）を自分で作ることになる。

| 列 | ビューの描画 | NULL のときの画面 | 並べ方 |
|---|---|---|---|
| 物件 入居率 / 賃料収入 | `@if($property->occupancy_rate !== null)` … `@else —` | **`—`** | **末尾へ**（非稼働だけが null。§2.2） |
| 部屋 面積 | `@if($unit->area_tsubo)` … `@else —` | **`—`** | **末尾へ** |
| 部屋 家賃 | `{{ number_format($unit->rent) }}円` | **`0円`**（`number_format(null)` は `'0'`） | **`0` として並べる**（末尾に飛ばさない） |
| 部屋 月額合計 | `{{ number_format($unit->monthly_total) }}円` | **`0円`**（アクセサが `?? 0`） | **`0` として並べる**（SQL 側も `COALESCE` 済みで NULL になりえない） |

したがって:

- 面積のみ `(units.area_tsubo IS NULL) asc` を前置する
- 家賃は **`COALESCE(units.rent, 0)`** で並べる（null 判定句は**付けない**）
- 月額合計は `MONTHLY_TOTAL_SQL` が `COALESCE` 済みなので **NULL になりえない**
  → null 判定句を書くと**常に false の死んだ SQL** になる。書かない

⚠ **当初「既知の穴」と書いていたが、実測すると穴ではなかった**（2026-08-26 訂正）。
`area_tsubo` は `decimal:2` キャストなので `0` は**文字列 `'0.00'` で返る**（§2.3 の実測どおり）。
PHP で falsy な文字列は `''` と `'0'` だけなので **`'0.00'` は truthy** ＝
`@if($unit->area_tsubo)` は実質 `!== null` と等価で、画面には `—` ではなく **`0.00坪`** と出る。
実測:

```
area_tsubo = '0.00' (string)  truthy=YES  → 画面「0.00坪」
```

つまり **`(units.area_tsubo IS NULL)` はビューの `@if` と完全に一致している**。
`0` を 0 として並べるのは表示と整合しており、直すべきものは何も無い。
⚠ **ここを「0 も末尾へ」に変えると、逆に表示と食い違う。**
テスト `test_a_zero_area_is_not_pushed_to_the_end` はその意図を固定するために残す。

### 4.5 モック

`docs/mockups/tenant/list-sorting.html`（ユーザー承認済み）。
実配色で 2 画面を再現し、ヘッダーを実際に押して 3 状態・「—」末尾・同点の既定順を試せる。
ブラウザ実測で **3 状態 / `aria-sort` / 「—」両方向末尾 / 同点の既定順** の 4 点を確認済み。

⚠ モック内の JS は表示デモ専用（`innerHTML` を使う）。
**本実装は Blade のエスケープ経由で描画し、JS は 1 行も足さない**（§5.1）。

⚠ **モックの `sortRows()` を並べ替え規則の正本として読まないこと。**
モックは `r[key] === null` を**列によらず一律で末尾**へ回す。
モックのデータでは `area` にしか `null` が無い（家賃は `0` であって `null` ではない）ため
画面上は正しく見えるが、この規則をそのまま写すと**家賃の NULL を末尾へ飛ばして §4.4 に反する**。
**並べ替え規則の正本は §4.4**、モックが示すのは**見た目と操作感**（3 状態・矢印・`aria-sort`・
「—」が末尾に見えること・同点が既定順に見えること）である。

### 5.2 `ListSort` の API

```php
/** @param list<string> $allowed この画面で並び替えを許すキー */
public static function fromRequest(Request $request, array $allowed): ?self
{
    $key = $request->query('sort');
    if (! is_string($key) || ! in_array($key, $allowed, true)) {
        return null;                      // 不正・未知・未指定 → 既定順（500 にしない）
    }
    $dir = $request->query('dir') === self::ASC ? self::ASC : self::DESC;

    return new self($key, $dir);
}

/** その列を今押したときの次の向き。3 巡目は null ＝ 並び替え解除 */
public static function next(?self $current, string $key): ?string
{
    if ($current === null || $current->key !== $key) { return self::DESC; }

    return $current->isAscending() ? null : self::ASC;
}
```

他に `->key` / `->direction` / `->isAscending()` /
`stateOf(?self $current, string $key): ?string` /
`url(Request $request, string $key, ?self $current): string`。

⚠ `is_string()` ガードは**飾りではない**。`?sort[]=a` と書かれると `query('sort')` は**配列**を返し、
`in_array()` は通らないにせよ型宣言や後段の文字列操作で落ちうる。ガードで早期に null へ落とす。

`url()` の要点 2 つ:

- **`page` を必ず落とす**（並べ替えた直後に 5 ページ目に居ないため。§4.3-5）
- **null を `''` に正規化してから `Arr::query()` に渡す。** 怠ると `?operation_status=` のような
  空の絞り込みがリンクから丸ごと消える（§2.3 の実測どおり `Arr::query()` は null のキーを捨てる。**Bug #31**）

### 5.3 物件一覧（PHP で並べる）

```php
$sort = ListSort::fromRequest($request, ['occupancy', 'income']);

// …既存のフィルタはそのまま…

$all = $query->orderBy('operation_status')->orderBy('code')->get();   // 既定順で全件

foreach ($all as $property) {
    $this->calculatePropertyStats($property);       // 計算はここ 1 箇所のまま
}

$properties = $this->paginateCollection(
    $request, $sort ? $this->sortProperties($all, $sort) : $all, 20
)->withQueryString();
```

- `calculatePropertyStats()` は**非稼働物件にだけ `null`** を入れる（稼働は坪数 0 でも `0`）。
  したがって **値を持つ行＝稼働中・「—」の行＝非稼働**にきれいに分かれ、
  「—」を末尾に回す処理が現在の「稼働が先」という既定順とも矛盾しない
- 同点の第 2 キーに **`code` を明示指定する**（PHP のソートが安定であることに暗黙に頼らない）
- ページングは `LengthAwarePaginator` を手で組む。既存ビューのインライン番号付きページネーション
  （`getUrlRange` / `nextPageUrl` / `hasPages`）はそのまま動く。**`->links()` には戻さない**（Bug #24 以来の規約）
- eager load（`units` / `contracts`）は現状のまま維持する ＝ 全件取得してもクエリ本数は増えない（§6.1-9 で固定）

### 5.4 部屋一覧（SQL で並べる）

§4.4 のとおり、**列ごとに「NULL を末尾へ回すか」が違う**ので、式と一緒に判断も返す。

```php
// 許可リストを通った値しか来ないので match の結果は必ずコード内の定数。
// 利用者の入力が SQL に混ざる経路は無い。
[$expression, $nullsLast] = match ($sort->key) {
    'area'    => ['units.area_tsubo',        true],   // NULL は画面で「—」    → 末尾へ
    'rent'    => ['COALESCE(units.rent, 0)', false],  // NULL は画面で「0円」  → 0 として並べる
    'monthly' => [Unit::MONTHLY_TOTAL_SQL,   false],  // COALESCE 済みで NULL になりえない
};

if ($nullsLast) {
    $query->orderByRaw("({$expression} IS NULL) asc");     // 「—」は常に末尾
}
$query->orderByRaw($expression . ' ' . ($sort->isAscending() ? 'asc' : 'desc'));

// 既定順を必ず最後に付ける ＝ 同点でもページをまたいで行が重複・消失しない
$query->orderBy('units.property_id')->orderBy('units.floor')->orderBy('units.room_number');
```

### 5.5 唯一の二重実装と、その塞ぎ方

月額合計だけは PHP（`getMonthlyTotalAttribute()`）と SQL の 2 つになる。**Bug #41 そのもの**なので 2 段で塞ぐ。

1. SQL 式を `Unit` モデルの定数にし、**PHP アクセサの真横に置く**（離れた場所に書かない）

```php
/**
 * 月額合計の SQL 式。下の getMonthlyTotalAttribute() と同じ計算をする。
 * ⚠ 片方だけ直すと、画面の数字は正しいのに並び順だけが別の値で並ぶ（画面から気づけない）。
 */
public const MONTHLY_TOTAL_SQL = '(COALESCE(units.rent,0) + COALESCE(units.common_fee,0)
                                 + COALESCE(units.garbage_fee,0) + COALESCE(units.pest_control_fee,0))';
```

2. 両者が一致することをテストで固定する（§6.1-6）

### 5.6 見出しコンポーネントの注意点

- **属性に `&quot;` を書かない**（**Bug #21**: 本番の `view:cache` でだけ 500 になる）。
  渡すのは `column="monthly"` `label="月額合計"` `:sort="$sort"` のような素の値だけ
- パディングを `<th>` から中の `<a>` へ移す。**見出しセル全体を押せるようにするため**で、
  これをやらないと文字の上しか反応しない（§6.5-1 で目視確認）
- 並び替え不可の列には矢印を出さない
- **`<a>` の中は「ラベル → 矢印」の順にする**（リンクを取り出すテストの正規表現がそれを前提にする）
- `<th>` に `aria-sort`
- ビューに渡す変数名は `$sort`（Blade 予約変数と衝突しないことを §2.3 で確認済み。**Bug #53**）
- 既存の `<th>` は物件一覧が Tailwind クラス、部屋一覧が inline `style` と**流儀が違う**。
  コンポーネントは**中身（リンク・矢印）だけ**を持ち、`<th>` 側の見た目は
  呼び出し元の既存指定をそのまま渡せる形にする（意匠を今回のついでに揃えない）

## 6. 設計③ テスト方針

### 6.1 想定する壊れ方と、それを捕まえるテスト

| # | 壊れ方 | 捕まえる方法 |
|---|---|---|
| 1 | **1 ページ目の中だけで並んでいる**（＝ JS 案と同じ壊れ方） | 物件を 25 件作り、**2 ページ目に 1 ページ目より大きい値が現れない**ことを検証。**ここが中心** |

### 6.2 特に注意して書くところ

1. **「全件を通して正しい」は 1 ページ目だけでは測れない。** 1 ページ目の 20 件が降順に並ぶことは
   JS 案でも成立する。**2 ページ目まで辿って初めて差が出る。** #1 #2 は必ず複数ページになるデータで書く
2. **ページ送りの URL を自分で組み立てない。** `?sort=rent&dir=desc&page=2` と手で書くと、
   **リンクが壊れていても sort が付いた状態で届くので必ず緑**になる。
   `$paginator->nextPageUrl()` を実際に辿る（**Bug #31**）
3. **SQL 式のテストは「0 になっていないこと」も見る。** テストの SQLite は綴りを間違えたカラム参照を
   **例外なく 0 で返す**ので（**Bug #40**）、式を全部壊しても
   「全行 0 → 全部同点 → 既定順 → PHP 側と一致」で**緑になりえる**。
   金額に分散があるデータを使い、値そのものも突き合わせる
4. **hidden の存在確認だけでは足りない。** `tests/Concerns/ParsesForms.php` の `parseForm()` で解析し、
   **そのまま送り返す**（**Bug #47** の方式）
5. **NULL の行はテストで作る。** 実データには面積・家賃とも NULL が **0 件**なので（§2.2）、
   作らないと #3 #3' が空振りして緑になる
6. **#3 と #3' は必ず別々のテストにする。** どちらも「NULL を含む部屋一覧を並べる」だけに見えるが、
   期待する位置が**正反対**（面積は末尾・家賃は先頭側）。1 本にまとめると
   片方の実装を壊しても文言が曖昧なまま緑になりうる（Bug #43 / #46 / #49 と同型）

## 10. 自己レビューで直した点（2026-08-25、承認後の清書時）

承認済みの設計を清書するにあたりコードと実データに当て直したところ、**3 点が実装と食い違っていた**。
いずれも**方針は変えず、根拠と条件だけを実測に合わせた**。

| # | 承認時の記述 | 実測 | 直した内容 |
|---|---|---|---|
| 1 | 同点ルールの理由を「**家賃 0 円の部屋が多数あるため**」としていた | `units.rent = 0` は **0 件**。同点は別の形で大量に存在（物件は 16 件中 **14 件**が 0.0% / 0円、部屋の家賃は 156 件中 **103 件**が同点グループ） | ルールは維持。理由を §2.1 の実測に差し替え |
| 2 | 「**「—」は常に末尾**」を全列に一律で適用する書き方だった | `units.rent` は **nullable** だが、ビューは `number_format(null)` で **`0円`** と描画する（`—` ではない） | §4.4 を新設。**揃える相手は NULL ではなく画面表示**と定義し、家賃は `COALESCE(units.rent, 0)`、面積のみ null 末尾に。テスト #3'・変異 1 通りを追加 |
| 3 | 部屋一覧の SQL に **全列共通で `(col IS NULL) asc`** を前置していた | `MONTHLY_TOTAL_SQL` は `COALESCE` 済みで **NULL になりえない** | 月額合計には null 判定句を付けない（常に false の死んだ SQL を書かない）。§5.4 を式と判定のペアを返す形に |

あわせて、承認済みモックの `sortRows()` が `null` を**列によらず一律で末尾**へ回す実装になっており、
上記 #2 と食い違うことが分かった。**モックは見た目と操作感の正本、並べ替え規則の正本は §4.4** と
役割を明記して両立させた（モックのデータでは家賃が `0` であって `null` ではないため、
画面上はどちらの規則でも同じに見える ＝ **モックを動かしても気づけない**種類の食い違いだった）。

⚠ **2026-08-26 追記 — 清書時に「既知の穴」として記録した 4 点目は、実測すると穴ではなかった。**
`area_tsubo = 0` が画面で `—` になると書いたが、`decimal:2` キャストにより `0` は
文字列 `'0.00'` ＝ **truthy** なので、実際には `0.00坪` と出る（§4.4 に実測を記載）。
**同じ設計書の §2.3 が「`decimal:2` は文字列で返る」と実測していながら、§4.4 でその実測を
自分に適用し忘れた**という自己矛盾だった。テスト #10 は「0 が 0 として並ぶ」＝
表示と整合することを固定するものとして残す（意味が変わっただけで、テスト自体は正しい）。
