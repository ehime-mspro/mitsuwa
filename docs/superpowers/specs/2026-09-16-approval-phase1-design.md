## 4. 調べて分かった事実（2026-09-15〜16 に実物で確認）

### 4.1 ログインとミドルウェア

- ログイン: `app/Http/Controllers/Auth/AuthController.php` — `email` を `required|email` で検証 → `Auth::attempt($credentials, remember)` → 無効（`status`）ならログアウトして差し戻し → セッション再生成 → `last_login_at` 更新 → `LoginHistory` 作成 → `must_change_password` なら `password.change` へ → 経営層は `dashboard.executive`・それ以外は `dashboard.tenant` へ。画面は `resources/views/auth/login.blade.php`（`name="email"` `type="email"`）
- 今のログイン試行の制限は `throttle:5,1`。未ログインだと IP（`domain|ip`）で数え、成功も 1 回に数える（`ThrottleRequests::resolveRequestSignature` / `handleRequest`）
- Laravel 12.55 の `Limit` には `after($callback)`（応答を見て数えるか決める）と `response(callable)` がある（`Cache/RateLimiting/Limit.php` 145・158 行）。`ThrottleRequests` は `afterCallback` が true を返したときだけ数える（169 行）
- パスワード変更: `PasswordController`（8 文字以上・英字と数字）→ 変更後は `route('dashboard')` へ。`/dashboard` のクロージャ（`routes/web.php` の先頭）がロールで振り分ける
- ミドルウェアの別名: `role` = `CheckRole` / `department.access` = `CheckDepartmentAccess`（経営層は全部通し、それ以外は `department_user` で判定。fail-closed）/ `password.change` = `ForcePasswordChange`（許可は `password.change`・`password.update`・`logout`）
- 既定の優先順（`Foundation/Http/Kernel::$middlewarePriority`）: … `StartSession` → `ShareErrorsFromSession` → `AuthenticatesRequests` → `ThrottleRequests` → `ThrottleRequestsWithRedis` → `AuthenticatesSessions` → `SubstituteBindings` → `Authorize`。`appendToPriorityList` / `prependToPriorityList` で割り込める
- ログイン済みの人が `guest` のルート（`/login`）を開くと、`RedirectIfAuthenticated` が `dashboard` という名前のルートへ送る
- ルート（2026-09-15 に worktree で `route:list` を実測）: 全 430 本。web グループ 427 本・`auth` 425 本・`password.change` 424 本。web の外は 3 本（`storage/{path}` の GET と PUT＝local ディスクの `serve` による署名つき URL 用・`/up`）。名前の無いルートは `GET /`・`POST /login`・`GET /up`。**`/dashboard/tenant` には `role:` も `department.access` も無く、全ロールが見られる**（＝ロールだけでは決裁のみ利用者を止められない画面が実在する）
- `routes/web.php` は 1 ファイル（1781 行）。`ARCHITECTURE.md` にある `buyer_routes.php` などの読み込みは今は無い

### 4.2 無効化と「ログインしたままにする」

- 無効（`status`）を確かめているのは**ログインした瞬間だけ**（`AuthController.php:47`）。`Admin\UserController::toggleStatus()` は状態を変えるだけで、セッションにも「ログインしたままにする」の鍵（`remember_token`）にも触れない
- 「ログインしたままにする」の有効期間は 576000 分＝400 日（`SessionGuard::$rememberDuration`）。セッションが切れても鍵で自動的に入り直し、そのとき無効かどうかは確かめない
- `SessionGuard::logout()` は鍵を作り直す（`cycleRememberToken`）＝ほかの端末の自動ログインも同時に無効になる
- 鍵の Cookie にはパスワードの控え（HMAC）が入っている（`queueRecallerCookie`）。`AuthenticateSession` はこれとセッションの控えを今のパスワードと比べ、違えばログアウトさせる。控えの無いセッションは初回に控えを作るだけ（反映した瞬間に全員がログアウトされることはない）。本人がパスワードを変えた回は、応答のあとに控えを作り直すので本人の端末は切れない

### 4.3 利用者と担当者の選択肢

- `app/Models/User.php` — SoftDeletes（2026-07-03 に追加。**CLAUDE.md の「User に deleted_at 列なし」は古い**）。`role` と `status` は enum キャストで `$fillable` に無い（明示代入）。`departments()` は基幹の `Department`（`department_user`）
- `UserRole` の表示は 経営層 / 部門管理者 / 一般担当者。値を列挙しているのは `admin/users/index.blade.php` の絞り込み（`UserRole::cases()`）と一覧のバッジ（`@switch`）の 2 か所。登録・編集のモーダルの選択肢は 3 つを直書き
- `User::scopeAssignable()` は「有効」だけの条件。基幹の担当者の選択肢は**コントローラ 9 本の 19 か所**すべてが `assignable()` / `assignableWith()` から作る（`CustomerController`・`CustomerSurveyController`・`Dad\ProjectController`・`Housing\HsContractListController`・`Mansion\ContractController`・`Mansion\ParkingContractController`・`RealEstate\ReContractController`・`Tenant\AreaBuildingSurveyController`・`Tenant\InquiryController`）
- 基幹の取込で担当者を氏名で引いている所が 3 か所ある（`Admin\CustomerImportController:238` は部分一致 `like`、`Admin\MansionImportController:888`・`:1133` は完全一致）
- `users` の定義（テスト用 migration `0001_01_01_000000`）: `email` は string(255)・一意・NOT NULL、`role` は enum(executive, manager, staff) 既定 staff、`status` は enum(active, inactive)、`must_change_password` 既定 true。**本番の定義（索引名・照合順序など）はまだ読み取っていない**（§7 の 1）
- `users.email` を使っているのはログインと `Admin\UserController`・`admin/users/index.blade.php` と、コマンド `ZealImportMembersCommand`（`--actor` をメールで引く）

### 4.4 基幹の利用者管理（`/admin/users`・経営層のみ）

- 新規登録: 初期パスワードは**画面の JS が `Math.random` で作り**（`admin/users/index.blade.php` の `regeneratePassword()`）、読み取り専用の欄に出してそのまま送る
- 再発行: サーバーの `generatePassword()`（8 文字・英大小・数字・記号）で作り、**新しいパスワードを平文でセッションのフラッシュ（`reset_password`）に入れる**。セッションの既定の保存先は database（`config/session.php`。本番の `.env` の値は未確認）＝ sessions テーブルに次のリクエストまで平文が残り、閉じたままなら夜間バックアップに入りうる
- 最後の有効な経営層を守る処理（ロール変更・無効化・削除）と、自分自身のロール変更・無効化・削除の防止がある
- 一覧は 20 件ずつ・状態・ロール・基幹の部門・氏名とメールで絞り込める

### 4.5 パスワードの暗号化にかかる時間

- アプリは `config/hashing.php` を持たず、フレームワークの既定（bcrypt・`BCRYPT_ROUNDS` 既定 12・`rehash_on_login` 既定 true）。テストは `phpunit.xml` で `BCRYPT_ROUNDS=4`
- 手元（Apple Silicon）で実測: **強度 12 は 1 人 0.240 秒、強度 10 は 0.065 秒**。強度 12 では 100 人で 24 秒かかり、本番（さくらの共有サーバー）はもっと遅い見込み
- `rehash_on_login` が true なので、低い強度で作ったパスワードは初回のログインで今の強度へ自動で掛け直される（`SessionGuard::rehashPasswordIfRequired`）

### 4.6 そのほか

- 基幹の `departments` / `department_user` は基幹のデータを見られる範囲（tenant・mansion・housing・realestate・welfare・dad・zeal。`CheckDepartmentAccess` とサイドバーが使う）。決裁の所属部門と共用すると、CSV で所属部門を更新したときに基幹の権限まで変わり、12.3「基幹の権限は変えない」に反する（D1）
- DAD の従業員マスタに社員番号の列がある（`dad_employees.employee_code` VARCHAR(20)・一意。画面の例は `M001`）。グループ全体の社員番号とは別物で、今回は使わない
- CSV 取込の既存の型: アップロード → 確認画面 → 描画された「インポート実行」フォーム（hidden の CSV）で確定。部品は `CsvImportReader`（UTF-8・Shift_JIS・EUC-JP を自動判定し BOM を落とす）・`CsvImportTemplate`（BOM 付き UTF-8）・`CsvImportException`。テストは `tests/Concerns/SubmitsImportPreview.php` と `ParsesForms` の往復（Bug #47・#53・#54）
- メール: 段階0 の型（`app/Mail/OpsTestMail.php`＝`ShouldQueue`・`$tries`・`failed()` で日本語をログへ）。キューは database で 5 分おきに送る
- サイドバー（`layouts/partials/sidebar.blade.php`・476 行）は展開・折りたたみ・スマホのドロワーの 3 か所。展開版の「ダッシュボード」見出しと折りたたみ版の `/dashboard` アイコンは**条件なしで出る**。展開版に `x-cloak` を戻さない（Bug #56）

### 5.2 門番（締め出し）

web グループに次の 2 つを足し、優先順の `AuthenticatesSessions` のあと・`SubstituteBindings`（ルートモデル結合）の前に置く（`appendToPriorityList`）。**ルートモデル結合より前で止めるので、存在しない ID でも 404 にならず、データがあるかどうかは漏れない**。

1. `EnsureUserIsActive`（§5.5）
2. `RestrictApprovalOnlyUsers`: 決裁のみ利用者は、次の許可リストにあるルートしか使えない
   - ルート名が `approvals.` で始まるもの
   - `password.change`・`password.update`・`logout`
   - `guest` ミドルウェアを持つルート（未ログイン専用。ログイン済みの人は元から `RedirectIfAuthenticated` が追い返す）

   許可リストに無いときの応答:
   - 画面を開く GET・HEAD（Ajax でないもの）→ 決裁のホームへ転送し、「決裁以外の画面は使えません。」と出す（フラッシュの `warning`）
   - それ以外（POST など・Ajax・JSON を求めるもの）→ 403（`abort(403, '決裁以外の画面は使えません。')`）

- 既存の `role:` と `department.access` も決裁のみ利用者を拒否する（ロールの一覧に無く、基幹の部門にも所属しない）。ただし `/dashboard/tenant` のように両方とも付いていない画面があるので（§4.1）、守りの本体は門番
- `ForcePasswordChange` はルートのミドルウェアなので門番より後に走る。初回ログインの決裁のみ利用者が基幹の URL を開くと、門番がホームへ転送し、ホームで `ForcePasswordChange` がパスワード変更へ送る
- `approvals.admin.*` の `EnsureApprovalAdmin` は、門番を通ったあとの 2 段目（決裁のみ利用者でも、基幹を使う人でも、指定されていなければ 403）

### 5.3 ログイン

- 入力欄: ラベル「社員番号またはメールアドレス」・`name="login_id"`・`type="text"`・`autocomplete="username"`・`autocapitalize="none"`・`spellcheck="false"`
- 照合の手順（`App\Support\LoginId` に 1 つにまとめ、ログイン・試行の制限の数え方・CSV・各フォームが同じものを使う）:
  1. 全角の英数字・記号・空白を半角にし（`mb_convert_kana($v, 'as')`）、前後の空白を除く
  2. `@` を含めばメールアドレスとして小文字にそろえ、`email` で照合する
  3. 含まなければ社員番号として英字を大文字にそろえ、`employee_number` で照合する
- 検証は `login_id` 必須・255 文字まで、`password` 必須。形式が社員番号の規則に合わなくても、そのまま照合して失敗させる（形式の違いを言わない）
- 失敗の文言: 「社員番号・メールアドレスまたはパスワードが正しくありません。」（どちらが違うかは言わない）。未入力は「社員番号またはメールアドレスを入力してください。」
- ログイン後の行き先の規則を `User::homeRouteName()` に 1 つにまとめ、ログイン直後・`/dashboard` のクロージャ（パスワード変更後もここを通る）が使う

| ロール | 行き先 |
|---|---|
| 決裁のみ | `approvals.home` |
| 経営層 | `dashboard.executive`（今までどおり） |
| 部門管理者・一般担当者 | `dashboard.tenant`（今までどおり） |

- 無効なアカウント・`last_login_at`・`LoginHistory`・初回のパスワード変更は今までどおり

### 5.4 ログイン試行の制限（D3・要件定義書からの変更 §3 の 1）

- `AppServiceProvider::boot()` で `RateLimiter::for('login', …)` を定義し、ルートを `throttle:5,1` → `throttle:login` にする
- 制限は 2 つ。回数は 1 か所（設定）に置き、変えられるようにする

| 数える単位 | 上限 | 数える鍵 |
|---|---|---|
| 同じログイン ID・同じ IP | 1 分に 5 回 | `LoginId` で正規化した ID ＋ IP（大文字小文字・全角・空白の違いで回避できない） |
| 同じ IP（ID を問わない） | 1 分に 30 回 | IP |

- どちらも `after()` で**応答のあとも未ログインのまま**（＝失敗・無効なアカウント・入力エラー）のときだけ数える。成功は数えない
- 30 回は、説明会で一斉にログインして初期パスワードの打ち間違いが重なっても止まらないための数（会社の PC は外から同じ IP になりやすい）
- 止まったら 429 の英語の画面ではなく、`response()` でログイン画面に戻し、「ログインの試行回数が多すぎます。〇秒後にもう一度お試しください。」と出す（秒は `Retry-After`。入力したログイン ID と「ログインしたままにする」は残す）
- 既存の `tests/Feature/Auth/LoginThrottleTest.php` の 2 本目（別の ID で 5 回失敗すると正しい資格情報でも 429）は、新しい規則で書き直す

### 5.5 無効化とパスワード変更の効き目（D7・D11）

- **`EnsureUserIsActive`**（web グループ）: ログイン中の人（「ログインしたままにする」で自動的に入り直した人を含む）が無効なら、ログアウト・セッションの破棄・CSRF トークンの作り直しをして、ログイン画面に「このアカウントは無効になっています。管理者にお問い合わせください。」（ログイン時の既存の文言。D15）と出す。Ajax・JSON には 401
  - ログアウトが鍵を作り直すので、ほかの端末の自動ログインも同時に無効になる（§4.2）
- **`AuthenticateSession`**（Laravel 標準。web グループに追加）: パスワードの再発行・本人の変更のあと、ほかの端末は次の操作でログアウトになる。変えた本人の端末はそのまま（§4.2）
  - 乗っ取られたアカウントも再発行で取り戻せる。今のままだと再発行しても相手のログインは続く
  - ⚠ 基幹の動きが変わる点: 本人がパスワードを変えると、ほかの端末（スマホなど）のログインも切れる
- 削除（SoftDelete）された人は、今でも利用者を引けずに実質ログアウトになる（変更なし）

### 5.6 利用者（users）の改修

- `employee_number` VARCHAR(20)・NULL 可・一意。保存の前に `LoginId` と同じ正規化をかけ、形式は `^[A-Z0-9-]{1,20}$`（D5）
- `email` を NULL 可にする（一意はそのまま）。前後の空白を除き小文字で保存し、空文字は NULL に直す（同じ正規化をモデルで行う）
- `role` に `approval_only` を足す: `UserRole::ApprovalOnly`・表示「決裁のみ」・`isApprovalOnly()`。`isExecutive()`・`isManagerOrAbove()` は false
- すべての登録・編集の経路で「**社員番号とメールアドレスのどちらかは必須**」（ログイン ID の無い人を作らない）
- 画面と CSV の入力は、**検証の前に正規化する**（一意の検査を保存する値で行うため。正規化の前の値で検査すると、大文字小文字の違いを本番の MySQL は同じとみなし、テストの SQLite は別とみなすので、テストだけ通って本番で一意の索引に当たりうる）
- 削除済みの利用者の社員番号・メールアドレスも一意の索引に残るので、同じ値では新しく登録できない（メールアドレスは今もそう。CSV での扱いは §5.10）
- `User::scopeBaseUsers()`（決裁のみ以外）を足し、`scopeAssignable()` を「有効かつ決裁のみ以外」にする。これで基幹の担当者の選択肢 19 か所に決裁のみ利用者が並ばない。`assignableWith($currentId)` は今の担当者を必ず含める今の意味のまま
- 基幹の取込で担当者を氏名で引く 3 か所（§4.3）にも `baseUsers()` を付ける（100 人以上増えると、部分一致で別人を拾う恐れがあるため）
- 決裁の関係: `approvalMember()`（hasOne）・`approvalDepartments()`（belongsToMany）・`isApprovalAdmin()`・`canViewAllApprovals()`（段階2 で使う）・`isApprovalPresident()`

### 5.7 基幹の利用者管理（`/admin/users`・経営層のみ）

- **一覧**: 社員番号の列を足し、検索の対象を氏名・社員番号・メールにする。ロールの絞り込みには「決裁のみ」が自動で加わる（`UserRole::cases()`）。一覧のバッジに決裁のみの色を足す。社長・全件閲覧・決裁の管理者の印を氏名の横に出す
- **社長**: 画面の上に「決裁の社長: 〇〇（変更）」の欄を置く（未指定なら「未設定」）。変更のモーダルの選択肢は、有効でメールアドレスのある利用者（基幹を使う人・決裁のみ利用者のどちらも。3.1）。「未設定に戻す」は作らない
- **新規登録**: 社員番号の欄を足し、メールアドレスを任意にする（どちらかは必須）。ロールの選択肢は今の 3 つのまま（決裁のみ利用者は決裁の管理者が CSV で登録するため）。基幹の所属部門は今までどおり必須。**初期パスワードの欄と JS の生成をやめ、サーバーで作って登録後にログイン案内の画面（§5.12）に出す**（D12）
- **編集**: 社員番号・全件閲覧者・決裁の管理者を足し、メールアドレスを任意にする。ロールに「決裁のみ」を選ぶと基幹の所属部門の欄が隠れ、保存すると基幹の所属部門（`department_user`）が外れる。決裁のみから基幹のロールに戻すときは、基幹の所属部門が必須
- **パスワード再発行**: 基幹を使う人・決裁のみ利用者のどちらにもできる（12.5）。フラッシュの `reset_password` をやめ、ログイン案内の画面に出したうえで通知メール（§5.13）を送る。一覧の上の再発行結果の表示（`session('reset_password')`）は消す
- **社長の守り**（12.6・3.1）: 社長に指定されている人は、無効化・削除・メールアドレスを空にする操作ができない。「〇〇さんは決裁の社長に指定されています。先に社長の指定を変えてください。」と出す（部門長・審査担当者の分は段階2 で足す）
- 今ある守り（自分自身のロール変更・無効化・削除の防止、最後の有効な経営層の保護）はそのまま
- 変更はすべて記録する（§5.14）

### 5.8 部門の管理（決裁の管理者・`approvals.admin.organization.*`）

画面は 1 枚で、「会社」「部門」「許可するドメイン」の 3 つの欄を並べる。追加と編集は基幹の利用者管理と同じくモーダル。変更はすべて記録する。

**会社**
- 会社名（50 文字まで・重複不可）・期の始まりの月（1〜12）・表示順
- 本番の SQL で 3 社（ミツワ都市開発 5 月・DAD 6 月・ZEAL 6 月。要件定義書 6.2）を入れておく。名前と月は画面で直せる
- 部門が 1 つでもある会社は削除できない

**部門**
- 会社（必須）・部門名（50 文字まで。同じ会社の中で重複不可）・略称（データ印の上段に入るので 6 文字まで）・アルファベット（英大文字 1〜3 文字。全角→半角・大文字にそろえる。グループ全体で重複不可。6.1）・表示順
- 一覧は会社の表示順 → 部門の表示順。所属の人数も出す
- 所属者がいる部門は削除できない（段階2 で「申請がある部門」の条件も足す）
- 部門長・審査担当者・今年度の開始番号は段階2 でこの画面に足す

**所属部門**
- 編集は利用者の管理（§5.9）と CSV（§5.10）で行う。この画面では人数を出すだけ
- 基幹の `departments` / `department_user` とは別の表で、互いに影響しない（D1）

**許可するドメイン**
- ドメインだけ（例 `mitsuwat.co.jp`。前後の空白を除き小文字で保存。`@` は付けない・付いていたら外す）。メールアドレスの `@` より後ろが**完全に一致**したときだけ許可する（サブドメインは別に登録する）
- 使い道は 2 つ: ① CSV のメールアドレスの検査 ② 通知メールの宛先の制限（8.2）
- 基幹の利用者管理の登録・編集では検査しない（ドメインがまだ登録されていない時期に、基幹の利用者の登録ができなくなるのを避けるため）
- 削除はいつでもできる。確認のモーダルに「このドメインのメールアドレスを持つ利用者: N 人（この人たちには通知メールが届かなくなります）」と出す

### 5.9 利用者の管理（決裁の管理者・`approvals.admin.users.*`）

- **一覧**: 削除されていない全員（基幹を使う人も所属部門の設定対象。3.2）。20 件ずつの番号つきページ送り（プロジェクトの規約）
  - 絞り込み: 区分（基幹を使う人・決裁のみ）・部門（「所属部門なし」も選べる＝申請できない人を見つけるため。5.1）・状態（有効・無効）・未ログイン（`last_login_at` が空）・キーワード（氏名・社員番号・メール）
  - 列: 選択（決裁のみ利用者の行だけ）・社員番号・氏名・区分・所属部門・メールアドレス・最終ログイン・状態・操作
- **編集**（モーダル）
  - 所属部門: 全員について編集できる
  - 氏名・社員番号: 決裁のみ利用者だけ（D8）。基幹を使う人と、社長・全件閲覧者・決裁の管理者に指定されている人は読み取り専用（D16）
  - メールアドレス: 読み取り専用。「変更は基幹の管理者に依頼してください」と添える
- **無効化・有効化**: 決裁のみ利用者だけ。自分自身は無効化できない。社長・全件閲覧者・決裁の管理者に指定されている人は無効化できない（D16）。文言は §5.7 と同じ形で「〇〇さんは決裁の〈社長／全件閲覧者／決裁の管理者〉に指定されています。基幹の管理者に依頼してください。」
- **パスワード再発行**: 決裁のみ利用者だけ（D8。基幹を使う人は基幹の管理者が再発行する）。社長・全件閲覧者・決裁の管理者に指定されている人は対象外（D16）
  - 1 人ずつ（行の操作）
  - まとめて（D9）: チェックで選んだ人、または「絞り込んだ全員（N 人）」。確認のモーダルに人数と氏名を出す。「絞り込んだ全員」は、確定の時にサーバーが同じ条件で引き直し、決裁のみ・有効・未削除**かつ決裁の権限に指定されていない人**に限る。一覧の選択欄も、指定されている人の行には出さない（静かに外すのではなく、選べないようにする）
  - 1 回に 200 人まで（超えたら絞り込みを求める。処理時間の上限のため。§5.10 の処理時間）
- 変更はすべて記録する

### 5.10 CSV 一括登録（`approvals.admin.users.import.*`）

**流れ**（既存の型）: アップロード → 確認画面 → 描画された「取り込む」フォーム（hidden の CSV と 1 回限りの鍵）で確定 → **確定時にサーバーで検査をやり直す**（hidden を信用しない）→ 結果の画面＝ログイン案内の画面（§5.12）

**ファイル**
- 文字コードは `CsvImportReader::decode()`（UTF-8・Shift_JIS・EUC-JP を自動判定）。テンプレートは `CsvImportTemplate`（BOM 付き UTF-8）
- 列: 社員番号・氏名・メールアドレス・所属部門。1 行目の見出しの名前で列を見つける（列の順番は問わない）。見出しが 1 つでも見つからなければ、ファイル全体をエラーにする。⚠ **文言は共有部品（`CsvImportReader`）のものを使う**（既存の取込 4 本と揃える）。実装の文言は **「必須ヘッダー「〇〇」がCSVに見つかりません。」**（`CsvImportReader::parse()` は最初に見つからなかったキーで throw するので、**足りない見出しは 1 つだけ**挙げる）。4 本が共有しているので、ここだけ変えない
- 所属部門は部門のアルファベットを並べる。区切りはカンマ・スラッシュ・空白・読点・中黒のどれでもよい（全角も可。英字以外はすべて区切りとみなす）
- 1 ファイルの行数の上限は **`config/approval.php` の `csv_max_rows` が正本**（2026-09-16 の本番実測で **50**）。まとめて再発行の 1 回の人数と同じ理由で、根拠は下の「処理時間」。⚠ **この文書に数を書き写さない**（書くと config と食い違う）

**行の検査**
- 社員番号: 必須。正規化してから D5 の形式
- 氏名: 必須・100 文字まで
- メールアドレス: 任意。書くなら形式が正しく、許可するドメインに限る。ドメインが 1 件も登録されていないうちは、メールアドレスのある行をエラーにして「許可するメールのドメインが登録されていません（部門の管理で登録してください）」と出す
- 所属部門: 1 つ以上。すべて登録済みの部門のアルファベットであること
- 同じファイルの中で社員番号またはメールアドレスが重なる行は、どちらもエラー

**既存の利用者との照合**（削除済みも含めて引く）

| 状況 | 扱い |
|---|---|
| 社員番号が A さん、メールアドレスが B さんに一致 | エラー行「社員番号は A さん、メールアドレスは B さんと一致します」 |
| 一致したのが削除済みの利用者 | エラー行「削除済みの利用者（〇〇さん）と一致します。基幹の管理者に復元を依頼してください」（一意の索引に当たって取込全体が巻き戻る型を防ぐ。Bug #60 と同じ型） |
| 一致した（同じ 1 人） | **更新**: 社員番号と所属部門だけを書き換える（所属部門は置き換え）。社員番号が変わるときは「ログイン ID が X から Y に変わります」と予告する。氏名・メールアドレス・ロール・状態は変えず、CSV と違えばその旨を注意として出す（「氏名が登録と違います（変えません）」「メールアドレスは変えません（変更は基幹の管理者に依頼）」「無効の利用者です（有効化は利用者の管理で）」） |
| 一致しない | **新規**: ロールは決裁のみ・有効・初回にパスワード変更を求める状態。初期パスワードは確定の時に 1 人ずつ作る（§5.11） |

- 基幹を使う人に一致した場合も、変えるのは社員番号と決裁の所属部門だけ（基幹のロール・基幹の所属部門は変えない。12.3）
- **エラー行が 1 行でもあれば、その回はまるごと取り込まない**（確認画面に取込のボタンを出さず、確定でもサーバーが同じ条件で断る）。CSV を直して上げ直してもらう
  - ⚠ **利用者の判断（2026-09-17）。既存の取込 4 本（「エラー行は飛ばして正しい行だけ入れる」）とは違う。**
    理由は 2 つ —— ①**新しく登録した人には初期パスワードの案内を印刷して手渡す**ので、部分的に入ると案内が
    2 回に分かれて**配り漏れの元になる** ②1 ファイル 50 行までなので、直して上げ直す手間が小さい
- **1 行 1 人。** 同じファイルの中で社員番号・メールアドレスが重なる行に加えて、**別のキーで同じ既存利用者に当たる 2 行**（行1 が社員番号で X さん・行2 がメールアドレスで同じ X さん）も、どちらもエラーにする。⚠ 見逃すと `apply()` が順に適用して**後の行が前の行を無音で上書きする**（一意の索引には当たらないので DB も止めない）
- 確認画面ではエラー（`rowErrors`）と注意（`warnings`）を別々に出す（Bug #53・#54 ④）。件数（新規 N・更新 M・エラー K）も出す
- **新しく登録した人が 1 人もいない回はログイン案内を返さない**（取込画面へ戻して成功を知らせる）。⚠ 印刷する初期パスワードが 1 つも無いのに「この画面を閉じると初期パスワードは二度と表示されません」だけが出て誤解を招くため
- 確定は 1 つのトランザクションで行う
- 新規登録では通知メールを送らない（8.1 に無く、紙で渡すため）

**処理時間**
- 新規の人ごとにパスワードを暗号化するので時間がかかる（§4.5）。初期パスワードだけ強度を 10 にし（§5.11）、1 ファイル 200 行・まとめて再発行は 1 回 200 人までに抑える（手元の速さで 200 人 約 13 秒）
- 本番の速さは反映の前に測り（§7 の 1）、上限の 200 はその結果で決め直す（利用者は 100〜200 人の想定。要件定義書 14.5）
- ⚠ **2026-09-16 に本番で実測して 50 へ下げた** — 強度 10 が **0.305 秒/件**（手元の 4.7 倍）で、200 人だと 1 リクエスト 61 秒になり Apache / FastCGI の待ち時間に収まらない恐れがある。50 人なら約 15 秒。稼働前の一括登録は 2〜4 ファイルに分ける。数は `config/approval.php` の 1 か所（実装計画 §0.4・§0.7 の P5）

### 5.11 初期パスワード（D13）

- 作る部品を 1 つ（`App\Support\InitialPassword`）にし、基幹の新規登録・基幹の再発行・CSV・決裁の管理者の再発行（1 人・まとめて）がすべてこれを使う。今の `generatePassword()`（8 文字・記号入り）と画面の JS の生成はやめる
- 10 文字・英小文字と数字だけ・見間違えやすい文字（0 o 1 l i）を除く（英字 23 種＋数字 8 種）。英字と数字を必ず 1 文字以上含め、暗号用の乱数（`random_int`）で作る。スマホで打ちやすく、本人が決めるパスワードの規則（8 文字以上・英字と数字）も満たす
- 暗号化の強度は 10（`Hash::make($pw, ['rounds' => 10])`）。初回ログインで今の強度（12）へ自動で掛け直され（`rehash_on_login`）、そもそも初回にパスワードの変更も求める。無作為な 10 文字を一時的に守るには十分
- 初期パスワードは画面に出すだけで、DB（ハッシュを除く）・セッション・ログ・記録には残さない
- ⚠ **稼働前に、本番の php.ini で `zend.exception_ignore_args=1` を確かめる**（要件定義書 16.3 の 15「本番の php.ini の調整」と同じ作業のついでに見る）。`Off` だと PHP は例外のトレースに**引数の値**を載せ、文字列は 15 文字で切られるものの**初期パスワードは 10 文字なので全部載る**。`InitialPassword::hash($plain)` / `User::setInitialPassword($plain)` のフレームが積まれている最中に例外が出ると、平文が `laravel.log` に残る経路が理論上できる（2026-09-17 の Task 13 のレビューで指摘。手元の php.ini は `Off` を実測）。⚠ **特定の画面の欠陥ではなく 4 経路すべてに等しく当てはまる**（基幹の新規登録・基幹の再発行・決裁の再発行・CSV の一括登録）ので、塞ぐ場所はアプリのコードではなく php.ini。⚠ アプリ側で平文を引数に取らない形へ寄せることもできるが、`Hash::make()` に渡す時点で必ずどこかのフレームには載るため、**根治は php.ini のほう**

### 5.12 ログイン案内の画面（D4・D9）

- 確定・再発行の POST の応答として、その場で描画する（リダイレクトしない）。`Cache-Control: no-store` を付ける
- 使う場面: 基幹の新規登録・基幹の再発行・CSV の確定・決裁の管理者の再発行（1 人・まとめて）。画面は共通の部品 1 つ
- **1 回限りの鍵**: これらのフォームに鍵（無作為な値）を入れ、処理した鍵を記録する（`Cache::add`・12 時間）。同じ鍵の 2 回目は処理せず「この操作はすでに実行されました。案内を印刷し直すには、もう一度再発行してください。」と出す。ブラウザの「フォームを再送信しますか」で続けてしまうと、印刷済みの案内がこっそり無効になるのを防ぐため
  - **基幹の新規登録だけ文言を変える**: 「この操作はすでに実行されました。案内を印刷し直すには、対象の利用者からパスワードを再発行してください。」（登録の画面に「再発行」という操作が無いため）
  - **鍵を使う（claim する）のは検証が通ったあと**、実際に作る・変える直前にする。**起きなかった処理で鍵を焼かない**ため
    - ⚠ **実測（2026-09-16）**: 基幹の利用者管理の画面では、hidden が描画のたびに `OneTimeAction::issue()` を呼び、検証エラーは `back()`（＝一覧を GET し直す）なので**毎回あたらしい鍵**になる。つまりこの画面では、順序を誤っても「送り直せなくなる」現象は起きない（焼けるのは捨てられる側の鍵）。**以前ここに「差し戻したフォームは同じ鍵を持ったまま再描画される」と書いていたのは誤り**
    - ⚠ **実測（2026-09-17・Task 13）**: CSV の確定も**同じ鍵を再掲しない**。確認画面は毎回 `preview` の POST の応答として描き直され、そのたびに `OneTimeAction::issue()` が呼ばれる（同じ CSV を 2 回上げた鍵は**別物**だった）。確定が断られたときの差し戻し先は `GET /users/import`（アップロードの画面）で、そこには `guide_token` も `csv_data` も**無い**（利用者は上げ直す）。つまりこの画面でも順序を誤って「送り直せなくなる」ことは起きず、焼けるのは捨てられる側の鍵。**ただし順序は正しいままにする** —— 起きなかった処理で鍵を焼かないという決まり自体は変わらない（`UserImportController::execute()` は検査をやり直し、行エラー・0 件を断ったあとで `claim()` する）
- 印刷用の独立したページ（サイドバー・ヘッダーを出さない）。`@page { size: A4; margin: 0; }` とし、余白はページの中の要素で取る（ブラウザが余白に日時や URL を印刷しないように）。1 人 1 ページ（`break-after: page`）
- 1 ページに載せるもの:
  - 見出し「ログインのご案内」とシステム名
  - 氏名、ログイン ID（社員番号。無い人はメールアドレス）、初期パスワード（大きな等幅の文字）
  - QR コードと URL（ログイン画面）
  - 初回ログインの手順: ① QR を読み取るか URL を開く ② ログイン ID と初期パスワードを入れる ③ 新しいパスワードを決める（8 文字以上・英字と数字を含む）
  - 注意書き: 初回ログインのあとは使えなくなる／本人以外に見せない／新しいパスワードに変えたらこの紙は破棄する
  - 発行日（同じ人に 2 枚あるときにどちらが新しいか分かるように）
- 画面にだけ出る帯（印刷しない）: 「印刷する」ボタン・「N 人分」・「この画面を閉じると初期パスワードは二度と表示されません。印刷してから閉じてください。」・通知メールの件数（§5.13）・元の画面へ戻るリンク。閉じようとしたらブラウザの確認を出す（`beforeunload`。D9）
- **QR**: 中身はその場のリクエストから作ったログイン画面の URL（`route('login')`。本番では `/system/manage/index.php/login` の形）で、全員同じ。サーバーで SVG を 1 回作ってページごとに使う。部品は実装計画で context7 を使って選ぶ（候補 chillerlan/php-qrcode・bacon/bacon-qr-code。条件: GD や Imagick が要らない SVG 出力・PHP 8.3・ライセンス・vendor ごと本番へ送れること）

### 5.13 再発行の通知メール（12.5・8.1・8.2）
